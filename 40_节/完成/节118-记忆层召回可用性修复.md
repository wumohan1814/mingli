### ③ 复测：BM25 召回表达方式（本地 SQLite 3.50.4 / FTS5，DDL 与线上一致 `tokenize='trigram'`）
| 查询表达 | 命中 |
|---|---|
| **现状**：整句短语 `"我今年财运怎么样"` | **0** |
| **改法**：3-gram OR `"我今年" OR "今年财" OR "年财运" …` | **1** ✅ |
| 2 字词项 `"财运"`（加引号 / 不加引号） | **0 / 0** |
| 2 字短问 婚姻 / 财运 / 事业 / 什么 | **全 0** |
| 无关问句 `"我想知道我什么时候能结婚"` | 0（正确的 0，无对应记忆） |

→ **结论**：`trigram` 下**短语查询 = 要求记忆原文包含用户原句的连续子串**；而 **<3 字的词项根本无法匹配**（与 `service.py` L368 `len(eff_query) >= 3` 的门槛同源）。因此线上实际生效的通道**几乎恒为 recency** —— 即"按重要度+新鲜度取记忆"，与当前问题无关。**这是"记忆看起来有、其实没用"的结构性根因。**

## 优化方向（四个方向 · 全部零新增算力）

### 方向一 · 召回可用性修复（**最优先，成本≈0**）
1. **查询表达改造**（修 R1）：整句短语 → **切分为 ≥3 字词项 + `OR` 连接**；可"短语优先，无命中再 OR 兜底"两段式
   - 零 schema 改动、零新依赖、同一索引；`MATCH` 词项由 1 → ~N，在单用户 ≤300 条索引上可忽略
2. **短问兜底**（修 R2）：<3 字时**不再直接退化 recency**，改用**一次 `LIKE '%词%'` 扫该用户活跃事实**（≤300 行，微秒级），保住相关度
3. **tags 进场**（修 R4）：tags 已由 LLM 免费产出却被丢弃 → 至少作为 **Python 侧关键词补充源**
   - **更正（清点后）**：tags 进 FTS 索引**不是"需另案评审的未知迁移"** —— 参考项目 `agent-memory-main/storage/schema.sql` 有现成实现：`fts5(content, tags)` **两列** + 3 个触发器用**嵌套 `replace()`** 把 `tags_json` 的 JSON 标点拍平成可检索文本，并用 `content='memories'` **外部内容表**模式，**约 35 行可直接抄**。⚠️ §禁碰清单的"单独评审"要求保留（毕竟要动 DDL/触发器），但**已知成本极低、无未知陷阱**
   - 更轻的替代（**不动表结构**）：参考 `agent-memory-main/extraction/entity_extractor.py` —— **13 行纯正则**实体抽取（`#标签` / 英文大写词 / `[\u4e00-\u9fff]{2,8}` 中文块）+ `entity_index(entity, memory_id)` 复合主键表 + `search_by_entities(limit=10)`，**零依赖零 LLM 无向量**。⚠️ 需自配停用词表过滤垃圾片段

### 方向二 · 打分公式修复（成本 = 纯算术，无新查询/新内存）
4. **RRF 多路融合**（修 R3）：把"二选一"改为融合 bm25 + recency（+ 将来的其它通道）
   - 借参考项目 `controller/router.py` L51-56（`1/(k+rank)` 累加，k=60，**6 行、零依赖**）
   - 代价：条件成立时**会多一次 recency 候选读取**（≤300 行）→ 属"微增"，**必须由基准给数字后决定去留**
5. **`trust` / `access_count` 进打分**（修 R5/R6）：已被维护却从不读取的信号，纯算术接入
6. **`importance` 校准**（修 R7）：按 `fact_type` 先验 + 钳制区间，降低 LLM 数值漂移对排序的影响

### 方向三 · 写入侧质量（成本 = 0，同一个 LLM 调用内）
7. 抽取 prompt（L117-129）要求产出**可检索关键词**并与 `tags` 对齐（现在只说要 2~5 个"简短关键词"，没定义用途）
8. 近重复事实治理：现在只按 `content_hash` **精确**去重（L158-160），语义重复仍会白占 300 条额度

### 方向四 · 离线基准（零线上负担，**建议第一个做**）
9. 自建离线基准：离线、不联网、不依赖向量，用播种类语料
   - **baseline 必须是"当前实现"**——参考项目自带的 baseline 是语义检索本身，不搬向量则无意义；其 `NEGATIVE` 项 30/30 是平凡项、会虚高总体，**不可当验收线**
   - 指标：命中率 / 延迟 p50·p95·p99 / 单次召回查询次数 / 进程峰值内存

### 方法学发现：延迟 +9.06ms 是**机器状态假象**（已证伪）

| 通道 | 理论天花板 |
|---|---|
| BM25 词项 OR | **3/70 = 4.3%** |

## 结构反思（破竹 §8）
- **哪里难**：记忆层最贵的能力（语义）在这台机器上买不起，于是"看起来只能靠加算力"。但真正的问题不在算力层，而在**检索表达层**——一个 `_fts_quote()` 把整句包成短语，就让整个 BM25 通道事实上停摆，而 recency 兜底把这件事**掩盖得很好**（永远有记忆注入，只是不相关）。
- **结构上怎么改**：把"召回"拆成三层各自独立可测——**表达（怎么问）→ 融合（怎么排）→ 打分（怎么加权）**。现状三层混在 `recall_memories` 一个函数里（L338-428），所以任何一处失效都无法单独观察。
- **下次会怎样**：有了离线基准，召回质量从"凭感觉"变成"看数字"；将来若要上语义通道，也是在同一套基准下与 BM25 对比后再定——**而不是先装模型再找理由**。
