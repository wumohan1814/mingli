## 第 4 项评估（首屏懒加载）· 待用户决策
- 事实：首屏 14 个外链 / 316KB gzip，其中占卜域 views-divination.js（91KB）、西式域 views-xishi.js（56KB）首页即加载，但用户未必进入。
- 取舍：当前是**全局作用域 + 顺序加载**架构，`<script defer>` 不安全——视图脚本必须先于 `index.html` 内联 App mount 执行，否则 render 时组件未定义。真正省字节需**按域动态注入**（进入该域再加载其 `views-*.js`），要引入加载态与顺序保证，且验收需用户浏览器亲验。
- 收益：首屏约 -147KB gzip / -2 请求（对**首次**访客）；对回访用户，第 2 项的 1h 缓存已把 316KB 变成「通常不重新下载」。
- 建议：**暂缓，另立一节做**（成本/风险偏高、需浏览器验收；不值得在当前这节塞进去）。

## 结构反思（破竹 §8）
- 哪里难：静态资源「既打进镜像（79.5MB）又由 Python 逐请求服务」——位置与服务方式耦合。
- 怎么改：第 1 项把「服务方式」拆成独立接缝（Caddy 直服），Python 只管 `/api` 与兜底。**已落地**。
- 下次会怎样：新增静态目录只需在 Caddyfile 加一条 matcher，不必让 Python 参与。
- 顺带收益：`web` 容器访问日志不再被 79% 静态请求刷屏，真实 API 负载更清晰可观测。
