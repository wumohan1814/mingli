## 〇、战略再澄清（2026-09-13 第二次沟通，覆盖前述理解）

**项目定位：开源项目**。其他开发者进入项目有两个选择：① 自行部署到自己的服务器（Web 形态）② 直接安装本地 APK。两条线路功能同源（「所有类型都一样」），差异只在能力提供者和运行条件。

**胖 APK 形态（用户已拍板技术路线 = 原方案乙）**：APK 包含全部内容（前端 + 排盘引擎 + 业务后端 + 素材 + prompt + 题库）。

**联网与 LLM 条件**：
- 是否联网由安装者决定（APK 本身不默认外联官方）
- LLM 功能**双条件**：安装者提供了 API Key **且** 允许联网，两条件同时满足才可用；无 Key 时确定性排盘类功能照常，LLM 功能不可用（入口给引导提示）

**APK 双运行模式（安装者二选一，可切换？待拍板）**：
- **模式 S · 单机**：APK 独立使用，在 APK 设置中填入 LLM API 地址 + Key，直连 LLM；数据全在设备本地
- **模式 C · 客户端**：在 APK 中填写线上「命理」服务的**网址 + 用户名 + 密码**，APK 绑定该自部署服务成为客户端；账号/数据/LLM 均走服务器

**维护责任边界（用户原话口径）**：开发者不负责本地 APK 的数据保存，也不负责他人自部署后的维护与保存。需转化为：开源协议免责声明 + 自部署文档（README/Docker）；本地导出备份是否仍做见待拍板第 5 项。

### 三种交付形态总矩阵

| | Web 自部署（浏览器） | APK · 单机模式 S | APK · 客户端模式 C |
|---|---|---|---|
| 前端 | 同源代码 | 同（壳内 WebView） | 同（壳内 WebView） |
| 排盘引擎 | 服务器 Node | **机内内嵌** | 服务器（内嵌的不参与？待拍板） |
| 业务后端 | 服务器 Python | **机内内嵌** | 远程自部署服务 |
| LLM Key | 服务端 .env（运维后台配置） | 机内设置自填 | 服务器配置 |
| LLM 联网 | 服务器→LLM | 设备→用户填写端点 | 服务器→LLM（设备不直连） |
| 账号 | 有（自部署者管理注册策略） | 无 | **有**（登录自部署服务） |
| 数据 | 服务器 DB | 设备本地 | 服务器 DB |
| 计费 | 随金数据删除节落地（另一 session 立项） | 无 | 随服务器策略 |
| 素材/Prompt 管理 | 运维后台 | 个人设置（管本机） | 隐藏（内嵌后端休眠，归服务器 admin） |
| 更新 | git pull / 重新部署 | 安装新版 APK | 服务器更新；APK 壳版本可较低频 |

**线上版「API 填写移到运维后台」在此定位下的含义已自洽**：Web/客户端模式下 Key 是服务端运维配置（本就在 admin 配置分区）；单机模式下 Key 才出现在 APK 的个人设置。即同一功能按运行模式出现在不同位置。

## 二、现状家底（2026-09-13 调研）

| 层 | 现状 | 对 APK 的含义 |
|---|---|---|
| 前端 | 免构建静态 React（UMD 多文件）+ PWA（sw.js/manifest，已有「安装到桌面」） | 可直接被 Capacitor/TWA/WebView 壳包成 APK，UI 层零重写 |
| 排盘引擎 | **Node 22 子进程**（`paipan-node/server.mjs`；vendored `mingyu-core`、`ziwei.cjs`；依赖 iztro），Python `paipan.py` 经 subprocess/HTTP 调它 | 引擎本身是 JS，理论可塞进 APK 的 WebView 同进程跑，不必带 Node 运行时；需做 Node API 适配层 |
| LLM 调用 | **全部在 Python 后端**：prompt 拼装、9 法并发编排（orchestrator）、校验子会话、合成器、合规护栏、重试、解读缓存 | 离线 APK 需把这部分逻辑在端侧重写/内嵌（见第五节三路线） |
| 数据 | MySQL（用户/档案/排盘/method_results/解读缓存/余额/订单/事件埋点） | APK 需换成本地库（WebView 内 IndexedDB 或端侧 SQLite），单用户模型 |
| 账号 | JWT + 刷新令牌 + 图形验证码 + 强制建档（REQ-092）+ 注册赠送余额 | APK 无账号；建档保留（单用户直接建），去掉登录态与权限中间件 |
| 计费 | credits 模块（余额、金数据充值轮询、兑换码、手动充值、扣费/退款、LLM 成本核算、付费门） | APK 整条摘除：余额条、付费按钮、金数据、兑换码、订单相关 UI/接口 |
| 分享 | case_share（档案分享免登录填写）、MBTI 分享链接 | APK 整条摘除（无服务器无法承接链接） |
| 后台 | admin.html 5 分区：报表/用户/Prompt/素材/配置；**LLM Key 在配置分区无入口**（配置分区只列 `recharge_rate` / `free_credit_on_register` 两个白名单键；原 `POST /admin/ops/llm-key`（operator+）自 2026-09-21 起 fail loud 拒绝写入，Key 只走系统环境变量 `MINGLI_LLM_API_KEY`） | APK 个人设置需**新增**：自填 API（地址+Key+模型名）、素材管理、Prompt 管理 |
| 素材 | 图片素材在服务端磁盘（/art），后台上传替换 | APK 把 /art 随包内置；「素材管理」= 端侧本地替换/导入 |
| Prompt | 23 个 .md 文件服务端磁盘读取，后台可在线编辑/版本/回滚 | APK 随包内置默认 prompt；「Pro 管理」= 端侧本地编辑（默认理解 = Prompt 管理，**待用户确认**） |
| MBTI | 题库/计分 Python（题库 JSON 已静态），文案后端托管 | 题库随包；计分逻辑小，需移植到端侧 |
| Agent | POST /api/agent/chat + 记忆层（memory 服务+表） | 端侧可走用户 API；记忆换成本地存储 |
| 埋点/报表 | events 模块 + admin 报表/漏斗/LLM 成本 | APK 无埋点上报（或仅本地日志）；无运营报表 |
| 构建部署 | Docker/Caddy 部署；前端免构建 | 需新增 APK 构建链（壳工程 + 签名 + 版本管理 + CI） |

## 三、用户问的开放问题：两条线还应该区分什么（差异矩阵）

除用户已提的 4 点（功能整合/网络接口/计费/账号社交）外，系统梳理还应区分：

| # | 维度 | 线上网页版 | 纯 APK 版 |
|---|---|---|---|
| 1 | **分发与更新** | 部署即更新（静态秒生效） | APK 发版/签名/升级；素材与 prompt 不能热推（随包 + 本地可改） |
| 2 | **排盘算位置** | Node 子进程在服务器 | 端侧 JS 引擎（WebView 内）或内嵌运行时 |
| 3 | **LLM 编排位置** | Python 后端（编排/校验/合成/缓存） | 端侧重写或内嵌；直连用户填写的 OpenAI 兼容端点 |
| 4 | **数据存储** | MySQL，多用户，服务端事实源 | 设备本地（IndexedDB/SQLite），单用户；**建议补本地导出/导入备份**（换机/重装不丢档案） |
| 5 | **多设备同步** | 天然云端同步 | 无（除非未来用户自填同步配置，本期不做） |
| 6 | **Key 安全** | .env 服务端保管 | 设备加密存储（Android Keystore），不进日志/截图风险提示 |
| 7 | **网络白名单** | 自有域名 + LLM 域名 | 仅允许访问用户填写的 API 域名（networkSecurityConfig 白名单），其余零外联 |
| 8 | **埋点/运营报表** | events 全量 + 后台漏斗/成本 | 无上报，最多本地日志 |
| 9 | **客服/反馈** | feedback 接口 | 本地暂存或去掉 |
| 10 | **法律文本** | 用户协议+隐私政策（注册流程强校验） | 仍需隐私政策（本地数据说明）；无注册协议勾选环节 |
| 11 | **管理能力位置** | 独立 admin.html（角色权限） | 素材/Prompt/API 并入个人设置（人人是自己机器的管理员，无角色概念） |
| 12 | **解读缓存/扣费语义** | 服务端缓存、二次点击零扣费 | 本地缓存；无扣费概念，但「省自己的 token」仍有缓存价值 |
| 13 | **Agent 记忆** | 服务端记忆层 | 本地记忆（IndexedDB） |
| 14 | **版本兼容/灰度** | 服务端配置开关/热修 | 无法强制升级；需最低版本提示与本地数据迁移预案 |
| 15 | **测试矩阵** | 一套 | 双构建目标 + 真机矩阵（节136 起的真机验收×2） |
| 16 | **包体** | 无 | 内置 /art 全部素材 + 引擎，预估包体几十 MB 级，需做素材分级（首包/按需） |
| 17 | **合规文案口径** | 「趋势参考不做决策建议」等 | 同样保留（护栏 prompt 随包，端侧执行） |
| 18 | **金数据/兑换码/充值** | 保留 | 代码与 UI 构建期剔除 |

**用户未提但我建议必须区分的 3 件事**：
- **a) 本地备份导出/导入**（第 4 行）：APK 无账号无云端，卸载即数据全丢，这是端侧版最大的信任风险，建议 V1 就做
- **b) 数据迁移预案**（第 14 行）：APK 升级后本地库结构要能向前迁移，不能发版后老用户档案打不开
- **c) 功能同步的工程机制**：为避免「做一遍线上再做一遍 APK」，需要构建风味（build flavor）机制——**同一套前端代码 + 渠道开关（web/apk），平台专属模块（计费/登录/分享/admin 路由）构建期或运行时按渠道剔除**，而不是维护两份代码

## 四、用户 APK 要求的落地形态（按双模式修正后）

> 注：以下 4 条在模式 S（单机）完全成立；模式 C（客户端）下账号/计费/分享以所绑定服务器的策略为准（APK 只是壳），素材/Prompt 管理作用域见待拍板第 3 项。

1. **个人设置扩容（模式 S）**：现有 7 项设置 + 三组管理：
   - 「接口设置」：API Base URL、API Key（Keystore 密文存）、模型名、连通性测试；未配置时 LLM 入口给引导提示，确定性排盘照常用
   - 「素材管理」：列出内置素材，支持本地替换、恢复默认
   - 「Prompt 管理」（即用户所称「Pro 管理」，已确认）：列出 23 个 prompt，本地编辑、恢复默认
2. **联网由安装者决定**：APK 不默认外联官方域名；模式 S 仅在用户配置 Key 且允许联网时访问其填写的 LLM 域名；模式 C 仅访问用户填写的服务器域名
3. **模式 S 零计费**：余额条/付费门/金数据/兑换码不渲染，深度解读改为「使用我的 API 解读」；本地缓存同时为用户省 token
4. **模式 S 无账号无分享**：启动即用、档案本地建、分享路由不渲染；模式 C 有登录态，分享能力跟随服务器

## 五、端侧技术路线（2026-09-13 用户已拍板：路线乙·胖 APK）

- ~~路线甲·瘦客户端（全 JS 移植）~~ 未选
- **✅ 路线乙·胖 APK（内嵌全部）**：APK 内含前端 + 排盘引擎 + Python 业务后端 + 素材/prompt/题库，单机模式在 127.0.0.1 本地跑完整服务
- ~~路线丙·务实混合~~ 不单独选，但其「LLM 编排 isomorphic 抽离」可作为远期降包体/统一架构的演进方向；**节128 自研内核若选 JS/TS 目标，仍能显著减少胖 APK 双运行时成本**

**胖 APK 技术栈预研点（立项首节做 POC）**：
1. **Python 运行时**：Chaquopy（Gradle 内嵌 CPython）跑 FastAPI + uvicorn 本地端口；需验证 3.13 兼容性、依赖（SQLAlchemy/Pydantic/httpx 等）纯 Python 可装、无 C 扩展障碍
2. **Node 运行时**：nodejs-mobile 跑 `paipan-node/server.mjs`；或把排盘 JS 引擎挪入 WebView 进程同构执行（省一个运行时，需评估 Node API 差异）
3. **本地存储**：单机模式 MySQL → SQLite（SQLAlchemy 方言切换，需排查 JSON 列等 MySQL 特有用法）；数据库文件入 App 私有目录
4. **模式 C 实现**：APK 切到客户端模式时，建议**内嵌后端休眠**，壳直接作为 WebView 指向用户填写的服务器 URL（登录/数据/计费全走服务端，行为与浏览器完全一致）；此设计下「胖」只体现在单机模式
5. 模式切换 UI：首启动引导「单机 / 连接服务器」二选一；设置中可切换；绑定信息（URL/账号密码/Key）加密存储（Android Keystore）
6. 包体评估与素材分级、双运行时生命周期/端口冲突/省电、离线 LLM 不可用时的优雅降级

**双模式的本质收益**：APK 是同一个壳，S 模式 = 内嵌服务器+无账号+本地 Key/存储；C 模式 = 远程服务器+有账号+服务端 Key/存储。前端只需感知一个「能力提供方」配置（local/remote base URL + 认证态），业务页面零分叉——这是保持「三形态功能同源」的架构支点。

## 七、验收原则（远期）

1. 三形态（Web/APK-S/APK-C）同源构建：同一业务功能行为一致，确定性排盘结果一致，LLM 质量不因形态降级（仅 Key 来源不同）
2. 模式 S：无 Key 时确定性功能全可用、LLM 功能明确引导；配置 Key 且联网后 LLM 全通；抓包零官方外联
3. 模式 C：正确绑定自部署服务后，体验与浏览器访问该服务一致；可解绑回单机
4. Web 自部署：用户侧无 API 填写入口，Key 仅运维后台可改；自部署文档可让第三方按 README 跑通
5. 模式 S 无任何余额/登录/分享入口；模式 C 这些能力由服务器策略决定
6. 开源仓库中官方专属能力（金数据商户号等）不硬编码、可配置剥离
7. 三形态功能清单有统一台账，新功能默认三端同源，形态专属项显式标注

### 9.2 依赖 C 扩展风险矩阵（对照 pyproject + 全量 import 扫描）

| 包 | 形态 | 风险 | 候选替代 |
|---|---|---|---|
| pydantic-core（pydantic v2） | Rust/pyo3 | 🔴 最高（Chaquopy 是否有 wheel ⏳） | pydantic v1（纯 Python）或纯 Pydantic 模型 |
| cryptography（python-jose extra） | Rust | ⚠️ 高（HS256 理论可脱离） | PyJWT / joserfc（纯 Python） |
| pillow（验证码） | C | ⚠️ 中（官网列支持 ✅） | SVG/纯 Python 生成 |
| greenlet（SQLAlchemy asyncio 可选） | C | ⚠️ 低-中（本仓同步 Session，缺失大概率不碍事） | 无 |
| bcrypt / passlib / apscheduler / alembic / uvicorn[standard] extra | C / 冗余 | ✅ 运行时不 import，可整体退役 | 无（打包用纯 uvicorn） |

### 9.3 单机内嵌要点

- **双运行时是核心**：八字/神煞/大运 = Python 侧 lunar-python（纯 Python ✅）；紫微/占星/七政/奇门/六爻/塔罗等 14+ 法全在 Node 内核 → Android 无 `node` 命令，subprocess 两条路都死；出路 = nodejs-mobile 进程内 libnode（ESM + createRequire 混合加载需真机验证）或逐步移植。
- **环境/路径适配**：`MINGLI_JWT_SECRET` 必填（单机需内置随机生成）；`frontend_path = ../frontend/public`、三库 `data/*.db`、`.env` 都是 cwd 相对（🔴 改 app 私有绝对路径注入）；admin 有写 `.env` 的端点（单机版需改 UI 自填 Key）。
- **LLM key**：模式 S 用户自填，存 app 私有目录（可被 root 提取，接受即不加固）。

### 9.4 首启动体验（§八 剩余待拍板 · 决策包）

- **默认推荐项（Agent 建议）**：**单机模式 S**。理由：APK 核心价值 = 不开服务器、数据在本地、零依赖，对绝大多数安装者是最低门槛；模式 C 需要另有一台自部署服务（按拍板仅部署者本人使用），是少数人群。支持「跳过 → 默认 S，设置中可改」。
- **文案草案（待拍板）**：
  - 标题：「命理 · 本机版」
  - 副题：「选择运行方式，可随时在设置中更改」
  - 选项 S（推荐）：单机模式 ——「无需服务器，数据保存在本机；填入你的 AI 接口即可使用全部功能」
  - 选项 C：连接我的服务器 ——「绑定你自己部署的「命理」服务，账号与数据都在你的服务器上」
  - 底部说明：「本应用不会自动联网；联网仅用于你配置的 AI 接口或服务器」
- **后果说明**：默认 S 会让首次体验最快（无需先部署服务器）；若默认 C 则大部分用户会卡在「还没有服务器」上。
