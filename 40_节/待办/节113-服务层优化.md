## 方向清单（按「收益 / 风险」排序）

### ⭐ 1. Caddy 直服静态（收益最大、风险低）
- **依据**：Python 扛了约 **79%** 的请求，且全是静态文件（js/css/art/data/vendor）
- **做法**：`Caddyfile` 对 `/js/ /css/ /art/ /data/ /vendor/ /tarot/ /lenormand/` 用 `file_server`；需把 `frontend/public` 只读挂载进 caddy 容器（当前 Caddy 是独立容器，看不到 web 容器内的文件）
- **验收**：静态请求不再出现在 web 容器日志；静态响应直接来自 Caddy（可用响应头 `server: Caddy` 区分）
- **改前基线**：静态 60 : API 16

### ⭐ 2. 静态资源加 `Cache-Control`（最便宜）
- **依据**：实测**无 `Cache-Control`** → 每次访问回源验证
- **做法**：在 Caddy（或应用层）加 `Cache-Control`；资源文件名带内容 hash 后可上 `immutable`（当前文件名无 hash，故先用 `max-age` + ETag 复验）
- **验收**：`curl -sI` 出现 `cache-control: max-age=...`
- **改前基线**：无该头

### ⭐ 3. Dockerfile 层序调整（同时消除"再次锁死"风险）
- **依据**：`COPY backend/` 在依赖安装之前 → **任何后端改动都让依赖层缓存失效 → 全量重装**（这正是 2026-09-11 那次 2核1G 构建锁死的根源）
- **做法**：先 `COPY pyproject.toml` / `package.json` → 装依赖（pip/npm）→ 再 `COPY` 源码
- **验收**：改一个后端文件后重新构建，依赖安装层**命中缓存**（构建时间显著下降）
- **改前基线**：后端一改即全量重装（无缓存）

### 4. 首屏按域懒加载视图（收益中等，需权衡）
- **依据**：首屏加载 **14 个 js/css、316KB（gzip）**，含用户未必进入的域（占卜 91KB / 西式 56KB）
- **做法选项**：A 按域动态注入 `<script>`（进入该域才加载其 `views-*.js`）；B 维持现状（接受首屏体积）
- **风险 / 代价**：当前是**全局作用域 + 顺序加载**架构，动态加载需引入加载态与顺序保证；与节110「按职责拆」目标不冲突，但增加复杂度
- **验收**：首屏请求数 / 字节数下降，且各域进入后功能一致

## 结构反思（破竹 §8）
- 哪里难：静态资源**既被打进镜像（79.5MB）又由 Python 逐请求服务**——"位置"与"服务方式"耦合在一起
- 结构上怎么改：第 1 项把服务方式拆成独立接缝（Caddy 直服），Python 只管 API
- 下次会怎样：新增静态资源目录时，只需在 Caddy 配置加一条，不必让 Python 参与
