# 节 135 · 正文数据统一管理与 i18n 基础设施

状态：🔵 进行中（阶段 A 已完成）｜ 强度：中改偏大 ｜ 日期：2026-09-12 → 待定

## 背景与缘起
节105（REQ-128 文案统一管理）已完成 UI 文案统一迁入 TC_COPY（阶段 0-4），实现界面标签"改一处全局生效"。

但正文类数据（卦辞、爻辞、签诗、塔罗牌义、MBTI 类型描述、行星名映射、格局名映射等）目前散落在各 views 文件的数据常量中，尚未统一管理。若要做国际化（i18n），这些正文数据必须先有统一的数据契约和加载机制，否则多语言版本的正文会散落在更多文件里，维护成本指数级上升。

## 目标
1. **统一管理**：所有面向用户的正文数据有单一权威数据源，改一处全局生效
2. **i18n 就绪**：数据结构天然支持多语言切换，加一门语言只需新增一个语言包文件
3. **按领域分治**：不同领域的正文数据（易经、塔罗、MBTI、占星等）各有独立模块，互不耦合
4. **懒加载**：正文数据量大，不与 UI 文案一起首屏加载，按需拉取

## 设计原则
1. **UI 与正文分离**：`UI_COPY`（`ui.*`）管界面标签，`CONTENT`（`content.*`）管正文内容，命名空间不混
2. **单一权威数据源**：同一条正文（如乾卦卦辞）只在一个地方定义，所有页面从那里取
3. **按领域分文件**：易经、塔罗、MBTI、观音灵签、占星等各管各的目录
4. **语言驱动加载**：数据 = 模块 + 语言，切换语言 = 切换数据文件
5. **向后兼容**：现有功能零回归，数据搬迁不改变展示逻辑

## 数据结构规范

### 命名空间
```
CONTENT.<领域>.<条目ID>.<字段>
```

### 各领域 key 规范
| 领域 | 模块名 | ID 格式 | 示例 |
|------|--------|---------|------|
| 易经卦爻辞 | `iChing` | `hex-01` ~ `hex-64` | `CONTENT.iChing['hex-01'].name` |
| 塔罗牌义 | `tarot` | `major-00` ~ `major-21` / `wands-1` / `cups-queen` 等 | `CONTENT.tarot['major-00'].name` |
| MBTI 类型 | `mbti` | `INTJ` / `ENFP` 等 16 型 | `CONTENT.mbti['INTJ'].strengths` |
| 观音灵签 | `guanYin` | `sign-001` ~ `sign-100` | `CONTENT.guanYin['sign-001'].poem` |
| 占星行星 | `astrology.planets` | `sun` / `moon` / `mercury` 等 | `CONTENT.astrology.planets.sun.keywords` |
| 占星宫位 | `astrology.houses` | `house-1` ~ `house-12` | `CONTENT.astrology.houses['house-1'].meaning` |
| 占星相位 | `astrology.aspects` | `conjunction` / `trine` 等 | `CONTENT.astrology.aspects.conjunction.meaning` |
| 格局（紫微/八字） | `patterns.<体系>` | 视体系定 | 待细化 |

## 语言切换机制
- 入口 `content/index.js` 维护当前语言状态
- `setLang(lang)` 触发：按需加载各模块目标语言版本 → 替换 CONTENT 对象 → 派发 `lang-change` 事件
- 各 view 监听 `lang-change` 事件刷新展示
- 默认语言 `zh`，中文数据首屏内联加载（保证零延迟），其他语言懒加载
