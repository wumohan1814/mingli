## 我的复述

## 期望形态（验收标准 · 用户可观察）
- 先出**数字**（改前）：admin 页面体积 / 加载、关键端点的响应时间与查询次数
- 据此判定：是否需要同款解耦（降检索成本）/ 是否需要端点优化
- 若做：admin.html 拆分后 <2000 行；页面行为一致（用户亲验）

## 覆盖声明（v0.21）
- 本节点**证明**：结构与规模事实已定位
- **未证明**：admin 性能是否真有问题（无取数；按 v0.15「性能的凭是数字」，不凭感觉定论）

## 现状坐标（Agent 用）
- `frontend/public/admin.html` = **2,444 行单文件**，多职责：报表（4 tab）/ 用户 / 余额调整 / Prompt 管理台 / 素材管理 / 错误报告 / Agent 运维通道 / 登录页
- `backend/app/admin/router.py` = 69KB、**30 个端点**
- **不在**节110（前端主入口解耦）与节111（系统优化）范围内
- **红线口径缺口**：`00_根/复用.md` §五只写「入口壳 `frontend/public/index.html` <2000 行」，**未覆盖 admin.html**（同类入口无约束）

## 复用判断
- 库内候选：无
- 结论：**复用节110 已建立的机制**——拆分规范（`00_根/复用.md` §六）+ 牵连表（`导航.md` §7）。同款解耦的路径已存在，**不需要新机制**（铁律 8）

## 方案选项
- **A（结构 · 同款解耦）**：admin.html 按 v0.18 判据拆为 `css/` + `js/`。代价：一次大改；效果：降改后台时的检索成本。**低优先级**（规模是 index.html 的 1/9、管理员低频、不在用户主路径）
- **B（性能 · 先取数）**：按 v0.15 排查四步，量 admin 关键端点（响应时间 / 查询次数 / 有无循环或 N+1）。代价：一次只读取数；效果：把"要不要优化"从感觉变成数字
- **建议顺序：B 先（便宜、可判定）→ 有痛点再 A**

## 禁碰清单
- 不改接口契约（method-result v2 / chart.json）；不碰用户端 `index.html` 既有结构（除非牵连）

## 冲突检查
- 与 `00_根/复用.md` §五**红线口径冲突**：红线按文件名硬编码（只写 index.html），同类入口 admin.html 不受约束 → 建议顺带把红线改为按**角色**表述（见下「结构反思」）

## 结构反思（破竹 §8）
- 哪里难：红线**按文件名写**（"入口壳 index.html <2000"），导致同类入口（admin.html）落在约束之外
- 结构上怎么改：红线改为按**角色**表述——"所有 HTML 入口壳 <2000 行；单 .js/.css <5000 行"
- 下次会怎样：新增入口自动受约束，不会因为"红线只点了某个文件名"而漏
