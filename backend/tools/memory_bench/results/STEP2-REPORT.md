## 4. 复测中发现并修掉的一个真实缺陷（R2-1 口径）

第一版 R2-1 实现是「短问**只取** LIKE 命中」，结果**出现 1 题回退**（`compare.py` 报 `A only=1`）。
逐题诊断（`q031`）：

| 项 | 内容 |
|---|---|
| 问题 | `性格`（short 档） |
| 期望事实 | `用户做决定的时候比较容易犹豫`（importance 0.9）／`用户喜欢独自思考问题`（0.7）——**两条的 tags 都含「性格」，但 content 里都没有「性格」二字** |
| 改前 | channel=`recency`，注入 **6** 条，**命中 1 条** |
| 改后（第一版） | channel=`like`，注入 **1** 条（LIKE 只命中 1 条 content 含「性格」的**噪声**），**命中 0 条** |

**根因**：LIKE 是**更窄**的通道，`k` 从 6 塌到 1 → 预算被压缩，反而丢掉了 recency 本来能命中的记忆。
**修法**：`RECALL_SHORT_QUERY_UNION=1`（默认）→ **LIKE 命中 ∪ recency 全集**，LIKE 命中加
`RECALL_KEYWORD_BONUS=0.35` 抬前，但**候选预算仍是完整 k 条**。

修复效果（同语料复测）：`short` 档 Recall **0.5714 → 0.6429**，`short` 平均注入 **5.2857 → 6.0**。

**关于验收④（各档注入条数是否一致）的精确结论**：`k` 减半已彻底移除，**人为削额消失**；
改后 short / medium / long 平均注入 = **6.0 / 5.8214 / 5.4643**。残余差异**不是人为限额**，而是
**那 4 道 BM25 命中的题各只匹配到 1 条事实**（候选数 < k，注入 1 条属合理行为——
宁少勿滥，好过拿无关记忆凑满名额）。最终对比 **`A only=0`**。

## 5. 延迟专项：`run.py` 报的 p50 +9.06ms 是**机器状态假象**（已证伪）

`compare.py` 显示 p50 10.374 → 19.437ms，触碰「不得显著恶化」。做了两步复测：

**第一步（发现混淆）**：同进程连续跑 6 组配置时，延迟随**执行顺序单调上升**：
```
R0_off 5.716 → R1_only 5.771 → R2_only 6.002 → R3_only 7.000 → R1R2 10.784 → ALL 11.552
```
→ 这是 **WAL / 页缓存累积**造成的，不是单项成本。**召回指标不受影响**（确定性：`R0_off` 每次都精确复现 0.3143）。

**第二步（交替 A/B，每轮独立进程，最终代码，repeat=5）**：

| 轮次 | `R0_off`（＝旧行为）p50 | `ALL` p50 | Δp50 | `R0_off` p95 | `ALL` p95 | Δp95 |
|---|---|---|---|---|---|---|
| 1 | 6.177 | 5.297 | **−0.880** | 7.983 | 6.679 | −1.304 |
| 2 | 5.009 | 5.637 | **+0.628** | 7.357 | 7.138 | −0.219 |
| 3 | 5.025 | 5.381 | **+0.356** | 7.080 | 7.443 | +0.363 |
| **均值** | | | **+0.035 ms** | | | **−0.387 ms** |

→ **Δp50 均值 +0.035ms（≈ +0.6%），在轮间噪声（±0.9ms）内；p95 无恶化。**
→ 反向证据同样有力：`R0_off` 在独立进程里量到过 **21.98ms**，而 `ALL` 量到过 **5.72ms** ——
**同一份旧代码路径也能量出 22ms**，说明那两次 `run.py` 的差异来自机器状态。

**结论**：**延迟与 SQL 无显著恶化**（SQL 3.8 → 3.943，+3.8%；峰值内存 +2.6%）。
**教训**：本基准的延迟必须用「交替 A/B + 每轮独立进程」测，不能只比两次 `run.py`。已写进 README §9。

## 6. ⚠️ 语料天花板：本次增益有多少是"真修好了"（必读）

用纯语料数学（不建库）算各通道的**理论上限**：

| 通道 | 理论上限 | 含义 |
|---|---|---|
| BM25 词项 OR | **3/70 = 4.3%** | 期望事实与问题有 ≥1 个共同 3-gram 的题 |
| LIKE（整句子串） | **1/70 = 1.4%** | 期望事实 content 含整句问题 |
| 该用户至少 1 条事实有共同 3-gram（OR 非空） | **4/70 = 5.7%** | 与实测 `bm25: 4` **完全吻合** → **证明 R1 实现正确，不是 bug** |
| **tags 匹配** | **26/70 = 37.1%** | 期望事实的某个 tag 出现在问题里 |

**根因**：本语料的 `expected_fact_ids` 是生成器**按主题自动标注**的，问题也按主题生成 →
**两者常常没有任何共同字面**（问「事业」，期望事实内容是「用户准备考公务员」）。
即这份语料测的是「**主题**检索」，不是「词面检索」。

**因此必须诚实区分**：
- **R1 的收益被语料卡在 4.3%**（+4 题），实现是对的、天花板是语料给的；
- **R2 的召回增益主要是"名额 3→6"**（`lift` 不显著）；
- **R3（tags）是本语料里唯一有真实信号的通道**（上限 37.1%），实测贡献 +7 题（显著、零回退），
  但只吃到了天花板的 **7/26 ≈ 27%** —— 因为 R3 目前只在候选集上**加分排序**，没有升级为**召回通道**。

**给下一步的建议（需用户裁决，本次未做）**：把 tags 从「打分加分项」升级为**独立召回通道**
（如 `tags_json LIKE '%词%'` 或 `entity_index` 式结构），有望显著吃到那 37.1% 的剩余空间；
且**仍不需向量、不需改 FTS DDL**。另：`tags` 在生产由 LLM 抽取（prompt 要求 2~5 个关键词），
本语料把「主题词」硬编码进 tags，**会高估 R3 在生产的收益**，须谨慎外推。
