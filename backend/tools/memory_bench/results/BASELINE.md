## 结论摘要（**这是当前实现的基线**，先看这个）

1. **BM25 通道一次都没有触发**：70 道题里 `bm25` 占 0.0%、`recency` 占 100.0%。结合 `_fts_quote()` 把整句包成 trigram 短语（`service.py` L293-295），BM25 实际要求「记忆原文包含用户原句的连续子串」，因此零候选 → 恒降级 recency。
2. **召回质量与随机抽取不可区分**：Recall@k=0.3143，而随机抽同样条数的下限是 0.2957，lift=+0.0186，95%CI [-0.0801, 0.1173]，**区间含 0，不能认为优于随机**。
3. **准确率极低**：注入条目中命中标注期望记忆的仅 8.8%，同主题的仅 9.3% —— 即约九成注入内容是无关噪声，却会占满 token 预算。
4. **失败被「静默降级」完全掩盖**：空召回 0 道（0%）——因为 recency 兜底永远能凑出条目，所以从外部看「记忆一直在注入」，只是与问题无关。
5. **短问反而拿到双倍名额**：短问（≤2 字）平均注入 6.0 条，中等/长问仅 3.0 / 3.0 条 —— 因为 ≥3 字才走 BM25，而 BM25 零命中时 `k` 被减半（`service.py` L381-384）。

## 8. 指标口径（避免误读）

- **Recall@k**：期望记忆集合与「实际注入的记忆 id 集合」有交集即算命中（`k` 未显式传入，用生产默认；注意 BM25 零命中会降级 recency 且 `k` 减半，故各分档的**平均注入条数不同**，跨档比较请看该列）。
- **准确率（严格）**：注入条目里属于「该题标注期望记忆」的比例 —— 只认标注，对 recency 通道必然偏低（它按重要度×新鲜度取，与问题无关）。
- **准确率（按主题）**：注入条目里与问题同主题的比例 —— 更宽容，反映「至少没跑题」。
- **随机下限**：从该用户全部活跃事实里随机抽「同样条数」至少命中 1 条期望记忆的概率（超几何）。**若实测 Recall 与它持平，说明召回通道没起作用。**
- 延迟只含 `recall_memories()` 自身（不含网络/LLM）；SQL 条数只统计 analytics 引擎（埋点写 ops 库不计入）。

> 结论性判断请见仓库 `40_节/待办/节118-记忆层召回可用性修复.md` 与 README；本文件只负责给数字。
