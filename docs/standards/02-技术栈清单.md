### 1.3 Phase2 迁移路线（规划中）

当单文件架构触达维护瓶颈（预估 30000+ 行代码或 5+ 前端协作人员）时，启动向工程化架构的迁移：

| 阶段 | 内容 | 触发条件 |
|---|---|---|
| 阶段 1 | 引入 Zustand 轻量状态管理，收敛全局状态 | 当前：15+ 处 localStorage 读写、状态不一致 Bug 增加 |
| 阶段 2 | 组件抽离为独立 JS 文件（多 script 标签加载） | 单文件超过 25000 行 |
| 阶段 3 | 迁移到 Vite + TypeScript 工程化体系 | 前端团队 ≥3 人，或需要单元测试 / E2E 测试体系 |

## 8. 胖 APK（单机模式）

> 第三种交付形态（另两种见 `docs/standards/08-运行形态与版本契约.md`）：**胖 APK · 单机模式** —— APK 内含
> Python 后端 + 全部前端与素材 + 排盘内核，**数据保存在设备本地**，LLM key 由安装者自填；
> 运行形态由 `MINGLI_RUNTIME_MODE=apk-local` 表达（默认 `web` = 现状）。三形态**共用同一份业务代码**。
> 本节与 §7 的 T11–T14 为 **2026-09-22 补入**（此前规范里完全没有 APK 板块）。

### 8.2 排盘内核：为什么不用 Node

| 项 | 结论 |
|---|---|
| 结论 | **APK 内不引入 Node 运行时**；排盘 JS 打成单文件 bundle，跑在 **App 自带 WebView（V8）** 里，Python 经 Java 桥调用 |
| 为什么不能用真 Node | 社区 nodejs-mobile 仅存 prebuilt v18.20.4，且实测 **`libnode.so` 不符 16KB 页对齐**；修复只进了 main 从未发版（发版 PR 至今 open）；唯一维护者已公开退出 → **"等上游修"不可依赖**，自编 libnode 等于长期维护一条交叉编译链 |
| 打包做法 | esbuild 把 `paipan-core` + `iztro` + `lunar-typescript` + `astronomia`（**精确子路径**，避免把 8.9 MB 数据表全带进来）打成 **IIFE 单文件 2.53 MiB**；产物 `apk/app/src/main/assets/paipan/paipan-bundle.js`（**生成物，不入库**） |
| 桥接方式 | `PaipanBridge`（Kotlin，`object`）：`evaluateJavascript` 注入/取回，**大 bundle 分块注入、大结果分块取回**；超时与 JS 异常一律返回 `{"error": …}` JSON，**不抛异常给 Python** |
| 与 Web 侧一致性 | bundle 的 8/8 稳定摘要与 Web 侧 `server.mjs`（`TZ=Asia/Shanghai`）**逐字节一致**；时区由宿主显式注入（不依赖设备时区） |

### 8.3 当前能力边界（POC-0，**未完成项，勿当成已具备**）

- 工程内 `pip{}` 是**空的**：APK 内跑的是**只依赖标准库**的自举服务 `apk/pysrc/apk_server.py`
  （`127.0.0.1:8765`，含 `/api/health` 与 `/api/paipan/*` → 透传到 JS 桥），**不是 FastAPI 后端**。
- 因此 **POC-0 内：LLM 功能不可用、Node 系方法（紫微 / 六爻 / 占星 / 塔罗等）不可用**；
  后续阶段按 §7 的 T11–T14 推进（先解决 pydantic-core 自建 wheel，再装 fastapi）。
- 真机验收（装包后能否启动、WebView 是否执行未 attach 界面的 JS、桥接是否通）**本机无法验证**，
  属真机待验项。
