# 08 · 运行形态与版本契约

> 生效日期：2026-09-22
> 对应代码：`backend/app/runtime.py`（能力清单单一事实源）、`backend/app/version.py`（版本单一来源）、`backend/app/api/runtime.py`（`GET /api/runtime`）、`frontend/public/data/runtime.js`（前端入口 `ML_RUNTIME`）
> 状态：✅ 已定（地基已落地；**兼容拒绝逻辑与前端条件化渲染尚未实现**，见 §6）
> 变更说明：本文件补两个地基 —— ① **同源构建的渠道开关**（一份代码支撑 web / APK 三形态）② **版本契约**（服务器端与 APK 端各自独立更新时，能判定彼此是否兼容）。

---

## 1. 为什么需要这两样

用户 2026-09-22 拍板：**不做双端自动同步更新机制**，服务器端与 APK 端今后**各自独立更新**（要更新哪一端由用户单独下令）。

这带来两个必须回答的问题：

| 问题 | 没有地基时的后果 | 本文件给的答案 |
|---|---|---|
| 一份代码怎么同时服务两种形态？ | 分叉成两份代码，功能各改各的，很快就「同源」失效 | §2 **渠道开关 + 能力清单**（唯一事实源） |
| 「这个 APK 壳配这个服务器」行不行？ | 只能靠人记，装上去才发现不兼容 | §3 **版本契约 + 兼容矩阵** |

**纪律（一句话）**：**能力差异只允许登记在本文件 §2 的矩阵里**；形态判断只允许走
`app/runtime.py` 的 `capabilities()` 与前端 `ML_RUNTIME.has()`。

## 2. 渠道开关（同源构建）

### 2.1 三种形态

配置项：`MINGLI_RUNTIME_MODE`（`backend/app/config.py`），**默认 `web`**。

| 形态 | 是什么 | 数据在哪 | LLM key 从哪来 |
|---|---|---|---|
| **`web`**（默认，= 现状） | 自部署/托管的 Web 服务（浏览器访问） | 服务器 SQLite | 服务端运维配置（用户侧无自填入口） |
| **`apk-local`** | APK 单机版（内嵌后端 + 引擎随包） | 设备本地 | **安装者在应用内自填** |
| **`apk-client`** | APK 壳指向用户自部署的服务器 | 服务器 | 服务器配置 |

> ⚠️ **非法值一律按 `web` 兜底**（配置写错时宁可退回老行为，也不要把服务锁成单机形态）。

### 2.2 能力矩阵（唯一事实源 = `capabilities()`）

| 能力键 | web | apk-local | apk-client | 说明 |
|---|---|---|---|---|
| `auth` | ✅ | ❌ | ✅ | 账号体系（注册/登录/JWT）。单机版单用户直用，无登录态 |
| `credits` | ✅ | ❌ | ✅ | 积分与逐法扣费（红线⑤口径）。单机版整条摘除，深度解读改「用我的 API」 |
| `share` | ✅ | ❌ | ✅ | 档案/结果分享链接。单机版无服务器可承接链接 |
| `admin` | ✅ | ✅ | ❌ | 管理后台。单机版「本机设置」即管理面；客户端形态归服务器 |
| `prompt_mgmt` | ✅ | ✅ | ❌ | Prompt 查看/编辑/回滚。web 走后台热生效，单机改本机随包那份 |
| `asset_mgmt` | ✅ | ✅ | ❌ | 素材替换。web 后台上传，单机本地替换 |
| `byo_llm_key` | ❌ | ✅ | ❌ | **用户自填 LLM key**。只有单机形态有；web 的 key 是运维配置 |
| `events_report` | ✅ | ❌ | ✅ | 服务端埋点上报。单机版无上报（最多本地日志） |
| `paipan_local` | ❌ | ✅ | ❌ | 排盘在内嵌 JS 内核里跑（web/客户端均由服务器排盘） |

**读取端（两个，同一张表）**：
- 后端：`from app.runtime import capabilities` → 业务代码按能力分支；
- 前端：`ML_RUNTIME.has('credits')` → 渲染决策。**未登记的能力键一律返回 `false`**（防未登记功能被误判可用）。

**`apk-client` 的一个易错点**：该形态下前端读到的是**服务器**返回的 `/api/runtime`
（`mode=web`），本地内嵌后端休眠、不对外应答；矩阵里 `apk-client` 那列描述的是
**壳自身承担的职责面**（壳侧渲染决策），不是取代服务器的答案。

### 2.3 新增功能怎么做

1. **默认双端同源**：新功能默认三种形态都有，不需要登记；
2. **形态专属项**才登记：在 `capabilities()` 加键 + 一行注释（哪个形态开/关、为什么），
   并同步本文件 §2.2 矩阵与 `WEB_FULL` 兜底表（`frontend/public/data/runtime.js`）；
3. **禁止**在业务代码里另写 `if mode == '...'` 散判断（那正是本文件要消灭的东西）。

## 3. 版本契约

### 3.1 单一版本来源

`backend/app/version.py`（**全仓唯一来源**）：

| 常量 | 含义 | 现状 |
|---|---|---|
| `APP_VERSION` | 服务器端发布版本；与 `backend/pyproject.toml` 的 `project.version` 同值 | `0.1.0` |
| `API_VERSION` | **接口契约版本**，形如 `MAJOR.MINOR` | `1.0` |

不变量由测试看住（`backend/tests/unit/test_runtime_contract.py`）：`APP_VERSION` 必须等于
`pyproject.toml` 版本、`API_VERSION` 必须是 `MAJOR.MINOR`、FastAPI 的 OpenAPI 版本不得漂。

### 3.2 什么时候必须 bump

| 变更 | 动哪个 | 判据 |
|---|---|---|
| 新增端点 / 新增响应字段 / 新增可选参数 | `API_VERSION` 的 **MINOR +1** | 老客户端不做任何改动仍能正常工作 |
| 删除字段 / 改字段语义 / 改响应形状 / 改错误码含义 / 改鉴权要求 | `API_VERSION` 的 **MAJOR +1** | 老客户端**必须**改才能工作 |
| 仅内部重构、无接口可见变化 | 都不动 | 前端/壳无感知 |
| 发布一个新 APK 包 | 壳的 `versionCode +1`、`versionName` 随 `APP_VERSION` 口径 | 见 §4 |

### 3.3 兼容矩阵（判定规则）

- 每个 APK 壳**声明自己要求的最低 `api_version`**（构建期写入，运行期随 `/api/runtime` 对比）；
- 服务器返回当前 `api_version`；**壳的 `MAJOR` 与服务器 `MAJOR` 不同 = 不兼容**；
  壳要求的最低 `MINOR` ≤ 服务器 `MINOR` = 兼容（服务器新 MINOR 对老壳安全）；
- 服务器**可以拒绝过旧的壳**（返回明确错误提示升级）。

⚠️ **本版未实现拒绝逻辑** —— §3.3 只定规则。实现前，兼容问题只能靠人工比对版本号。

## 4. APK 侧对接点（约定，未实现）

APK 必须：

1. 在自己的本地服务上暴露**同样的 `GET /api/runtime`**（`mode = "apk-local"`，
   能力清单取自同一张表），使前端代码**零分叉**；
2. 把自己的 `versionCode` / `versionName` 映射到 `app_version`（口径与 `APP_VERSION` 一致）；
3. 在请求头带客户端标识 `X-Mingli-Client: apk/<versionCode>`，便于服务器记录与拒绝过旧壳。

**以上三条本版均只约定、未实现**（APK 工程尚在 POC 阶段）。

## 5. 更新节奏声明（用户已拍板）

- **不做双端自动同步**：服务器端与 APK 端各自独立更新，**推送代码不会改变已安装的 APK**
  （胖 APK 把前端/后端/prompt/素材/引擎全打进包，装上的那一刻即快照）；
- 服务器端更新 = `git pull` + `docker compose up -d --build`（现状，手动）；
- APK 端更新 = 重新出包 + 用户安装（**必须先做本地库版本化迁移**，否则新版装上去老档案打不开；
  迁移落点在 `backend/app/database.py` 的 `ensure_schema()`，版本化改造属后续节）；
- 因此**每一端都必须能独立判定对端版本是否兼容** —— 这正是 §3 存在的理由。

## 6. 本版已实现 / 未实现（诚实清单）

**已实现（有测试与真实响应为证）**：
- `MINGLI_RUNTIME_MODE` 开关（默认 `web`，非法值按 web 兜底）；
- `capabilities()` 能力单一事实源 + 三形态矩阵；
- `GET /api/runtime`（无鉴权，信封 `{code, message, data}`，含 `mode/capabilities/api_version/app_version`）；
- 前端 `ML_RUNTIME` 入口（`has()/ready/onReady` + `runtime-ready` 事件；**取不到接口按 web 全能力兜底**）；
- 版本单一来源与三条不变量测试。

**未实现（明确登记，别误以为已有）**：
- 服务器对过旧壳的**拒绝逻辑**（§3.3 只定规则）；
- `X-Mingli-Client` 请求头（§4）；
- **前端 UI 条件化渲染**（本版只建入口与读取，页面尚未按 `has()` 分支）；
- APK 侧本地 `/api/runtime` 与 `versionCode → app_version` 映射（APK 尚在 POC）；
- `backend/app/main.py` 的 `FastAPI(version=...)` 仍是字面量（与 `APP_VERSION` 同值，由测试看住不许漂）。
