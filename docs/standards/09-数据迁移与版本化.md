# 09 · 数据迁移与版本化

> 生效日期：2026-09-22
> 对应代码：`backend/app/migrations/`（`registry.py` 登记表 + `runner.py` 执行器）+ `backend/app/database.py::ensure_schema()` 末尾的调用
> 状态：✅ 已定（v1 基线 + v2 记账表已落地，7 例单测全绿）
> 何时必须读：**改任何表结构 / 加列 / 加表 / 建索引之前**；发布服务器端或 APK 端之前

## 1. 为什么要有这条链（不是「顺手加的规范」）

本项目有三种形态：**Web 自部署（服务器 SQLite 三库）**、**APK 单机（同一套三库，落在设备私有目录）**、
**APK 客户端模式**。已拍板：**不做双端自动同步**，将来由人**分别**下令更新服务器端或 APK 端。

这条决策的直接后果是：**任一端更新后，另一端的老数据必须还能被正确打开**。而 SQLite 没有服务端 DDL
版本协商，旧程序打开新结构只会「读得到一部分、悄悄算错」——所以版本化迁移是硬需求，不是锦上添花。

三条硬约束由此而来：
1. 更新后老数据必须能打开（**升级路径**）；
2. 新版写过的库被老版打开必须 **fail loud**（**不得静默损坏**）；
3. 迁移本身失败必须整体回滚并可见（**不得半升**）。

## 2. 版本号语义

| 版本 | 含义 | 谁写 |
|---|---|---|
| **v1 = 基线** | 「`create_all` + `ensure_schema()` 里那批历史遗留补列/种子跑完」的现状。**既有库（无版本记录）由 v1 盖章**，不碰任何既有结构 | `registry._v1_baseline_stamp` |
| **v2 …** | 真实结构变更（加表/加列/加索引/回填）。**新增变更一律走这里** | 每次新增一个步骤 |
| **库版本 > 代码版本** | 库由更新版本的程序写过 | **拒绝打开**（`MigrationError`，见 §4） |

版本号存在每库自己的 `schema_meta` 表（`k='version'`，字符串存整数）。

## 3. 两张载体表

| 表 | 作用 | 谁建 |
|---|---|---|
| `schema_meta` | 键值事实：`version` / `app` / `baseline_stamped_at` | 执行器（机制自身，**不是**编号步骤） |
| `schema_migrations` | 逐步骤记账：`app, version, name, summary, applied_at`（主键 `app+version`） | **v2 步骤**（真实新建；v1 阶段还没有这张表，故记账是「有表才记」） |

> 为什么要两张：`schema_meta.version` 只回答「现在是多少」，`schema_migrations` 回答「哪一步、什么时候、跑过没有」——
> APK 端老库排障时要能逐步骤对账。

## 4. 执行时机与 fail loud 的两种情形

**时机**：`app.database.ensure_schema()` 的**最后**（即 `create_all` → 历史补列/种子 → 迁移链），
三库各跑一次：`analytics` / `feedback` / `ops`。基线版本的定义就是「历史补列跑完的现状」，
所以**必须在它们之后**，顺序不能反。

| 情形 | 行为 | 为什么 |
|---|---|---|
| 某步骤抛错 | **整库回滚**（一库一事务，SQLite 的 DDL 也参与事务）+ 抛 `MigrationError` → **启动失败** | 半升的结构比不升更危险；宁可起不来 |
| 库版本 > 代码已知版本 | **拒绝打开**该库 + 抛 `MigrationError`（错误里带库版本/代码版本/路径） | 旧程序读新结构 = 静默算错，必须拦住 |

其余情形都是安静的：已最新 → `applied=[]`、零写入（幂等）；既有库 → 盖章（`baseline_stamped=True`）。

并发：执行器用 `BEGIN IMMEDIATE` + `busy_timeout=10s` 取写锁，多 worker 启动时**串行**；
超时则 `MigrationError`（fail loud，不会出现两个进程交错写结构）。

## 5. 加一步迁移：操作清单（照抄就能加）

1. **判断是不是结构变更**：是 → 走这里；只是「历史补列」→ 停，别再往 `ensure_schema()` 加（§7）。
2. **在 `backend/app/migrations/registry.py` 写步骤函数** `def _vN_xxx(conn, app): ...`：
   - 只用标准库 `sqlite3`（**不许 import SQLAlchemy / 应用模型**，执行器要能脱离应用跑）；
   - **幂等写**：`CREATE TABLE/TABLE IF NOT EXISTS`、`INSERT OR IGNORE`、加列前先 `PRAGMA table_info` 探测；
   - 不依赖外键强制（执行器**不设** `PRAGMA foreign_keys=ON`）。
3. **append 一条 `Migration(version=N, name="...", summary="...", fn=_vN_xxx)`**：版本号 = 当前 `SCHEMA_VERSION + 1`，**只能 append**。
4. **不改已有步骤**（改了 = 不同库跑出不同结构，无法复现）。
5. **补测试**：在 `backend/tests/unit/test_migrations.py` 加该步骤的「升级前 → 升级后」断言（含数据不丢）。
6. **跑门禁**：`python -m pytest tests/unit/test_migrations.py -q`（全量由收尾统一跑）。
7. **登记影响面**：本表结构变了 → 同步 `docs/standards/03-接口与数据字典.md`；
   触发「新增/改契约」→ 记 `99_状态/决策.md`（破竹 §6）。
8. **想清楚 APK 端**：老 APK 的本地库升级到这一版会发生什么？步骤幂等 + 不改既有表结构 = 安全；
   若必须重建表（SQLite 12 步法），要为老库数据写显式回填（§6 第 3 条）。

## 6. 纪律（违反即返工）

1. **只增不改**：已发布的步骤内容不许动；要改结构就加新步骤。
2. **必带测试**：没有「升级前/后」断言的步骤不许合入。
3. **必须考虑 APK 端老库**：设备上的库可能停在任意旧版本，步骤必须能从**任意旧版本**跑到最新（链式，不是跳版本）。
4. **状态表也是数据**：`schema_meta` / `schema_migrations` 不要当缓存清、不要手改。
5. **不许把迁移写进业务代码路径**：迁移只在启动时跑一次（`ensure_schema()`），运行中不迁移。
6. **不许「跳过继续」**：任何调用方**都不得**吞掉 `MigrationError` 让服务带病启动（刻意降级要在决策里写明并留痕）。

## 7. 与 `ensure_schema()` 的分界线（重要）

| | `ensure_schema()` | `app/migrations/` |
|---|---|---|
| 定位 | **历史遗留补列/种子**（jobs/cases/conversations/… 那批 ALTER + `system_configs` 种子） | **版本化结构变更** |
| 状态 | **自 2026-09-22 冻结**：不改、不删（避免动到线上既有行为），只留原地 | 唯一入口，**新增一律走这里** |
| 版本感 | 无（幂等就完事） | 有（v1 基线起逐步骤记账） |

> 一句话：**旧的那条线不再长，新的线从 v2 开始长。**

## 8. 三形态一致性

| 形态 | 库位置 | 迁移链 |
|---|---|---|
| Web 自部署 | 服务器 `/app/data/*.db`（挂载卷） | 同一执行器（容器启动即跑） |
| APK 单机 | 设备**应用私有目录**（POC 阶段待接：当前代码用 cwd 相对 `data/*.db`，需改绝对路径注入） | **同一执行器**（同一套代码） |
| APK 客户端 | 数据在服务器 | 同 Web |

因此「本机版档案打不开」不再是空白项：**只要结构变更走这条链，APK 端老库会被升上来**；
先决条件是 APK 端要能定位到自己的库文件（POC 阶段待办，不属本链范围）。

## 9. 排障速查

```bash
# 看某库版本与逐步骤记账
sqlite3 data/mingli_analytics.db "SELECT * FROM schema_meta; SELECT * FROM schema_migrations ORDER BY version;"

# 报「库版本高于本代码已知版本」怎么办
#  → 这是保护，不是 bug：先升级程序；确需用旧程序打开，先备份库，别硬改 schema_meta
 
# 报「迁移失败并已回滚」
#  → 库未被改动（含失败步骤的 DDL 也已回滚）；看错误里的 vN + 步骤名，修步骤后重跑启动即可
```

## 10. 已知边界（没做，也不假装做了）

1. **不做降级**：库比代码新时只拒绝，不提供「降级回旧结构」（降级必丢数据语义）。
2. **不做跨库事务**：三库各自一事务；跨库一致性靠「迁移步骤本身不跨库」这条纪律。
3. **不做在线迁移**：迁移只在启动时跑，运行中的服务不会被热迁。
4. **并发假设**：靠 SQLite 写锁串行；不假设存在「多进程同时迁移」之外的分布式锁。
5. **FTS5 索引与同步触发器不进本链**：`agent_memories_fts` + 三个触发器由
   `ensure_agent_memory_fts()` 单独幂等创建，且**失败只降级不阻断启动**（既有契约）。
   把它搬进本链会让「FTS5 不可用」从降级变成**启动失败**（APK 端 SQLite 是否带 FTS5 尚未实测），
   属行为变更 —— 故**刻意排除**；将来要纳入，必须同时决定是否改成 fail loud，并单独留痕。
