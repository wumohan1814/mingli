# ADR-0004: 阶段 4 路由决策独立为 `routing` 模块，配置化

## Status

Accepted（2026-09-05）

## Context

- 技术框架方案 v2.3 §4.1 步骤 5 写「按权重 + 路由（主法全跑、辅法按主问高相关子问题跑）」，
  但 **9 类模块清单中没有路由模块**，全文也未提及 mingli 的 `references/routing.md` 与
  `路由决策.md` 产物——即"谁来决定这次跑哪几法"没有归属。
- 若路由由 LLM 阅读提示词决定，则**每次预测都多一次 LLM 调用**，且结果不确定（相同主问可能
  选出不同方法），与「排盘与路由都应确定性」的原则冲突。

## Options

| 方案 | 描述 | 优点 | 代价 |
|---|---|---|---|
| A | 网关内联路由表 | 改动最小 | 网关承担领域逻辑，路由表难以被其它模块复用 |
| **B** | **独立 `routing` 模块 + 配置化路由表** | 职责清晰、确定性、零 LLM、可测试 | 多一个模块 |
| C | 沿用 mingli `routing.md` 由 LLM 解读 | 复用现成文档 | 每次预测多一次 LLM 调用且结果不确定 |

## Decision

选择 **B**。

1. 新增 `backend/app/routing/` 模块，职责：**主问 → 主 / 辅方法集合** 的决策。
2. 路由表**配置化**（仓库内的结构化配置，非提示词），决策为纯查表 + 权重排序，**零 LLM 调用**。
3. 输入：`主问领域` + `校准权重`（来自 `score.py`）+ `degraded_methods`（降级法需剔除）+ 用户点名的方法。
4. 输出：**路由决策记录**（选用的方法清单、主 / 辅角色与理由），落库留存，供阶段 5 推理链路与
   事后复盘使用。
5. 规则：主方法全跑；辅方法只跑与主问高相关的子问题；**被降级的方法不得进入路由结果**；
   用户点名的方法强制纳入。

| 主问 | 主方法 | 辅方法 |

## Consequences

### 变得更容易
- 路由确定性、可单测、可审计；相同输入必得相同方法集合。
- 省掉每次预测的一次 LLM 路由调用。
- 路由决策落库后，阶段 5 的「为何选这几法」有据可查。

### 变得更难
- 路由表成为**需维护的配置资产**：新增方法模块必须同步登记，否则永远不会被选中。
- 主问领域识别（用户自然语言 → 主问枚举）仍需一次轻量分类，**这不属路由模块职责**，
  由网关/建档阶段产出 `主问` 字段（可在建档表单中让用户直接选择主场景，进一步省掉分类调用）。

### 需要同步修改

- [x] `backend/app/routing/` 由「⚠️ 待决策」转为正式模块
- [x] `docs/standards/03-接口与数据字典.md`：新增路由决策记录的数据字典项
