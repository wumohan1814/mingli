# FE-001：前端采用免构建单文件架构

- 状态：✅ 已定（2026-09-10 校准）
- 决策人：前端负责人
- 生效日期：V0 MVP 启动
- 关联文档：`docs/standards/02-技术栈清单.md`

## 背景

太初作为 MVP 阶段的命理 H5 应用，面临以下约束：
1. **部署环境不确定**：可能部署在沙箱/轻量云等无 Node 构建链的环境
2. **团队规模小**：初期仅 1 名前端开发，无需复杂协作流程
3. **迭代速度优先**：MVP 阶段需求变化频繁，需要快速验证
4. **代码规模可控**：预计 V0 阶段前端代码量在 15000-25000 行

## 决策

采用**免构建单文件架构**：
- 所有前端代码（HTML / CSS / JSX）集中在单个 `frontend/public/index.html` 文件中
- React / ReactDOM 通过 CDN 加载生产构建的 UMD 版本
- JSX 由 Babel Standalone 在浏览器端实时转译
- 后端 FastAPI 直接静态托管 `frontend/public/` 目录

## 备选方案对比

| 方案 | 优点 | 缺点 |
|---|---|---|
| **免构建单文件**（选定） | 部署简单、零构建、便于沙箱迁移、单文件心智模型清晰 | 无类型检查、无代码分割、调试难度随规模上升 |
| Vite + TypeScript 工程化 | 类型安全、构建优化、生态完善、易扩展 | 需要构建链、部署复杂、MVP 阶段 overhead 高 |
| Next.js / Remix SSR | SEO 友好、性能优化内置 | 服务端渲染增加运维成本，与命理应用场景不匹配 |

## 风险与应对

| 风险 | 影响 | 应对措施 | 触发条件 |
|---|---|---|---|
| 单文件过大导致维护困难 | 代码可读性下降、Bug 增加 | 按模块分区组织代码 + 清晰注释 | 超过 25000 行 |
| 无类型检查导致运行时错误 | 接口联调出错率高 | 统一 `api()` 封装 + 严格契约文档 | Bug 率超过阈值 |
| 无法多人协作 | 并行开发受限 | 按功能模块分工 + Git 规范合并流程 | 前端 ≥2 人 |
| 首屏加载性能差 | 用户体验下降 | 关键 CSS 内联 + 非核心数据懒加载 | LCP > 3s |
| Babel runtime 转译性能开销 | 低端机首屏慢 | 生产环境仍使用 runtime 转译；待评估预编译方案 | 转译时间 > 500ms |

## Phase2 迁移路线

当满足以下任一条件时，启动向工程化架构的迁移评估：
1. 单文件代码量超过 30000 行
2. 前端团队 ≥3 人
3. 需要建立完整的测试体系（单元测试 + E2E）
4. 性能瓶颈明确且无法通过单文件优化解决

迁移步骤（详见 standards/02 §1.3）：
1. 引入 Zustand 收敛全局状态
2. 组件抽离为独立 JS 文件
3. 完整迁移到 Vite + TypeScript

## 后果

- **正面**：部署极简、迭代快速、运维成本低
- **负面**：工程化能力受限、类型安全缺失、规模化扩展成本高
- **中性**：技术债在可控范围内积累，待 MVP 验证后统一偿还

## 补充记录

### 2026-09-10：引入轻量状态管理（Zustand UMD）

- 背景：全局状态分散在 15+ 处 localStorage 读写，已出现状态同步 Bug（如 BUG-011 会话越权）
- 决策：引入 Zustand UMD 版本，统一管理用户会话、余额、皮肤、档案选择等全局状态
- 影响面：`frontend/public/index.html` 中 App 级状态管理逻辑
- 风险：低 —— Zustand 仅 1KB，UMD 版本通过 CDN 加载，不改变构建流程
