# ADR-0006: 归档以数据库为唯一事实源，Markdown 导出留 Phase2

## Status

Accepted（2026-09-05）

## Context

- mingli `SKILL.md` §7 用 `archive.py` 归档到 **Obsidian vault**，产出 `chart.md`、`04-校准记录.md`、
  `05-推理链路.md` 等 6 个会话 Markdown 文件。
- 技术框架方案 v2.3 改为**双库落盘**（用户分析库 + 跨用户质疑库），`GET /api/cases/{id}/archive`
  定位为"派生视图"，但**全篇未说明 `archive.py` 是废弃、替换还是保留**——归档形态存在空档。
- 产品规划 §7.2 强调「命理档案（生辰 + 历史对话）是第二阶段横向扩展的数据底座与差异化护城河」，
  因此归档不能只是"导出便利"，它承载资产属性。
- 前置决策：ADR-0001 已确定自研，Obsidian 相关的外部脚本不再引入。

## Options

| 方案 | 描述 | 优点 | 代价 |
|---|---|---|---|
| **A** | **DB 唯一事实源，导出留 Phase2** | 单一事实源，无双写一致性问题；结构化数据天然支撑横向扩展与 LTV | 人类可读性暂时依赖前端渲染 |
| B | DB + Markdown 双写（对齐 mingli） | 人类可读、可直接进知识库 | 双写一致性负担；归档失败是否回滚需取舍 |
| C | 以 Markdown / Obsidian 为主 | 与 mingli 一致 | 与多用户、查询、横向扩展需求冲突 |

## Decision

选择 **A**。

1. **用户分析库是命理档案的唯一事实源**：chart、各法 `method-result`、`validation`、
   校准记录、对话、报告全部结构化落库。
2. **不引入 Obsidian / `archive.py`**；`reference/mingli/` 中的归档脚本仅作参考。
3. `GET /api/cases/{id}/archive` 返回**结构化 JSON 档案**（含推理链路要素：路由决策、
   各法置信与校验告警、合并冲突说明、校准状态）。
4. Phase2 视需求再提供 Markdown / PDF 导出（**导出产物是派生，不是事实源**）。

## Consequences

### 变得更容易
- 单一事实源，消除双写一致性与"归档失败是否回滚"的取舍。
- 结构化档案直接支撑 Phase2 横向扩展（生肖 MBTI / 塔罗打通）、回访节点与 LTV 分析。
- 不依赖 Obsidian，部署环境更轻。

### 变得更难
- 失去 Markdown 的"人可直接打开阅读"便利性 → 前期排查靠前端页面或导出脚本。
- 「推理链路」需在 DB 中显式建模（路由决策表 / 校验告警字段 / 冲突说明字段），
  不能像 Markdown 那样自由书写。

### 需要同步修改

- [x] `docs/standards/03-接口与数据字典.md`：archive 返回体的要素清单
- [ ] 技术框架方案 §3.7 / §10：明确不引入 `archive.py`
- [ ] 数据字典：路由决策与冲突说明的落库字段（随 ADR-0004 一并设计）
