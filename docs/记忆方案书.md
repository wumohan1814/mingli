## 0. 摘要与硬性约束映射

本模块为「太初先生」Agent（REQ-076）提供**跨会话长期记忆**：把用户与先生的对话回合中透露的用户偏好、身份/背景、目标、持久性事实，在**不阻塞主对话接口**的前提下异步交给外部 LLM 抽取为结构化事实，落 SQLite 事实表并同步 FTS5 全文索引；用户在后续会话中提问时，按「BM25 相关度 + 时间衰减」召回若干条记忆，拼入发给模型的 system 上下文。

硬性约束 → 方案落点对照：

| REQ-077 硬性约束 | 本方案落点 |
| --- | --- |
| 服务器 2C1G | 全文检索用 SQLite FTS5（单进程内、毫秒级），内存/CPU 增量见 §3 估算 |
| 禁止新增后台进程 / 独立服务 / 向量数据库 / 自托管向量服务 | 全部逻辑在既有 FastAPI 进程内：worker 为 lifespan 注册的进程内 asyncio 协程（§2），无 daemon、无 MCP、无 go-server、无新 Node 子进程 |
| 完全舍弃向量化与 Embedding | 存储与检索仅：事实表（字段/时间/重要度）+ FTS5 BM25 全文索引，无任何 embedding 列/向量索引 |
| 单 SQLite 文件嵌入现有业务进程，零外部依赖 | 事实表/任务表落既有业务库 `data/taichu_analytics.db`（复用 Base + analytics_engine + 既有 WAL/busy_timeout/foreign_keys pragma，§1.1）；FTS5 为 Python 自带 sqlite3 内建（实测 Python 3.13.14 + SQLite 3.50.4 已编译 ENABLE_FTS5），零 pip 依赖 |
| 多用户隔离 | user_id 为全局隔离键，贯穿建表、任务、召回 SQL、管理接口四层（§4） |
| 事实抽取交给外部 LLM API 且异步执行，不得阻塞主对话接口 | 对话接口只做「落 agent_messages + 入队（<1ms）」，抽取 LLM 调用仅发生在进程内后台 worker 协程（§2） |
| 召回记忆拼入提示词 | 请求组装期把召回事实渲染为独立 system 段，位于 REQ-076 角色 prompt（master.md）之后（§5） |
| 参考 agent-memory-main | 借鉴点：事实元数据字段（importance / trust / access_count / last_accessed / source 溯源）、FTS5 同步触发器思路、bm25() 排序 + 1/(1+\|bm25\|) 归一、LLM 结构化抽取 schema + 规则启发式兜底。**不借鉴**：其多表因果链（entity_index/relations/evolution_log/audit_log）、双阈值遗忘分层、RRF 多路融合、sqlite-vec/向量 fallback、Go 服务/daemon/MCP/REST 网关等（2C1G 与「零向量」约束下无必要，见 §1.2 借鉴取舍说明） |

## 1. 表结构

### 1.1 落库位置与库文件

- 事实表与任务队列表**落在既有业务库 `data/taichu_analytics.db`**（`settings.db_path`），与 `users` / `cases` / `conversations` 同库同文件，`Base`（analytics_engine）注册，符合 REQ-077「单 SQLite 文件嵌入现有业务进程」与 REQ-078「新增表走 Base.metadata.create_all 幂等建表」口径。
- 理由：
  1. 事实表需要 `user_id → users.id` 的外键语义，SQLite 外键**跨库不可用**，同库才能保持引用完整性；
  2. REQ-078 已把 `agent_messages` 与 `agent_memories` 并列规划在本库（⑤ 紧随 ④）；
  3. 复用现有 WAL + `busy_timeout=10000` + `foreign_keys=ON` pragma（backend/app/database.py 三引擎 connect 事件），零新增连接配置。
- 记忆写入频率低（抽取 worker 串行、批量提交，§3.3），对既有业务写放大可控，不单开库文件。

### 1.2 agent_memories 事实表（核心表）

每条记录 = 一条结构化事实。字段设计借鉴 agent-memory-main `memories` 表（importance/trust/last_accessed/access_count/source 溯源/软删标记），按本项目**单用户隔离 + 去重刷新 + 无因果链**的 MVP 简化：

| 字段 | 类型 | 约束/默认 | 说明 |
| --- | --- | --- | --- |
| id | INTEGER | PK 自增（rowid 别名，FTS 同步用） | 主键 |
| user_id | INTEGER | NOT NULL，FK→users.id，索引 | **多用户隔离键**（§4），各用户记忆独立 |
| case_id | INTEGER | NULL（普通列，无 FK） | 可选归属档案（REQ-076 顶部选的「默认档案」）；仅作召回上下文标记，不建外键（删除档案不级联，沿用 PairReading 无 FK 先例） |
| content | TEXT | NOT NULL，≤500 字符（超出该条的抽取结果截断/丢弃） | 事实正文（中文自然语句，如「用户偏好绿茶」） |
| fact_type | VARCHAR(16) | NOT NULL 默认 `preference` | preference 偏好 / identity 身份背景 / goal 目标 / event 事件经历 / habit 习惯（抽取 LLM 给定枚举，非法值落 `general`） |
| importance | REAL | NOT NULL 默认 0.5，0~1 | 重要度（抽取 LLM 给出） |
| trust | REAL | NOT NULL 默认 0.7，0~1 | 可信度（规则抽取固定 0.75） |
| content_hash | CHAR(40) | NOT NULL，**UNIQUE(user_id, content_hash)** | 规范化文本 sha1（中文归一 + 空白归一），去重/刷新键（§2.6） |
| source_type | VARCHAR(16) | NOT NULL 默认 `agent_chat` | 来源（预留：`agent_chat`） |
| source_msg_id | INTEGER | NULL | 来源回合的消息 id（指向 REQ-076 的 agent_messages，**普通列不建 FK**——agent_messages 未建/建表顺序解耦，先例同 PairReading） |
| source_task_id | INTEGER | NULL | 写入该条事实的抽取任务 id（agent_memory_tasks.id，排查溯源用） |
| tags_json | TEXT | NULL | 抽取标签（JSON 数组文本，MVP 不用于检索，仅展示） |
| access_count | INTEGER | NOT NULL 默认 0 | 累计被召回次数 |
| last_recalled_at | DATETIME | NULL | 最近一次被召回时间（清理/新鲜度用） |
| created_at | DATETIME | NOT NULL 默认 now | 首次入库时间 |
| updated_at | DATETIME | NOT NULL 默认 now | 去重命中刷新（重要性取 max、时间戳更新）时更新 |
| deleted_at | DATETIME | NULL | 软删标记（用户删除/清理淘汰先软删，检索一律过滤；物理清除由维护任务执行） |

建表 DDL 草案（SQLite 语法；实际以 ORM 模型 + create_all 生成，字段对齐即可）：

```sql
CREATE TABLE IF NOT EXISTS agent_memories (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id         INTEGER NOT NULL REFERENCES users(id),
    case_id         INTEGER,
    content         TEXT NOT NULL CHECK (length(content) <= 500),
    fact_type       VARCHAR(16) NOT NULL DEFAULT 'preference',
    importance      REAL NOT NULL DEFAULT 0.5 CHECK (importance BETWEEN 0 AND 1),
    trust           REAL NOT NULL DEFAULT 0.7 CHECK (trust BETWEEN 0 AND 1),
    content_hash    CHAR(40) NOT NULL,
    source_type     VARCHAR(16) NOT NULL DEFAULT 'agent_chat',
    source_msg_id   INTEGER,
    source_task_id  INTEGER,
    tags_json       TEXT,
    access_count    INTEGER NOT NULL DEFAULT 0,
    last_recalled_at DATETIME,
    created_at      DATETIME NOT NULL,
    updated_at      DATETIME NOT NULL,
    deleted_at      DATETIME
);
CREATE UNIQUE INDEX IF NOT EXISTS ux_agent_memories_user_hash
    ON agent_memories(user_id, content_hash);
CREATE INDEX IF NOT EXISTS ix_agent_memories_user_created
    ON agent_memories(user_id, deleted_at, created_at DESC);
CREATE INDEX IF NOT EXISTS ix_agent_memories_user_type
    ON agent_memories(user_id, fact_type);
```

### 1.3 agent_memories_fts —— FTS5 全文索引（BM25）

- 采用 **FTS5 内容表（自持文本镜像）**，`rowid = agent_memories.id`，与事实表由数据库触发器自动同步（借鉴 agent-memory-main schema.sql 的 FTS5+触发器方案，但**不用其 external-content 形态**，改用自持内容，规避外部内容表对中文 tokenizer 的兼容问题）。
- **中文 tokenizer 选型（重要，已实测）**：FTS5 默认 unicode61 分词把连续中文视为一个 token，对中文查询基本无效（实测整句「用户喜欢喝茶偏好绿茶」被索引为单 token，查询「喝茶」无命中）。故采用内建 **trigram tokenizer**：实测对 ≥3 字子串查询可命中（`"偏好绿茶"` 命中、`"今年升"` 命中），2 字查询返回空集（不报错）——检索层须对短查询（<3 字符）做降级（§5.2 兜底）。trigram 由 SQLite ≥3.34 自带（本机 3.50.4，实测可用），零外部扩展。
- 注意：实测 trigram 表**不支持 FTS5 特殊 `'delete'` 命令**（SQL logic error），故触发器同步用普通 `DELETE FROM ... WHERE rowid=old.id`（实测可用）。

DDL 草案：

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS agent_memories_fts USING fts5(
    content,
    tokenize = 'trigram'
);

CREATE TRIGGER IF NOT EXISTS agent_memories_ai AFTER INSERT ON agent_memories BEGIN
    INSERT INTO agent_memories_fts(rowid, content) VALUES (new.id, new.content);
END;

CREATE TRIGGER IF NOT EXISTS agent_memories_ad AFTER DELETE ON agent_memories BEGIN
    DELETE FROM agent_memories_fts WHERE rowid = old.id;
END;

CREATE TRIGGER IF NOT EXISTS agent_memories_au AFTER UPDATE OF content ON agent_memories BEGIN
    DELETE FROM agent_memories_fts WHERE rowid = old.id;
    INSERT INTO agent_memories_fts(rowid, content) VALUES (new.id, new.content);
END;
```

> 去重刷新（§6.2）只 UPDATE 时间戳/importance（不动 content），不触发 FTS 触发器，无写放大。
> user_id 刻意**不进** FTS 列：多用户共享同一全文索引，隔离靠检索 SQL 中 `m.user_id = ?` 的 join 过滤（§4），配合单用户事实条数上限，候选集规模可控。

### 1.4 agent_memory_tasks —— 抽取任务队列表（调度持久化）

§2 的异步抽取需要跨重启的持久化队列（进程内内存队列在崩溃/重启即丢），故设任务队列表。**不做成独立消息系统/服务**，仅是业务库内一张普通表 + 进程内 worker 轮询认领：

| 字段 | 类型 | 约束/默认 | 说明 |
| --- | --- | --- | --- |
| id | INTEGER | PK 自增 | 任务 id |
| user_id | INTEGER | NOT NULL，FK→users.id，索引 | 被抽取记忆归属用户（隔离键，§4） |
| start_msg_id | INTEGER | NOT NULL | 抽取游标起点（该用户上次已抽取的最新消息 id，含自身为下一条） |
| end_msg_id | INTEGER | NOT NULL | 本轮要抽到的消息 id（= 最新回合 user 消息 id；同用户 pending 合并时前滚） |
| status | VARCHAR(16) | NOT NULL 默认 `pending` | pending / running / done / dead（状态机见 §2.3） |
| attempts | INTEGER | NOT NULL 默认 0 | 已尝试次数（≤ max_attempts=3） |
| next_retry_at | DATETIME | NULL | 指数退避后的最早可执行时间 |
| last_error | TEXT | NULL | 最近一次失败原因（截断 200 字符，日志/埋点用） |
| created_at | DATETIME | NOT NULL | 入队时间 |
| updated_at | DATETIME | NOT NULL | 状态变更时间 |

DDL 草案：

```sql
CREATE TABLE IF NOT EXISTS agent_memory_tasks (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id      INTEGER NOT NULL REFERENCES users(id),
    start_msg_id INTEGER NOT NULL,
    end_msg_id   INTEGER NOT NULL,
    status       VARCHAR(16) NOT NULL DEFAULT 'pending',
    attempts     INTEGER NOT NULL DEFAULT 0,
    next_retry_at DATETIME,
    last_error   TEXT,
    created_at   DATETIME NOT NULL,
    updated_at   DATETIME NOT NULL
);
CREATE INDEX IF NOT EXISTS ix_agent_memory_tasks_status_due
    ON agent_memory_tasks(status, next_retry_at);
CREATE INDEX IF NOT EXISTS ix_agent_memory_tasks_user_pending
    ON agent_memory_tasks(user_id) WHERE status IN ('pending','running');
```

### 1.5 与现有表的关系

```
users (已建, analytics 库)
 └─ agent_messages   ← REQ-076 会话消息表（REQ-078 ④；开发 REQ-076 时建，本模块不建）
     · user_id FK→users.id, role(user/assistant), content, 计费 tokens
 └─ agent_memories   ← 本方案事实表（REQ-077，审批后建）
     · user_id  FK→users.id（隔离键）
     · case_id  普通列（可空，关联 REQ-076 所选档案，无 FK——档案删除不级联）
     · source_msg_id 普通列（溯源指向 agent_messages.id，无 FK——表序解耦）
 └─ agent_memory_tasks ← 本方案抽取任务队列表（REQ-077，审批后建）
     · user_id  FK→users.id
     · 经 start_msg_id/end_msg_id 指向 agent_messages 消息区间（普通列）
```

关系要点：
- **只读依赖** agent_messages：抽取 worker 读取的对话必须是「任务.user_id 自己的 agent_messages」子集（SQL 恒带 user_id），不读、不写其它来源消息；agent_messages 的建表/归属由 REQ-076 实现时定（新表或 conversations 扩展），本模块通过「user_id + role + 时间序」读取，与具体形态解耦。
- 不新增对 users 之外现有 28 张表的任何改动（REQ-078 D 口径：不重构现有表）。

### 1.6 建表方式（幂等）

与现有 `main.py` lifespan 顺序对齐，分两段（均幂等，可重复执行）：

1. **ORM 模型注册 + create_all**：新增 `AgentMemory`、`AgentMemoryTask` 两个模型类注册到 `Base`（analytics），`main.py` lifespan 中既有 `Base.metadata.create_all(bind=analytics_engine)`（checkfirst=True）自动为老库/新库补建两表——与现有 `recharge_codes`/`asset_slots` 同一机制，**无需手写 ALTER**。索引/唯一约束在模型 `__table_args__` 内声明，由 create_all 生成（与 1.2/1.4 DDL 对齐）。
2. **FTS5 原生幂等 DDL**：create_all 之后（事实表已存在）调用新增 `ensure_agent_memory_fts(engine)` 函数，执行 §1.3 的 `CREATE VIRTUAL TABLE IF NOT EXISTS` + `CREATE TRIGGER IF NOT EXISTS`（SQLite 均支持 IF NOT EXISTS，重复执行安全）；该函数挂在 lifespan 的 `ensure_schema()` 同区段。

> 本方案书**不执行任何建表**；两表 + FTS 索引仅在审批通过后随开发落地，并在 REQ-077 需求行备注回填。

## 2. 异步抽取任务模型与失败重试

### 2.1 硬约束：不新增任何后台进程/独立服务

抽取在既有 FastAPI 进程内完成，机制选型（在 REQ-077 给的候选里取「任务队列表 + 进程内异步调度」组合）：

| 候选机制 | 评价 | 结论 |
| --- | --- | --- |
| FastAPI BackgroundTasks | 随请求生命周期执行、无持久化、无重试/退避控制，进程崩溃即丢 | 不采用（仅可作为入队后的轻量提醒，无持久化保障） |
| 裸 `asyncio.create_task` 内存队列 | 无持久化，重启丢任务；但**在进程内、零新增进程**，适合做「唤醒」通道 | 部分采用（worker 唤醒事件） |
| **任务队列表（agent_memory_tasks）+ 进程内常驻 asyncio worker 协程** | 任务落 SQLite 持久化，重启可恢复；worker 是 lifespan 内 `asyncio.create_task` 的协程（**不是进程/线程/daemon**），随 FastAPI 启停；天然串行化 + 可做指数退避 | **采用（主方案）** |
| 复用/扩展 AsyncIOScheduler 定时 tick 扫队 | 与既有 jinshuju poller（main.py lifespan 内 AsyncIOScheduler）同风格、进程内；tick 粒度 ≥秒 | 备选/辅助（worker 的兜底轮询可复用它，二选一实现） |

结论：**agent_memory_tasks 持久化队列 + lifespan 注册的进程内单 worker 协程（唤醒事件 + 5s 兜底轮询）**。worker 不是独立进程、不是线程、不是 daemon；进程退出即随事件循环关闭，未完成任务保留在表内由下次启动恢复。

### 2.2 抽取触发时机

- **触发点**：REQ-076 对话接口每完成 1 回合（收到用户消息 → 生成先生回复 → 落 agent_messages → 计费落账）**返回响应之后**，在请求处理器内同步投递一个「抽取任务」（向 agent_memory_tasks 插入/合并一行，纯本地单条 INSERT，<1ms）即返回。**该路径上不发起任何 LLM 调用**，抽取 LLM 只发生在 worker 协程中，主对话接口零阻塞（响应已返回，用户无感）。
- **同用户 pending 合并（coalesce）**：投递时若该用户已有 `pending/running` 任务，则仅把已有任务的 `end_msg_id` 前滚到最新消息 id（一条 UPDATE），不再插新行——同一段密集对话的多次触发收敛为一次抽取，控制 LLM 成本。
- **抽取对象**：任务区间 `(start_msg_id, end_msg_id]` 内该用户自己的 **user 角色**消息（先生回复不抽取）；上下文字符数上限 4000（超长只取尾部最新消息），控制 prompt 与成本。
- **首启处理**：新用户无历史消息不产生任务；若某用户从未抽过（start_msg_id=0）且历史对话量巨大，单次任务最多回溯最近 200 条消息（防一次拉全量）。

### 2.3 任务状态机与处理流程

```
                 投递（对话接口返回后）
pending ────────────────► running ──────► done
  │  ▲                    │   ▲
  │  │ 可重试失败           │   │ 非可重试失败 / 超时丢弃
  │  │ (attempts<3,        │   │ (attempts≥3)
  │  └── next_retry_at=    │   └──► dead
  │      退避后时间          └────────────► (dead 前做规则兜底抽取，见下)
  └──── 启动恢复：残留 pending/running 统一重置为 pending（next_retry_at=now）
```

worker 单循环（串行，全局一次处理一个任务）：

1. 认领：`UPDATE agent_memory_tasks SET status='running', updated_at=now WHERE id = (SELECT id FROM agent_memory_tasks WHERE status='pending' AND (next_retry_at IS NULL OR next_retry_at<=now) ORDER BY id LIMIT 1)`（原子认领，先到先得）；
2. 读该用户 `(start_msg_id, end_msg_id]` 的 user 消息，拼装抽取 prompt（§2.4）；
3. 调外部 LLM（异步 httpx，超时 60s，json_mode 输出结构化 JSON）；
4. 解析结果 → 逐条规范化 → 去重刷新/插入 agent_memories（FTS 触发器自动同步）→ 游标推进（该用户后续任务起点）→ 任务置 done → **单事务批量 commit**（一次 commit 写完所有事实，降写放大）；
5. 失败分支见 2.5；LLM 不可用/解析失败等异常由 worker 捕获，绝不波及主流程。

### 2.4 抽取执行：LLM 优先 + 规则兜底（借鉴 agent-memory-main extraction/pipeline.py）

- **LLM 抽取**：system prompt 明确「只抽跨会话有用的稳定事实（偏好/身份/目标/习惯/经历），忽略寒暄、一次性闲聊；输出 JSON」；response_format=json_object，schema 为 `{"memories":[{"content":str,"fact_type":enum,"importance":0~1,"tags":[str]}]}`，单条 content ≤500 字。复用现有 `app.llm.client.chat`（同 DeepSeek 官方 API、同 usage 埋点、内置可重试错误指数退避，其 max_retries 由本任务层控制为总尝试 ≤3）。
- **规则兜底（关键降级）**：LLM 失败（网络/鉴权/超时/JSON 解析失败，任务标记 failed/dead）或 LLM 未配置时，worker 内同步跑启发式规则抽取兜底：仅取 user 消息、按中英文句读断句、过滤寒暄词（谢谢/好的/嗯等）、长度 ≥6 字且命中偏好标记词（喜欢/偏好/习惯/目标是/因为/我需要/希望等）才入候选，importance 按命中数 0.55~0.85、trust=0.75。**保证记忆能力在 LLM 抖动期不静默丢失，且零额外成本**。
- 计费衔接（待确认项 #4）：抽取走与解读同一 DeepSeek 计费口径；是否向用户余额扣费见 §8 决策点，默认**首版不向用户扣费**、usage 照常埋点（`llm_call` event）便于成本核算。

### 2.5 失败重试与退避

- 可重试错误（网络/超时/429/5xx，client 已分类 retriable）：`attempts+1`，若 `attempts < max_attempts(3)` 则置回 pending 并写 `next_retry_at = now + 2^attempts 分钟`（60s / 120s / 240s），worker 轮询按 due 时间认领；
- 不可重试错误（401/400/404 等）与 `attempts ≥ 3`：置 **dead**，并在 dead 前**执行一次规则兜底抽取**（§2.4），保证该回合至少以规则方式入记忆；`last_error` 截断落库 + `record_event("agent_memory_extract", {status:"dead", ...})` 埋点；
- 任务不无限重试：dead 即终态，人工/运维可在后台按用户手动补投（预留管理端点，P2）。

### 2.6 幂等（防重复抽取同一段对话 / 重复插入同一条事实）

三层幂等：

1. **任务层**：任务以「用户 × 消息区间」语义入队 + 同用户 pending 合并（§2.2），不会对同一回合产生两个任务；
2. **游标层**：每用户抽取游标（下一任务的 start_msg_id）与任务状态在**同一事务**内推进——worker 崩溃在 commit 前：任务仍 pending、游标未动，重启重跑同一区间；崩溃在 commit 后：任务 done、游标已前移，不会重跑；
3. **事实层**：`UNIQUE(user_id, content_hash)`（content 规范化：trim、全/半角统一、空白折叠、英文小写，再 sha1）——即便同一事实跨回合重复出现或被重复抽取，也只会命中**去重刷新**（更新 importance 取 max、更新时间戳，不新增行），绝不重复插同一条事实。

### 2.7 超时与丢弃策略

- 单次 LLM 抽取调用超时 60s（显式传 timeout 覆盖 settings.llm_timeout=180 的解读长超时，抽取短任务不需要长等待）；
- 队列背压：全库 pending 任务数超过阈值（默认 500）时，新投递直接**丢弃并埋点**（记 user_id+消息数，随后续回合自然重抽）；单用户 pending 恒为 1（已由合并保证）；
- 永不丢弃已入库事实；丢弃只发生在「尚未抽取」的调度环节，属成本保护，不影响对话功能。

### 2.8 启动恢复与优雅关停

- **启动**：worker 协程在 lifespan 内 `asyncio.create_task(...)` 启动；启动第一步把残留 `pending/running` 任务重置为 `pending` 且 `next_retry_at=now`（对齐现有 `_recover_orphan_jobs()` 的孤儿恢复先例，置为可重试而非直接 failed——记忆抽取无用户可见成本，值得补跑）；
- **关停**：lifespan shutdown 中 `task.cancel()` + 等待当前一轮收尾（当前 LLM 调用 await 自然中断，任务行保持 running → 下次启动恢复），日志提示未完成任务数。

## 3. 与现有 FastAPI 进程的资源估算（2C1G）

### 3.1 内存增量（预计 ≤ 20MB，典型 <10MB）

| 项 | 估算 |
| --- | --- |
| SQLite 页缓存 | 复用既有 analytics_engine 连接 pragma，FTS5/事实表数据按页惰性加载；默认每连接 cache ~2MB，增量可忽略 |
| worker 协程与任务 | 单 worker + 每次最多 1 个任务的上下文，占用 <1MB |
| 抽取 prompt/响应 | 单次 ≤4k tokens 文本 ≈ 16KB 内存，处理完即释放 |
| 检索结果 | 每问答召回 ≤60 条粗候选再裁到 ≤8 条，<50KB |
| 数据文件体积 | 见 §3.5，不由内存承载 |
| 结论 | 相对现有进程（FastAPI+SQLAlchemy+排盘 node 子进程等）增量很小，1G 内存下无压力 |

### 3.2 CPU 增量

- 抽取为**异步 I/O 密集**：本地 CPU 仅 JSON 解析 + 数条 SQLite 插入（单批 <5ms CPU），主要耗时在等待外部 LLM 网络（不占 CPU，事件循环让出）；
- 检索为单条 FTS5 MATCH + join：单用户 ≤300 条、全库（多用户共享索引）即便 5 万事实，实测参考项目 p95 检索延迟 16.64ms（BM25 查询量级），CPU 占比可忽略；
- 规则兜底抽取（纯字符串扫描）单次 <1ms；
- 结论：抽取 worker 串行化后（2.1），对 2 核 CPU 的增量 <5% 量级，且集中在对话不活跃时段的静默窗口。

### 3.3 SQLite 锁 / WAL / 写放大

- 现状：三个库均已 `PRAGMA journal_mode=WAL` + `busy_timeout=10000` + `foreign_keys=ON`（database.py connect 事件）——WAL 下**读写不互斥**，仅写写互斥；10s busy_timeout 使并发写排队而非报错。
- 记忆写路径（低频）：抽取 worker 串行写，**一个任务的所有事实单事务批量 commit**（一次 BEGIN/COMMIT 写 N 行），锁持有时间 = 数行插入的毫秒级，与既有业务写（断前尘 method 并发落库等）碰撞概率极低；撞上则 busy_timeout 排队，不影响主对话读。
- 写放大控制：
  - FTS 为内容表镜像，插入 = 基表 1 行 + FTS 1 行（触发器），×2 写放大——已是最小化形态（external-content 形态会省镜像写入，但与 trigram 组合受限，MVP 不取）；
  - 去重命中（同 content_hash）只 UPDATE 时间戳，**不触发 FTS UPDATE 触发器**（§1.3 触发器限定 `AFTER UPDATE OF content`），无额外放大；
  - WAL 文件随提交增长，默认 checkpoint 自动回收；维护任务（§6.5）周期性在低峰执行 `PRAGMA wal_checkpoint(TRUNCATE)`（WAL 超过阈值如 10MB 才做，幂等），防 WAL 无界膨胀。
- 主对话请求的库访问（agent_messages 写入 + 检索 session 数据）均为小事务，与抽取写共用 analytics 库同一单写者——WAL + busy_timeout 已覆盖，**无需分库**。

### 3.4 抽取任务与主对话请求的资源竞争控制

| 竞争维度 | 控制手段 |
| --- | --- |
| 抽取 LLM 并发 | 全局**单 worker 串行**（同时只 1 个抽取 LLM 调用），自然不争抢全局 LLM 配额；主对话解读/排盘沿用既有 `llm_global_max_concurrency=100` 与每用户 3 并发，互不干扰 |
| 抽取 CPU/DB | 批量小事务 + 串行 + 唤醒/5s 轮询低占空比；可配静默窗口（默认不做） |
| 队列背压 | pending 上限 500，超出新任务丢弃（§2.7），防止突发对话洪峰积压内存/表 |
| 对话延迟 | 对话路径零额外 LLM/网络等待，仅 <1ms 入队写，响应不受抽取队列长短影响 |
| 兜底 | worker 协程任何异常被 try/except 捕获并记日志/埋点，不触碰请求线程与事件循环主路径 |

### 3.5 数据增长估算（磁盘）

- 单条事实：content 平均 ~60 汉字 ≈ 200B，基表行含元数据 ≈ 350B，FTS 镜像 ≈ 200B → **约 0.6KB/条**；
- 单用户上限默认 300 条 ≈ 0.2MB；活跃 Agent 用户 1000 人 ≈ 200MB 以内；全库行数告警阈值 10 万行（≈60MB 文本数据）时提示运维评估（§6.5）。2C1G 磁盘与 WAL 均无压力（MVP P2 功能，真实 Agent 活跃用户规模远低于此量级）。

## 4. 多用户隔离键设计

**user_id 为唯一隔离键**，四层贯彻：

1. **数据层**：事实表/任务表 `user_id NOT NULL` + 复合索引（§1），唯一键 `(user_id, content_hash)` 保证去重域按用户隔离——不同用户说同一句话会各自存一条；
2. **任务层**：抽取任务携带归属 user_id；worker 认领任务后**只读取该 user_id 自己的 agent_messages**（SQL 恒带 `AND user_id=:uid`），绝不以相邻用户消息为上下文；
3. **检索层**：召回 SQL 强制 user_id 过滤（唯一入口为封装好的检索函数，形如下例），FTS 命中行 join 回事实表后必须 `m.user_id = :uid` 才能进入候选：

```sql
-- 检索封装（参数 :uid 恒为当前登录用户，服务端赋值，不接受客户端传入）
SELECT m.id, m.content, m.fact_type, m.importance, m.created_at,
       bm25(agent_memories_fts) AS bm
FROM agent_memories_fts f
JOIN agent_memories m ON m.id = f.rowid
WHERE agent_memories_fts MATCH :q
  AND m.user_id = :uid
  AND m.deleted_at IS NULL
ORDER BY bm
LIMIT 60;                    -- 粗召回上限，最终 K 条由混合分裁（§5.2）
```

4. **接口层**：
   - 用户可见/删除记忆接口（§6.4）一律经鉴权依赖取 `current_user.id`，**服务端固定使用该值**；接口不接受 body/path 里的任意 user_id，杜绝「查他人记忆」参数注入；
   - REQ-076 对话接口本身的 user_id 同样来自鉴权（既有口径），记忆模块不引入第二个身份源。

**防越权核对清单（开发自测/测试用例）**：a) 甲用户检索不出现乙用户事实（同关键词互测）；b) 甲删除记忆接口传乙的记忆 id → 404/403（按 (id, user_id) 双条件命中才删）；c) 甲的记忆不进入乙的开场/提问召回；d) 抽取任务不跨用户读消息；e) 全库扫描型接口不暴露（列表接口只按当前用户分页）。

## 5. 召回注入 prompt 策略

### 5.1 召回时机（两处，均可独立开关）

1. **开场召回（进入会话/先生开场白生成时）**：用户在太初先生会话页发起新一轮（先生按角色设定生成开场白，REQ-076②c）时，若该用户有既往记忆，按**时间衰减+重要度**取最近/最重要的 K 条拼入（此时无用户查询词，走 recency 通道，§5.2）。目的：让先生开场带记忆连续性（如记得用户上次谈的烦心事），贴合「看开、开导」人设。
2. **每轮提问前召回（核心）**：每收到一条用户提问、组装发给 LLM 的上下文时，以**最新用户消息文本为查询词**做 BM25 召回（可选叠加所选档案 case_id 过滤，见决策点 #6）。目的：先生回答结合用户既述偏好/背景/目标，跨会话一致。

约束：召回**不改变 REQ-076 的会话内上下文窗口口径**（闲聊标准、保守窗口）——记忆块占用计入该窗口预算，K 值按预算控制（5.5）。

### 5.2 召回条数上限与排序

- 条数：粗召回 60 → 混合分裁 **最终 K**。默认 K：提问前 6 条、开场 8 条（决策点 #1）。
- 排序 = **BM25 相关度 + 时间衰减** 混合分：
  - BM25 相关度归一：`rel = 1 / (1 + |bm25(agent_memories_fts)|)`（负分越小越相关，借鉴参考项目转换式）；
  - 时间衰减：`fresh = exp(-age_days / τ)`，τ=30 天（约 30 天新鲜度折半）；
  - 最终分：`score = rel + α · importance · fresh`，α 默认 0.35（权重可配）。
- 通道与兜底：
  - 有查询词（≥3 有效字符，trigram 起效）→ BM25 通道 + 混合分；
  - 无查询词（开场）→ recency 通道（纯 `importance · fresh` 排序取 K）；
  - 查询词 <3 字符或 BM25 零命中 → 降级 recency 通道取 K/2（避免空召回），埋点 `agent_memory_recall` 记录通道与命中数。
- 冲突记忆（如用户后来改口）：MVP 不做自动合并/裁决，靠「用户最新表述优先」的提示词规则（5.4）+ 用户可见可删接口人工纠正（§6.4）；同内容重复自动去重刷新（§6.2）。

### 5.3 注入位置与格式

- 位置：作为**独立 system 消息段**，紧跟 REQ-076 角色主 prompt（master.md）之后、用户消息之前（顺序：system[角色] → system[记忆块] → …历史消息 → system/当前问题）。独立成段，使记忆块**不污染**后台可配置、可版本回滚的角色 prompt 文本（REQ-048 只管 master.md 原文，记忆为请求期动态装配，回滚 master 不影响记忆管线）。
- 用户侧不可见、不可改：记忆块只存在于发给模型的消息数组，前端不展示（先生回复文本自然带出即可）。
- 渲染示例：

```
【长期记忆（内部参考：勿向用户复述本条原文；若与用户当前说法冲突，以用户最新表述为准）】
- 用户偏好绿茶，习惯晚睡（偏好，重要度 0.8）
- 用户在互联网公司做产品经理，目标是今年升职（身份/目标，重要度 0.9）
```

### 5.4 与 REQ-076 角色 prompt 的关系与边界规则

- REQ-076②c：system prompt 用户不可改、后台可配置（backend/prompts/agent/master.md，纳入 REQ-048 热改+回滚）。记忆块**不属于** master.md 内容，是动态追加段——两者职责分离：master.md 管角色/指引原则/免责/开场白话术，记忆块管「这位用户是谁、说过什么」。
- 提示词内嵌 3 条边界规则（防幻觉/防泄隐私/防陈旧）：
  1. 记忆仅供参考，与用户当前表述冲突时以用户最新说法为准；
  2. 不得向用户复述记忆库原文或声称「我记着你的档案」式暴露内部机制；
  3. 用户话题与记忆无关时不硬套记忆。
- 档案（case）数据的咨询上下文仍走 REQ-076 既有档案摘要通道，**记忆块不承载档案排盘数据**（防把档案数据拷入记忆造成冗余），记忆只存跨会话的用户自身事实；case_id 仅作召回时可选的范围标记。

### 5.5 token 预算与静默降级

- 记忆块预算上限：默认 1,200 tokens/次（6~8 条 × 平均 ~150 tokens 渲染），超出按混合分从低到高裁掉；整个请求仍在 REQ-076 保守窗口内（决策点可调）。
- 召回/渲染任何异常（FTS 不可用、解析错误）：**静默降级为不注入记忆**，先生正常应答，不报错、不影响计费与对话（记忆是增强不是依赖）。
- 埋点：`agent_memory_recall`（user_id、通道、命中数、注入条数、耗时）、`agent_memory_extract`（抽取结果数/去重数/失败）。

## 6. 数据增长与清理策略

### 6.1 上限

| 上限 | 默认值 | 说明（决策点 #1/#2） |
| --- | --- | --- |
| 单用户活跃事实上限 | 300 条 | 抽取落库前检查，超出按淘汰分驱逐（见下） |
| 全库行数软告警 | 100,000 条 | 仅运维告警（ops events/后台提示），不自动删 |
| 单条 content | ≤500 字 | 抽取结果超长截断 |

### 6.2 去重 / 刷新 / 合并

- **去重（自动）**：`UNIQUE(user_id, content_hash)`——用户重复陈述同一事实（跨回合/跨会话）只刷新：importance 取 max、updated_at 前移、累加一个来源引用计数（MVP 不存明细，仅埋点计数），不新增行（§2.6 事实层幂等）。
- **刷新**：去重命中时更新时间戳，等于提升新鲜度，避免「反复念叨的事反而被当旧事清理」。
- **语义合并/LLM consolidate**：MVP 不做（2C1G 下每轮 consolidation LLM 调用不值当）；预留：若需求方后续要，可借鉴参考项目 consolidation 思路做低峰批量合并，见决策点 #7。

### 6.3 过期清理（低价值 / 长期未用）

维护任务（进程内 asyncio，每 24h 低峰一次，幂等；与抽取 worker 同属 lifespan 协程，不新增进程）执行：

1. **淘汰驱逐（维持单用户上限）**：抽取新事实前若该用户已达 300 条，计算淘汰分 `score = 0.6·importance + 0.4·log1p(access_count) - 0.5·age_days/90`，逐条软删 score 最低者直至腾出空位（软删 → FTS 由触发器同步摘除）；
2. **低价值/长期未用清理**：软删满足 `deleted_at IS NULL AND last_recalled_at < now - 180 天 AND importance < 0.5`（默认 180 天，决策点 #3）的事实；已被用户手动删除的不复活；
3. **物理清除**：软删超过 30 天的事实物理 DELETE（回收空间，触发 FTS 行删除），并执行 `PRAGMA wal_checkpoint(TRUNCATE)`（§3.3）；
4. 每次清理产出计数埋点 `agent_memory_cleanup`（清理条数/驱逐条数），供运维核对。

### 6.4 用户可见/可删（REQ-066 开关与用户控制呼应）

- **用户查看**：`GET /api/agent/memories?page=&size=`——返回当前登录用户全部事实（分页，含 fact_type/importance/created_at/最近召回时间），前端在「太初先生」会话页或「功能设置」内提供「记忆管理」入口展示（MVP 前端展示形态待定，见决策点 #5）；
- **用户删除**：`DELETE /api/agent/memories/{id}` 单条软删（仅本人，按 (id, user_id) 双条件，防越权）；可选 `DELETE /api/agent/memories` 一键清空本人记忆（二次确认）；
- **REQ-066 开关关系**：
  - 「太初先生 Agent」开关（REQ-066⑦，默认开）关时：入口隐藏、**不召回、不抽取**，但既有记忆数据保留（与 REQ-066⑦「既有会话与数据保留，重开可见」同口径）——开关仅控制显隐，不触发数据清除；
  - 是否单设「长期记忆」独立子开关（默认随主开关）为决策点 #4；若设独立开关，用户可「关记忆但继续用 Agent」。
- 账号删除联动（若未来提供注销）：事务内物理清除该用户 agent_memories/agent_memory_tasks（含 FTS 行），不留残留。

### 6.5 运维/后台可观测（呼应 REQ-050/REQ-048 风格）

- 埋点事件（events 表，ops 库）：`agent_memory_extract`（每次抽取：抽出/去重/失败数、耗时、通道）、`agent_memory_recall`、`agent_memory_cleanup`、复用 `llm_call`（抽取 LLM usage）；
- 后台预留（P2）：按 user_id 查看记忆列表与手动补抽/清理入口，纳入后台审计（admin_audit_logs，沿 REQ-050 Agent 通道或 admin 页）。

## 7. 附录：与 REQ-076 太初先生 Agent 的接口衔接

### 7.1 对话流时序（记忆视角）

```
用户 ──消息──► REQ-076 对话接口（POST /api/agent/chat）
                │ 1) 落 agent_messages（user 消息）
                │ 2) 组装上下文：master.md 角色 prompt + §5 召回记忆块（查询=本条用户消息）
                │ 3) 调 LLM 生成先生回复 → 4) 落 agent_messages（assistant）→ 5) 计费扣分
                │ 6) 返回回复给前端（用户无感）
                │ 7) 投递抽取任务：agent_memory_tasks 插/合并 1 行（<1ms，无 LLM）
                ▼
      进程内抽取 worker（lifespan asyncio 协程，串行）
                │ 认领 → 读该用户 (start,end] 回合 user 消息 → LLM 抽取（json_mode, 60s 超时）
                │ → 去重刷新/插入 agent_memories（FTS 触发器同步）→ 游标前移 → done（单事务）
                │ 失败：指数退避重试 ≤3 → dead 前规则兜底抽取（§2.5）
                ▼
      下一次会话提问/开场 → §5 召回（BM25+时间衰减）→ 拼入 system → 先生应答带记忆
```

### 7.2 衔接约定清单

| 衔接点 | 约定 |
| --- | --- |
| 对话接口 | 由 REQ-076 在返回响应后调用记忆模块入队函数（`enqueue_extraction(user_id, last_user_msg_id)`）；入队失败（库不可用等）静默记日志，不影响对话 |
| 消息读取 | 记忆 worker 只读「本 user 的 agent_messages 中 role='user' 且 id ∈ (start,end]」；agent_messages 建表归 REQ-076，字段最小约定：id / user_id / role / content / created_at（REQ-078 ④口径：user_id + role + content + 计费 tokens） |
| 开场白 | 先生开场白仍由 master.md 配置段（可轮换）决定话术；开场召回记忆仅作 system 记忆块注入，不覆盖开场白文本 |
| 计费 | 对话回合按 REQ-076 既有口径扣分；抽取 usage 独立埋点，是否计入余额见决策点 #3 |
| 上下文窗口 | 记忆块计入 REQ-076 保守窗口预算（默认 1,200 tokens，§5.5），由记忆模块按预算自裁 |
| 版本/回滚 | master.md（REQ-048）与记忆块完全解耦：后台改/回滚角色 prompt 不影响记忆存储与召回逻辑 |
| 埋点 | agent_message（REQ-078 C）由 REQ-076 打；agent_memory_* 由记忆模块打 |
| 交付顺序依赖 | 记忆模块可独立开发联调（用临时消息来源表/mock），agent_messages 就绪后切正式读取；**agent_memories / agent_memory_tasks / FTS 仅在审批通过后建** |

## 8. 待需求方确认的关键决策点

| # | 决策点 | 方案默认建议 | 影响 |
| --- | --- | --- | --- |
| 1 | 单用户记忆条数上限 / 全库软告警阈值 | 300 条 / 10 万行 | 数据量、清理频率、检索性能上限 |
| 2 | 每轮召回条数 K（提问前 / 开场）与记忆块 token 预算 | 6 条提问 / 8 条开场，预算 1,200 tokens | 提示词质量与上下文成本平衡 |
| 3 | 抽取 LLM 是否走现有余额计费（1 积分=1000 tokens 口径） | 首版**不计费**（后台成本，usage 照常埋点）；如需计费按 consume 流水单列并标注 memory_extract | 成本归属与用户余额口径 |
| 4 | 抽取触发粒度与成本：每回合合并抽取 vs 会话空闲窗口批量 | 每回合触发 + 同用户 pending 合并（密集回合收敛为一次 LLM 抽取）；是否叠加「静默 5 分钟窗口」待确认 | LLM 调用次数/月成本、记忆时效 |
| 5 | 用户是否可见/可删记忆，及前端入口形态 | 可见（分页列表）+ 可单条删/一键清空；入口建议「功能设置-太初先生」下「长期记忆管理」 | 用户控制感、合规（呼应 REQ-066） |
| 6 | REQ-066 记忆开关形态 | 随「太初先生 Agent」总开关（关=不召回不抽取但保留数据）；是否单设「长期记忆」独立开关（默认开） | 开关清单与 UI 文案 |
| 7 | 过期清理阈值与是否引入 LLM 语义合并 | 180 天未召回且 importance<0.5 清理；MVP 不做语义合并（预留 P2） | 记忆保鲜与算力成本 |
| 8 | 抽取的内容边界 | 仅抽取 user 消息中「稳定偏好/身份/目标/习惯」，不抽取先生回复、不抽取一次性闲聊；敏感/隐私类信息是否需过滤词表 | 隐私与体验边界 |
| 9 | 部署形态假设 | 维持 MVP **单进程**（现有 usage 账本等已按单进程假设）；若未来多 worker 部署，任务认领 SQL 天然安全（原子 UPDATE 认领），进程内唤醒通道需再评估 | 扩展性预埋 |
| 10 | master.md 与记忆块的提示词内是否需要「我记着……/向我确认」式的表述引导 | 不暴露记忆机制（§5.4 规则 2），先生自然带出即可 | 对话体验与拟人度 |
