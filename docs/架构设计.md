## 1. 概述与设计原则

### 1.1 产品定位与硬约束

- 形态：仅 H5，不做 APP / 小程序；每用户独立账号自主完成。
- 主钩子：事业运势（"事业运势趋势参考"），不铺"什么都能算"落地页。
- 内容定性：命理文化 / 国学运势 / 事业运势趋势；**不承诺结果**；禁医疗 / 投资 / 司法预测（双层合规护栏兜底，§11.4 附录错误码之外见 ADR）。
- 架构即成本：排盘/演算/校准打分为**确定性计算**（本地执行、零 LLM）；仅"解读 / 校验 / 修正对话"调用模型。
- 数据资产：独立账号 + 生辰 + 历史对话 + 消费流水 = 可累积"命理档案"，是横向扩展（生肖 MBTI / 塔罗）与商业化（积分体系）底座。
- 单位经济优先：成本闸门前置（§13），先量单位成本再定价。

### 1.2 架构范式：模块化单体（微服务就绪）

- **单进程模块化单体**：FastAPI 单端口（8000）同时服务 `/api` + 前端静态；模块按服务形状切分（独立 I/O 契约、独立提示词、独立表/路由），Phase2 可把模块"拎"成独立进程/容器即物理微服务（迁移清单见 §14.2）。
- **模块间通信**：MVP 单进程内直接调用 + 后台任务编排（等价于进程内事件分发器，不再引入独立总线/消息中间件）；Phase2 升真实事件总线（Redis Streams / Kafka，分区键 = methodKey）时事件 Schema 不变、需激活幂等（去重键 `caseId+methodKey+phase`，防御性预留）。
- **落库为唯一事实源**：chart / method-result / 校验 / 校准 / 对话 / job 进度全部持久化，进度不只存内存。
- **多用户隔离（硬约束）**：JWT 取 `userId` 注入所有查询；`userId`-scoped repository，任何 `SELECT/UPDATE/DELETE` 必带 `user_id` 条件；否定用例（A 访问 B 的 caseId → 403/404 且不泄漏）列入测试。
- **合规护栏横切**：生成侧 prompt 话术 + 输出侧硬过滤（`check_output` 禁区检测 + `append_disclaimer` 末行免责 + 占卜门控）。

### 1.3 本文相对旧稿的关键更新点（不再按旧稿表述）

1. **并发模型**：断前尘/预测均按「每 job 内 3 并发 + 模块级全局信号量兜底（默认 100，跨所有用户）」执行；预测本就是并行扇出，同样两层信号量限流。旧稿"9 法串行 / 逐个串行 / 严禁并行 / 串行子会话"表述全部废止（详见 §7.2）。
2. **积分计费**：改为**逐法扣费**——断前尘/预测每生成一个 method 答案立即按该法 token 扣积分（ref 形如 `job:{jobId}:{methodKey}`）；追问（revise）与单法直问（query）也在 LLM 返回后即时扣；失败也按已消耗 token 扣。旧稿"任务收尾统一扣费（`_charge_after_run` 风格）"表述废止（详见 §7.3 / §9.4）。
3. **LLM 超时与输出上限**：`llm_timeout = 180s`；新增 `llm_max_tokens = 12000`（method analyze 输出上限）、`llm_validation_max_tokens = 4000`（校验输出上限）（§6.3 / §8）。
4. **新增 LLM session 断点续跑机制**：服务重启孤儿 job 置 failed + 同 case 同 phase 部分结果续跑注入 `continuation` 上下文（§7.5）。
5. **新增 job 幂等防重复**：断前尘/预测端点复用进行中（及断前尘已成功）的 job（§7.6）。
6. **case.status 状态机补全**：`created → paipan_done → dqc_done → calibrated → predict_done`（§4.3）。
7. **积分扣费位置共 4 处**：断前尘逐法、预测逐法、revise 即时、query 即时；排盘/校准打分不扣（§9.4）。
8. **注册赠送积分 = 220**（`free_credit_on_register=220`；1 元 = 10 积分，1 积分 = 1000 tokens）（§9）。

## 3. 用户系统与鉴权

### 3.1 注册（手机号 + 图形验证码 + 设备指纹 + IP 限流）

- **手机号即用户名**：注册填 11 位中国大陆手机号（前端正则 `^1[3-9]\d{9}$` 校验 + 提示），`username` 唯一；密码 min 6 位，确认密码字段。注册成功即建 `users` 行（密码哈希，不存明文）+ 赠送 220 积分（§9.3）。
- **图形验证码（注册必填）**：`GET /api/auth/captcha` → PIL 生成 4 位 PNG（去易混淆字符 0/O/1/I/L），5 分钟 TTL、**一次性**（比对即作废）、纯内存存储不落盘；注册请求带 `captcha_id` + `captcha_code`。
- **设备指纹**：前端生成 `device_fingerprint`（默认空串兼容旧客户端）；注册成功落 `register_limits` 一行。
- **IP 限流（防脚本批量注册）**：同一 IP 1 小时内最多 **2** 次注册（`REGISTER_IP_MAX_PER_HOUR=2`，查询带 1 小时窗口）；同一设备指纹**永久只能注册一个账号**（不带时间窗）。
- 登录失败锁定与刷新令牌见下。

### 3.2 登录与令牌模型（JWT HS256）

- **登录**：`POST /api/auth/login`（错误统一 401）。失败计数（`login_attempts`）：同 username 累计失败 ≥ **5 次**（`login_max_failures`）→ 锁定 **24 小时**（`login_lock_minutes=1440`，`locked_until` 内拒绝登录）；登录成功清空失败记录。
- **令牌模型**：
  - 访问令牌：**JWT，HS256 签名**（ADR-0008），含 `sub=userId`、`type=access`，**30 分钟**过期（`access_token_ttl=1800`）；服务端零存储、无 sticky session、任意实例可验。
  - 刷新令牌：opaque，签发时服务端存 **hash** 到 `refresh_tokens`（`expires_at=7d`，`refresh_token_ttl=604800`，`revoked` 标志可整体清理）；`POST /api/auth/refresh` 换发新访问令牌。
  - MVP 不暴露用户侧吊销端点；**不做找回 / 改密 / 注销**（忘记密码由运维进库重置哈希），Phase2 扩展。
- 网关从 `Authorization: Bearer <JWT>` 提取 `userId`，注入所有模块调用与 DB 查询（多用户隔离硬约束，§1.2）。

### 3.3 case 生命周期端点（用户侧）

| 方法 | 路径 | 要点 |
|---|---|---|
| POST | `/api/cases` | 建档：生辰/性别/出生地/经纬度/真太阳时 + 主问场景（需 JWT）；返 `caseId` |
| POST | `/api/cases/{id}/paipan` | 触发排盘（确定性零 LLM）；幂等 upsert `charts`；置 `paipan_done`；返 chart 摘要 + `degradedMethods` |
| POST | `/api/cases/{id}/duan-qian-chen` | 断前尘（异步）：202 `{jobId,total}`；**job 幂等防重复**（§7.6） |
| POST | `/api/cases/{id}/calibration` | 校准反馈逐条提交 → 契合度打分（纯代码）→ 置 `calibrated` |
| POST | `/api/cases/{id}/predict` | 预测（异步）：路由选法 + 并发 + 合成；202 `{jobId,total}`；job 幂等（§7.6） |
| POST | `/api/cases/{id}/revise` | 多轮修正对话（LLM，即时扣费） |
| POST | `/api/cases/{id}/query/{methodKey}` | 单法直问（bypass 聚合，缓存优先，即时扣费） |
| GET | `/api/cases/{id}/archive` | 命理档案查询导出（结构化 JSON，数据库为唯一事实源） |
| GET | `/api/jobs/{jobId}` | 查任务状态：`{status, completed, total, result?}`；**纯读库、零 LLM** |

> 完整 REST 清单（逐端点字段 / 长任务标记）以 `standards/03-接口与数据字典.md` 为权威（行为语义见 §3.3/§7/§9）。轮询是纯代码行为：前端 `setInterval` + HTTP GET，不触发任何模型调用、无 token 消耗。

## 4. 数据模型

### 4.1 分库策略（SQLite 三库）

| 库 | 职责 | 表 |
|---|---|---|
| `taichu_analytics` | 用户 / 排盘 / 档案 / **积分 / 运营配置** | users、refresh_tokens、login_attempts、register_limits、cases、charts、method_results、calibrations、conversations、jobs、route_decisions、**credit_accounts、credit_transactions、system_configs**（节146 已 DROP `recharge_codes`） |
| `taichu_feedback` | 跨用户质疑（方法迭代底座） | feedbacks、feedback_summaries |
| `taichu_ops` | **埋点 / 后台 / 错误上报**（写多读少、量大、可单独清理归档） | events、admin_users、admin_audit_logs、error_reports |

### 4.3 case.status 状态机（现行补全）

```
created ──paipan──▶ paipan_done ──duan-qian-chen(成功)──▶ dqc_done
   │                                                        │
   │                    ◀──calibration── calibrated ──predict(成功)──▶ predict_done
   ▼
 failed（任意阶段任务失败/中止可置 failed；job 失败语义见 §7）
```

- `paipan` 成功 → `paipan_done`（charts 幂等 upsert）。
- 断前尘 job `succeeded` → `dqc_done`（旧稿仅提 paipan_done/calibrated，已补全）。
- 校准提交 → `calibrated`（可多次，upsert）。
- 预测 job `succeeded` → `predict_done`。
- 后台运维「重置档案」把 case 的 charts/method_results/calibrations/conversations 删除、`status` 置回 `created`（保留 user 与积分）。
- 枚举中另有 `dqc_running` / `predict_running`（任务进行中）与 `failed` 兜底。

## 5. 排盘引擎

### 5.1 技术路线（ADR-0001：自研为主）

- **确定性、零 LLM**：排盘是纯计算，不每次调模型；只有"解读 + 校验 + 修正对话"消耗 token。
- **自研为主**：排盘胶水、9 法切片、契合度打分、全部 method-prompts、合并规则自研（`app/paipan/`：engine + shensha + slicer + scorer）；底层历法/星盘计算用开源库（Python `lunar-python`、Node 端 `iztro` / `mingyu-core`）；mingli 仓库**仅作参考，不 import、不打包**。
- **双运行时**：Python 侧负责编排与确定性切片；Node 22 常驻服务 `paipan-node/server.mjs`（:9317）承载需要 iztro / mingyu-core 的流派（紫微/西占/七政/奇门等），**HTTP 优先路径 + subprocess 降级**（ziwei.cjs / extra.mjs），应用启动时拉起，失败仅告警不阻断。
- **输出**：`chart.json` 全量落库 `charts.chart_json`（唯一事实源）；REST 按前端所需投影裁剪。

### 5.3 契合度打分（scorer，纯代码防幻觉）

- 输入：结构化反馈 `[{method, domain, claim, feedback: confirmed|denied|corrected}]` + `results`（method-result 聚合）+ `validations`。
- **三因子公式**（硬编码契约 W 权重，勿运行期改）：
  - 命中率 = `(confirmed + 0.5×corrected) / (confirmed+denied+corrected)`；分母 0 → 该方法不计入评分；
  - 命题质量 = `1 − (error×0.5 + warning×0.25 + info×0.1)`（severity 来自该校验输出；无 validation ⇒ 0.5）；
  - 依据链完整度 = 条目中「evidence 或 basis 非空」占比；总条目 0 ⇒ 0.5。
- **契合度 = 0.5×命中率 + 0.3×命题质量 + 0.2×依据链完整度**（clamp 0–1）。
- **校准权重**：`weight = 0.4 + 0.6 × 契合度`；无反馈方法权重 0.5。
- 落库：`calibrations.record_json`（反馈原文）+ `fit_json`（fit rows + weights）；整体 fit = 有行方法的契合度均值；无行兜底 0.5、`complete=False`。
- 质量兜底：排盘回归基线 + 案例库锚点（自研排盘与提示词回归，`tests/fixtures`），防引擎升级/逻辑改动/提示词漂移破坏正确性。

## 6. LLM 接入与方法模块

### 6.1 LLM 客户端（app/llm/client.py）

- 模型：`deepseek-v4-flash`（`TAICHU_LLM_MODEL`），OpenAI 兼容接口，base `https://api.deepseek.com`；key 只允许环境变量 / `backend/.env`，严禁硬编码。
- `chat(messages, json_mode=…, max_tokens=…)`：超时 `llm_timeout = 180s`（TAICHU_LLM_TIMEOUT；长 prompt + 长 JSON 输出需更长超时）；重试 `llm_max_retries = 1`（原始 1 次 + 重试 1 次 = 最多 2 次尝试）；`llm_temperature = 0.3`。
- **输出上限**：`llm_max_tokens = 12000`（method analyze 输出上限，防超长拖慢生成）；`llm_validation_max_tokens = 4000`（校验输出上限）。

- 每次调用记录 `llm_call` 埋点（model / prompt_tokens / completion_tokens / latency / 成功失败，§11）。

### 6.2 方法模块（app/methods/，9 法）

- 注册表 `METHOD_KEYS`（顺序与 slicer / 路由表对齐）：`bazi-pattern, bazi-dayun-liunian, bazi-shensha-nayin, bazi-hunyin-caiyun, ziwei, xizhan, qizheng, qimen-lifetime, wuyun-liuqi`；因目录名带连字符，用 importlib 按文件路径加载各目录 `analyzer.py`，导出 `ANALYZERS: {key: async analyze(...)}`。
- 每个方法一个目录：`analyzer.py`（薄封装）调用公共 `analyze_method`，持有自己的提示词 `backend/prompts/method-prompts/<key>.md`（自研，9 份）。
- **占卜类（六爻/梅花/大六壬/择日）不注册**到现行路由（Phase2 开放，显式触发）。

### 6.3 analyze_method 契约（含 continuation）

```python
async def analyze_method(method_key, phase, slice_data, user_question="",
                         calibration_feedback=None, continuation=None) -> dict | None:
    # 1) prompt 缺失 / slice 空 → 返回 None（编排层按「方法降级」处理，零 token）
    # 2) 组装 messages（system=method prompt；user=JSON：method_key/phase/问题/切片/
    #    calibration_feedback?/continuation?）
    # 3) chat(json_mode=True, max_tokens=settings.llm_max_tokens)
    # 4) LLMError → 抛给编排层决定降级；输出解析失败(ValueError) → 同上
    # 5) 返回 method-result v2（method 字段回填 method_key）
```

- **`continuation` 参数**：断点续跑时由编排器注入（§7.5）；非空时写进 user payload，指示模型"继续完成剩余方法，不要重复已完成的结论"。
- 校准反馈：断前尘阶段后的多轮修正把 `calibration_feedback` 一并注入；单法直问/预测传 `user_question`。

### 6.4 method-result v2 契约（太初自主定义，兼容 mingli 关键字段）

```jsonc
{
  "method": "bazi-pattern",
  "phase": "duan-qian-chen",            // | "prediction"
  "past_propositions": [                 // 断前尘：过去断言
    { "year_range": "...", "domain": "事业|财运|婚姻|…", "claim": "…",
      "confidence_level": "high|medium|low|speculative",
      "confidence_reason": "…", "basis": "…" }

}
```

- `validation.json`（断前尘）**另存**于 `method_results.validation_json`，不混入 method-result。
- `confidence_level` 归一映射（仅内部裁决用，不写回 JSON）：high≈0.8 / medium≈0.55 / low≈0.3 / speculative≈0.15。
- 契约字段为跨模块唯一协商点，禁止私自改；mingli 升级仅作人工评估参考（ADR-0001 代价：失去上游自动惠及，需自行守提示词质量）。

### 6.5 主模块 / 聚合职责（问卷与裁决，置于任务编排收尾）

- **断前尘问卷**（编排收尾合成）：收集本 case 全部已落库断前尘结果 → 保留 `confidence_level ∈ {high, medium}` 的命题 → 按 domain 去重 → **最多 10 条**问卷断言（`_compose_questionnaire`），随 job 结果返回 H5。

- 单方法直问（query）**bypass** 聚合：直接方法模块 + 缓存优先，不触发其他法的 LLM 调用。

## 7. 任务编排（断前尘 / 预测）

### 7.1 总览：jobId + 代码轮询（ADR-0005，现行）

- `POST /api/cases/{id}/duan-qian-chen` 与 `POST /api/cases/{id}/predict`：创建 `jobs` 行（`pending`）→ `asyncio.create_task` 后台执行编排器 → **立即返 `202 {jobId, total}`**。
- 进度**必须落库**：每个 method 完成即 `_bump_completed`（SQL `completed = completed + 1` 原子自增，避免并发读改写丢更新）。
- 前端**代码轮询** `GET /api/jobs/{jobId}`（纯读库、零 LLM）：2s 起、指数退避上限 10s，终态立即停止；轮询硬超时断前尘 10min（`job_timeout_dqc=600`）/ 预测 3min（`job_timeout_pred=180`）。
- 任务开头**余额预检** `_check_balance_or_fail`：积分不足（BizError 5002）→ job 直接 `failed`（error=积分不足），不跑 LLM。

### 7.2 并发模型（现行：每 job 3 并发 + 全局 100 兜底）

断前尘与预测**均不再串行**，统一为两层信号量嵌套限流：

```python
# 模块级全局信号量：跨所有用户、所有 job 的 method 并发兜底（默认 100）
_global_llm_semaphore = asyncio.Semaphore(settings.llm_global_max_concurrency)  # =100

# 每个 job 内新建 per-job 信号量：单用户（单 job）method 并发上限（默认 3）
sem = asyncio.Semaphore(settings.llm_max_concurrency)                            # =3

# 每个 method 协程内两层嵌套（先全局、后 per-job；退出反向释放）：
async with _global_llm_semaphore, sem:
    ...
```

- 语义：**单用户单 job 同时最多 3 个 method 在跑**（控单盘成本/单用户占用量）；**所有用户同时进行的 method 总数 ≤ 100**（全局兜底，防整站打爆 LLM 配额）。
- 配置：`llm_max_concurrency=3`（TAICHU_LLM_MAX_CONCURRENCY）、`llm_global_max_concurrency=100`（TAICHU_LLM_GLOBAL_MAX_CONCURRENCY）。
- **断前尘**：`pending = 9 法去降级/未注册`，`asyncio.gather(return_exceptions=True)` 并发扇出；每法协程独立短 `AnalyticsSession`（绝不共享主 session，防并发串数据），协程内：查缓存 → analyze → 【仅断前尘】validate → 落库 → 逐法扣费 → 原子推进度。
- **预测**：本就是**并行扇出**，同样两层信号量限流；路由选法后并发 analyze（**不校验**，§8），完成后 synthesize。
- 单法 `LLMError/ValueError` 只记入 `failed_methods`（不因单法整体崩）；`pending` 非空且全部失败 → job `failed`，error=`LLM 服务不可用，全部方法失败`；其余未捕获异常 → job `failed`，error=str(e)。
- 跳过的法（降级/未注册）只原子推进度、不调 LLM、不产生扣费。

### 7.3 逐法扣费（现行计费模型）

- **原则：每生成一个 method 答案就立即按该法实际 token 扣积分**，而不是任务收尾统一扣：
  - 每法协程在 analyze 前快照本协程 context 的 usage 账本（`before = get_usage()["total_tokens"]`）；
  - 处理完（成功、或 `ValueError`——LLM 已成功返回但解析失败）后按差值 `tokens = get_usage()["total_tokens"] - before` 立即调用 `_charge_method(user_id, tokens, ref=f"job:{job_id}:{key}")`；
  - ContextVar 隔离保证差值只含**本方法**的 analyze(+validate) 消耗，ref 精确到 `job:{jobId}:{methodKey}`；
  - `LLMError`（chat 未成功返回、usage 未累加）差值通常为 0，不产生扣费；
  - **失败也按已消耗 token 扣**（只要 LLM 消耗过）；扣费失败只记日志、不阻断任务进度。
- 任务收尾不再有"统一扣总账"步骤；`job.result_json["_usage"]["total_tokens"]` 用逐法 tokens 求和（主 task 的 contextvar 不含子协程累计，不能直接 get_usage）。
- 扣费单位：`delta = -ceil(tokens / 1000)` 积分（§9.2）；余额可为负，下次任务开头 `check_balance` 拦截。
- 校验（validate）tokens 并入该法差值一起扣（同一 ref）；缓存命中的法 **不调 LLM、不扣费**。

### 7.4 编排子流程

- **断前尘收尾**：gather 后主 session 串行 `_compose_questionnaire`（收集本 case 全部已落库断前尘结果含历史缓存行，high/medium + domain 去重 ≤10 条，记录 `method_count` 与 `failed_methods`）→ 写 `job.result_json` → `completed = total` → `case.status = dqc_done` → `job.status = succeeded`。
- **预测流程**：路由 `route(user_question, Phase.prediction, degraded_methods)`（零 LLM，配置化路由表：主法全跑、辅法按主问高相关子问题跑、降级法不得入选、用户点名法强制纳入）→ `main+support` 去重（保序）→ 回填 `job.total` → 落 `route_decisions` → 并发 analyze（每法独立 session 落库 + 逐法扣费）→ synthesize（阶段5 合并裁决 + 免责声明）→ `case.status = predict_done`、`job.status = succeeded`。

### 7.5 LLM session 断点续跑（新增机制，现行）

- **服务重启孤儿恢复**：应用启动 lifespan 内 `_recover_orphan_jobs()` —— 把残留 `pending/running` 的 job **统一置为 `failed`**（`error="服务重启，任务中断，请重新触发"`）。进程重启后旧编排 task 已消失，残留 job 不可能自行推进；恢复失败只记 warning，不阻断启动。
- **续跑检测（重新触发后）**：断前尘/预测编排开头统计该 case 该 phase 已落库**非空 MethodResult** 的数量 `done_count`：
  - `0 < done_count < total` → 判定为重启后中断续跑 → 对剩余 method 注入 **`continuation` 上下文**：`"该档案之前的推演被服务器重启中断，请继续完成剩余方法的分析，不要重复已完成的结论。"`；
  - **缓存命中跳过已完成 method**：每法协程先查 `method_results`（case_id+user_id+method_key+phase），已有非空 `result_json` 即复用（`cached=True`），**不调 LLM、不重跑校验、不扣费**；
  - `analyze_method` 支持 `continuation` 参数（§6.3），仅续跑轮次注入。
- 用户侧体验：任务中断后 job 显示 failed（提示重新触发）；重新触发后**只跑剩余方法**，已完成方法直接复用，无重复扣费。

### 7.6 job 幂等防重复（新增机制，现行）

- **断前尘** `POST /cases/{id}/duan-qian-chen`：同一 case 已有 `pending/running/succeeded` 的断前尘 job 时**直接复用**（断前尘结果确定性：排盘不变、问卷不变；`succeeded` 的最新 job 也复用，前端轮询立即拿到 questionnaire）→ 返 `202 {jobId, total, reused:true}`。
- **预测** `POST /cases/{id}/predict`：复用 `pending/running` 的 predict job（预测同样输入结果确定）→ 同上。
- 效果：杜绝页面刷新/重复进入导致的**重复跑 + 重复扣费**；`GET /api/jobs/{jobId}` 只读库返回当前进度。

### 7.7 缓存复用策略

- 实现口径：以 `method_results`（case_id + user_id + method_key + phase）为准，已有非空 `result_json` 即命中复用（`cached=True` 标记）；单法直问（query）先查 prediction 缓存，命中零 LLM 直接返回。
- 首次全盘：断前尘 9 法各一次 + 9 次校验 + 预测路由主/辅法各一次，分别落 `method_results`（`cached=false`），随后合成问卷/裁决。
- 失效注意：重排（paipan 幂等 upsert charts）后若排盘输入变化导致盘面内容不同，历史 method_results 的语义需人工判断是否重算（现行实现未按 chart_version 自动失效，作为已知边界记录于此；chart 表保留 `version` 列供后续启用）。

## 8. 校验模块（validation）

- **范围（ADR-0002，现行）**：**仅断前尘阶段**执行校验——每法产出 method-result 后立即跑一次规则性校验（9 法各一次，随该法协程）；**预测阶段跳过**，改用 `confidence_level` 纪律兜底。
- **职责**：对 method-result 做规则/逻辑校验（如断言可核对性、数值年份合理性等），产出 `validation.json`（结构含 `validations: [{severity: error|warning|info, …}]`），供 scorer 的「命题质量」因子使用。
- **独立性**：抽为独立 `app/validation/validator.py`，方法模块不内嵌校验逻辑；`validate(result, slice_data)` 在断前尘每法协程内被调用。
- **模型与计量**：使用独立模型配置 `TAICHU_VALIDATION_MODEL`（现行与主模型同档 `deepseek-v4-flash`，预留切换更便宜模型档）；输出上限 `llm_validation_max_tokens=4000`；校验 tokens 随该法一起计量扣费（§7.3）。
- **开关**：`TAICHU_VALIDATION_ENABLED`（`validation_enabled`，默认 True）可**整体关闭**校验兜底。
- 与打分联动：命题质量 = `1 − (error×0.5 + warning×0.25 + info×0.1)`；无 validation ⇒ 0.5（会削弱校准区分度，故校验不可整体缺席）。
- 风险与锚点：校验模型太弱会污染命题质量 → `tests/fixtures` 建校验回归锚点；`validation_json` 与 method-result 分开落库（`method_results.validation_json`），预测阶段为 `null`。

## 9. 余额系统（REQ-085）

### 9.1 换算与常量（现行）

> **换算**：1 元 = 10,000 tokens；存储层 `credit_accounts.balance` 为整数（1 存储单位 = 1000 tokens），展示层 `balance_yuan = round(balance/10, 2)`（1 元 = 10 单位）。「积分」概念已全站废除，改「余额 ¥」口径（详见 REQ-085）。

| 常量 | 值 | 说明 |
|---|---|---|
| `credit_per_token` | 1000 | 1 存储单位 = 1000 tokens（TAICHU_CREDIT_PER_TOKEN） |
| `recharge_rate` | 10.0 | 1 元 = 10 单位 = 10,000 tokens（TAICHU_RECHARGE_RATE；存 `system_configs`，后台可动态改、无需重启） |
| `free_credit_on_register` | **220** | 新用户注册赠送 22 元 = 220 单位（TAICHU_FREE_CREDIT；220 单位 = 22 万 tokens ≈ 9 盘首跑 + 3 次追问量级） |

### 9.2 模型与扣减规则

- `credit_accounts.balance`（整数，可为负）；所有变动记 `credit_transactions`（**不可变流水**）：`delta>0` 入账（free/recharge/manual/refund）、`delta<0` 消费（consume）。
- 扣费：`delta = -ceil(tokens / 1000)` 单位；一次调用 tokens 超过余额允许扣成负数，下次任务开头 `check_balance`（余额 ≤0 → BizError **5002 余额不足**）拦截；负余额记为待补（运营可视）。
- 计费范围：**只扣 LLM 调用**；排盘（确定性计算）与校准打分（纯代码）**不扣**。
- 注册赠送：注册成功即 `recharge(user_id, 220, type="free", note="注册赠送 22 元")`（失败只记日志不阻断注册）。

### 9.3 模块与 API

```
backend/app/credits/
  service.py    # balance / check_balance / consume / recharge / manual / adjust_balance / transactions
  router.py     # C 端：GET /api/credits/balance、GET /api/credits/transactions
                #   （节146：POST /api/credits/charge-code 已删除）
  labels.py     # 事件中文名 EVENT_NAME_ZH（积分→余额 语义）
                # 节146 删除：codes.py（充值码）/ jinshuju.py（金数据客户端）/ poller.py（轮询入账）
admin：app/admin/credits.py  # POST /admin/credits/manual（余额充值 / 余额调整 + audit）
```

- C 端：`GET /api/credits/balance`、`GET /api/credits/transactions?limit=&offset=`（分页流水）。
- 后台：`GET /admin/config`（运营配置含 recharge_rate）、`PUT /admin/config/{key}`（改折算率等，+audit）、`POST /admin/credits/manual`（余额调整，入参 user_id/delta/note，+audit）；后台新建用户同样赠送 `settings.free_credit_on_register`（22 元）。

### 9.4 扣费位置（共 4 处，现行）

| # | 位置 | 时机 | ref 形如 |
|---|---|---|---|
| 1 | **断前尘编排** `run_duan_qian_chen` | 每法 analyze(+validate) 完成后**立即逐法扣**；任务开头 `check_balance` | `job:{jobId}:{methodKey}` |
| 2 | **预测编排** `run_predict` | 每法 analyze 完成后**立即逐法扣**；任务开头 `check_balance` | `job:{jobId}:{methodKey}` |
| 3 | **revise（追问）** 同步端点 | `chat()` 返回后**即时扣**（调用前 `check_balance`） | `revise:{caseId}` |
| 4 | **query（单法直问）** 同步端点 | LLM 已调用后按本次 analyze 实际消耗**即时扣**（调用前 `check_balance`；缓存命中零 LLM 不扣） | `query:{caseId}:{methodKey}` |

> 排盘 / 校准打分不扣。`analyze_method` / `validate` 本身不感知余额（保持纯函数），计费统一在编排器/端点层做——**逐法扣费**在编排层按每法 usage 差值即时执行（§7.3），端点层（revise/query）在 LLM 返回后即时执行；扣费失败只记日志 + `error` 埋点，进入对账，不吞。

### 9.5 埋点与错误码

- 埋点（events）：`credit_consume`（user_id, tokens, delta, ref）、`credit_recharge`（user_id, delta, type, amount）、`credit_insufficient`（user_id, required, balance）。事件中文语义见 `backend/app/credits/labels.py` 的 `EVENT_NAME_ZH`（积分→余额 展示口径，如「积分消费」→「余额消费」）。
- 错误码：`5002 余额不足`（前端弹中性「余额不足」提示，**节146 后不再引导充值**）、`5003 计费异常`。
- 前端：发起断前尘/预测/追问前可 `GET /api/credits/balance` 预检（可选优化）；**节146 起已无任何充值入口与到账轮询**——用户侧只有「看余额 + 逐法扣费」，余额只能由后台开号赠送或人工调分产生。

## 13. 成本与单位经济

### 13.1 成本闸门（手动切档，人判定）

- 配置 `TAICHU_COST_GATE_MODE = full | lite | minimal`（默认 full），**由人判定切档、不做运行时自动切换**（MVP 最简、无误触发）：
  - `full`：完整断前尘（9 法 + 校验）+ 预测；
  - `lite`（方案C）：2–3 法轻量校准；
  - `minimal`（方案A）：仅主法 + 一轮修正。
- 计量口径：**分析和校验分开计量**（校验模型便宜档），否则阈值不可信；self-run 实测「单 case 首跑全盘总成本（断前尘 + 预测两 phase，含校验）」与「缓存后边际成本」，实测后回填单 case 成本阈值（原设计建议区间 ¥0.5–1.0/case，待实测校准）。

### 13.2 Token 阈值与换算

| 项 | 值 |
|---|---|
| method analyze 输出上限 | 12000 tokens（`llm_max_tokens`） |
| 校验输出上限 | 4000 tokens（`llm_validation_max_tokens`） |
| 换算 | 1 积分 = 1000 tokens；1 元 = 10 积分 ⇒ 1 元 ≈ 1 万 tokens |
| 注册赠送 | 220 积分 = 22 万 tokens ≈ 9 盘首跑 + 3 次追问量级 |
| 首跑 LLM 调用量级（断前尘 + 预测） | 断前尘 9 次分析 + 9 次校验 + 预测路由主/辅法数次（随路由裁剪变化） |

### 13.3 降本杠杆

1. 缓存复用（同 case+phase 结果复用，命中零 LLM，§7.7）；
2. 校验用独立/便宜模型档（现行与主模型同档，预留切换）；
3. 路由表裁剪辅法（ADR-0004，预测只跑高相关方法）；
4. 降级链 `full → lite → minimal`（手动切档）；
5. 并发限流（每 job 3 + 全局 100）控峰、`llm_max_tokens` 防超长生成拖慢/超支；
6. 余额预检（积分不足不跑 LLM）+ 失败按已消耗 token 扣（不吞账）。
