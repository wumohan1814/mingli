## 2. 购买形式：分档位 + 充值码

### 2.1 档位设计（金数据表单「商品」字段）

| 档位 | 金额 | 积分 | 约可支持 |
|---|---|---|---|
| 体验 | ¥6.9 | 70 | 1 次单法直问 |
| 轻量 | ¥9.9 | 100 | 约 10 万 tokens |
| 标准 | ¥19.9 | 200 | 接近 1 次完整首跑 |
| 进阶 | ¥29.9 | 300 | 1 次完整 + 余量 |
| 高阶 | ¥49.9 | 500 | 约 2 次完整 |

> 金额上限 49.9 元受**免费版月交易额 500 元/月**约束（约 10 笔即触顶）；营收上量须升专业版（10 万/月）。

> 档位与「1 元 = 10 积分」的 `recharge_rate` 挂钩；金数据表单里的金额是**写死的**（改档位需手动改表单），而我们的 `system_configs.recharge_rate` 是后端的积分折算口径，两者要**人工保持一致**（见 §6 对账）。

### 2.2 充值码（解决「用户名非手机号」）

用户注册用的是随机用户名，不能靠「手机号/用户名」可靠关联。改用**一次性充值码**：

```
用户在 taichu 前端点「充值」→ 后端生成充值码（如 TC-9F3K2M，绑定 user_id + 15 分钟有效 + 未使用）
  → 跳转金数据表单，充值码作为预填字段（URL query 传参，如 ?code=TC-9F3K2M）
  → 用户选档位 + 支付
  → 金数据表单提交，含「充值码 + 档位金额」
  → 回调（webhook/API/CSV）拿回充值码 → 后端按码找 user_id → 充值 + 标记码已用
```

**充值码特性**：一次性、短时效（防重放）、绑定 user_id、充值后作废。

## 3. 服务器设置（新加坡）

**基本无需额外设置**，已满足：
- ✅ **公网可达**：新加坡服务器有公网 IP。
- ✅ **HTTPS**：`taichu.xyz` + Caddy 自动 Let's Encrypt（C 端充值入口需要）。
- ✅ **免备案**：新加坡服务器不受国内 ICP 备案约束。

**要做的**（免费版采用 API 轮询，无需 webhook 接收端点）：
1. 后端定时任务（如每 5 分钟）用**个人 Token** 调金数据 API `get_form_entries` 拉充值表单数据。
2. 网络方向是**我们主动拉金数据**（新加坡 → 金数据国内服务器），跨境有延迟但可控；本地幂等（按 entry_id/充值码去重）。

## 4. 支付回调（免费版实际方案：API 轮询为主）

### 4.1 首选：API 主动轮询（②，免费版可用 ✅）

- 金数据 API v1 `GET /api/v1/forms/{token}/entries`，个人 Token（Bearer）认证，100 次/小时。
- 我们写**定时任务**（如每 5 分钟），拉取「充值表单」最近提交 → 解析「充值码 + 档位金额 + 支付状态/订单号」。
- 小金商户的支付结果会**写回表单条目**（支付状态/金额/订单号），轮询能拿到这些字段，本地幂等落库即可。
- 幂等：按 `entry_id` + 充值码去重；只处理「支付成功」状态的条目。
- 配额：100 次/小时 × 每页 50 条 ≈ 5000 条/小时，小项目日订单几十~一两百笔完全够。

### 4.2 兜底：CSV 导出 + 运维手动赠送（③，免费版可用 ✅）

- 管理员金数据后台导出 CSV（充值码 + 金额，单次 ≤5000 条）→ 后台手动赠送积分（运维空间）。
- 用于 API 轮询故障时的人工兜底 / 对账。

### 4.3 不可用：Webhook 自动推送（①，免费版不可用 ❌）

- 免费版无「数据推送」开关；专业版 599 元/年起才开「新增数据」推送。**暂不使用**；未来升专业版可平滑切换到 webhook（只新增一个接收端点）。

> **结论**：MVP 用 **4.1 API 轮询** 跑通「支付 → 赠积分」，4.2 兜底；营收上量升专业版后，再切 4.3 webhook。

## 5. 端到端数据流（免费版 API 轮询的完整链路）

```
[taichu 前端] 点「充值」→ POST /api/credits/charge-code → 后端生成充值码(绑定 user_id)
   → 302 跳转 https://jinshuju.net/f/XXXX?code=TC-9F3K2M
[用户] 在金数据选档位(6.9/9.9/19.9/29.9/49.9) → 微信/支付宝支付 → 提交表单
[金数据] 支付成功 → 支付状态/金额/订单号写回表单条目
[taichu 定时任务] 每 5 分钟 API 轮询 get_form_entries → 发现新「支付成功」的充值码
   → 幂等(按 entry_id + 充值码) → 按码找 user_id → recharge → 记流水(type=recharge) → 记埋点 credit_recharge
[taichu 前端] 轮询余额变化 → Toast「充值成功，积分已到账」（最长延迟 ≈ 轮询间隔 5 分钟）
```

## 6. 与积分系统的衔接

- 充值折算：`delta = int(amount * recharge_rate)`，`recharge_rate=10`（1 元=10 积分，存 `system_configs`）。
- 档位金额（金数据表单写死）与 `recharge_rate`（后端）**必须人工一致**；改档位时两处同步。
- 扣费：`check_balance`（预检）+ `consume`（按 `ceil(tokens/1000)` 扣），复用 `docs/架构设计-积分系统开发方案.md`。
- 充值流水类型：金数据自动回调 = `recharge`；免费版手动导出后运维补登 = `manual`。

### 9.4 充值码生成（P1）

```python
# codes.py
def create_code(db, user_id, ttl_minutes=15) -> str:
    code = "TC-" + secrets.token_hex(3).upper()      # 6 位，约 1677 万种
    db.add(RechargeCode(code=code, user_id=user_id, status="unused",
                        expires_at=now + ttl_minutes))
    db.commit()
    return code

def resolve_code(db, code) -> RechargeCode | None:
    """返回 unused 且未过期的码；否则 None。"""
    row = db.query(RechargeCode).filter_by(code=code, status="unused").first()
    if row and row.expires_at > now:
        return row
    return None
```

```python
# router.py —— POST /api/credits/charge-code（需 JWT）
@router.post("/charge-code")
async def charge_code(user_id, db):
    code = create_code(db, user_id)
    return {"code": 0, "data": {
        "code": code,
        "url": f"{settings.jinshuju_form_url}?code={code}",   # 前端 302 跳转
    }}
```

### 9.5 金数据 API 客户端（P2）

```python
# jinshuju.py
async def fetch_entries(page=1, per_page=50) -> dict:
    url = f"{settings.jinshuju_api_base}/forms/{settings.jinshuju_form_token}/entries"
    r = await httpx.AsyncClient().get(
        url,
        headers={"Authorization": f"Bearer {settings.jinshuju_access_token}"},
        params={"page": page, "per_page": per_page},
        timeout=30,
    )
    r.raise_for_status()
    return r.json()   # 形如 {"count": N, "entries": [{...}, ...]}
```

> 字段取值规则（已锁定，实际表单 K4kgC7）：充值码 = `entry["field_1"]`；档位金额 = `entry["field_2"]` 数组里 `number>0` 项的 `price`；支付成功 = `entry["trade_status"] ∈ {TRADE_SUCCESS, MOCK_PAY_SUCCESS}`；幂等主键 = `entry["serial_number"]`；处理状态 = `entry["field_3"]`（可选回写）。

### 9.6 定时轮询 + 幂等充值（P2，核心）

```python
# poller.py
# 支付成功判定集：生产只认 TRADE_SUCCESS；自测阶段额外允许 MOCK_PAY_SUCCESS
PAID_STATUSES = {"TRADE_SUCCESS"}
if settings.jinshuju_allow_mock:            # 生产环境设 False，防止模拟表单白送积分
    PAID_STATUSES.add("MOCK_PAY_SUCCESS")

async def poll_and_recharge(db):
    data = await fetch_entries(page=1, per_page=50)
    for entry in data.get("entries", []):
        serial = entry.get("serial_number")          # 幂等主键（系统字段）
        trade_status = entry.get("trade_status")     # 支付状态
        code = entry.get("field_1")                  # 充值码（field_1）
        items = entry.get("field_2") or []           # 商品档位数组 [{name,number,price}]

        # 1) 判定支付成功：trade_status ∈ 成功集
        if trade_status not in PAID_STATUSES:
            continue
        # 2) 充值码必须有效（unused 且未过期）—— 天然幂等：已 used 的码跳过
        row = resolve_code(db, code)
        if not row:
            continue
        # 3) 金额：从 field_2 数组取 number>0 的那条 price
        paid_item = next((it for it in items if (it.get("number") or 0) > 0), None)
        if not paid_item:
            continue
        amount_float = float(paid_item.get("price", 0))
        # 4) 充值
        delta = int(amount_float * settings.recharge_rate)   # 1 元 = 10 积分
        recharge(db, row.user_id, delta, type="recharge",
                 amount=amount_float, ref=f"serial:{serial}")
        # 5) 标记码已用（防重放，兼作幂等）
        row.status = "used"
        db.commit()
        # 6) 埋点 credit_recharge
        track("credit_recharge", user_id=row.user_id, delta=delta, amount=amount_float)
```

**幂等关键**：`resolve_code` 只认 `unused` 码；充值后立刻置 `used`，同一 `entry` 被重复拉到时 `resolve_code` 返回 None 即跳过，不重复充值。

### 9.7 定时任务启动（APScheduler）

```python
# app/main.py lifespan 内注册
from apscheduler.schedulers.asyncio import AsyncIOScheduler

scheduler = AsyncIOScheduler()
scheduler.add_job(poll_and_recharge, "interval",
                  seconds=settings.jinshuju_poll_interval,  # 300s
                  id="jinshuju_poll", coalesce=True, max_instances=1)
scheduler.start()   # lifespan yield 后 shutdown
```

> `coalesce=True` + `max_instances=1` 防止任务堆积（金数据 100 次/小时配额内，5 分钟一次 = 12 次/小时，远够）。

### 9.8 充值到账的 C 端感知

- 前端充值后：`setInterval` 每 3–5 秒 `GET /api/credits/balance`，检测到余额增加 → Toast「充值成功，积分已到账」→ 停止轮询（超时 10 分钟放弃）。
- 因金数据 API 轮询有 ≤5 分钟延迟，到账**非实时**，前端文案可提示「预计 1–5 分钟到账」。

### 9.10 上线前「钉死」清单（真实收款，必做）

1. **钉死 TRADE_SUCCESS**：上线后第一笔真实收款，拉一次 entry，把 `trade_status` **原样打印并钉进代码注释**——当前判定集 `{"TRADE_SUCCESS"}` 是基于业界 + 金数据历史样本，但**未 100% 实测**，真实值以第一笔为准。
