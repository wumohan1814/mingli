# 架构设计 · 产品化扩展（数据库 / 埋点 / 后台 / 积分 / 错误码）

> 状态：设计稿（未实现）｜ 日期：2026-09-06
> 定位：在 Phase 1–7 已完成的 MVP 主链之上，补齐「可运营、可观测、可收费、可运维」的产品化底座。
> 设计原则：**延续模块化单体 + SQLite 逻辑分库 + FastAPI + 免构建前端**；所有扩展按「最小可用 → 分期增强」，不引入重框架（不用 ClickHouse/Kafka 等，Phase2 再评估）。

---

## 0. 现状基线（扩展的起点）

- 已实现：`taichu_analytics`（10 表）+ `taichu_feedback`（2 表）双库；排盘→断前尘→校准→预测→修正→档案全链路；DeepSeek LLM；异步 jobId。
- 缺口：无埋点、无积分、无后台、错误码零散（`HTTPException` + `detail` 字符串）、数据库未覆盖计费与运维。

## 1. 初期数据库架构

### 1.1 分库策略（延续「逻辑分库」，新增 1 库）

| 库 | 职责 | 现表 | 新增表 |
|---|---|---|---|
| `taichu_analytics` | 用户 / 排盘 / 档案 / **积分** | users、refresh_tokens、login_attempts、cases、charts、method_results、calibrations、conversations、jobs、route_decisions | `credit_accounts`、`credit_transactions` |
| `taichu_feedback` | 跨用户质疑 | feedbacks、feedback_summaries | — |
| `taichu_ops`（新） | **埋点 / 后台 / 错误上报**（运维数据，可单独清理归档） | — | `events`、`admin_users`、`admin_audit_logs`、`error_reports` |

> 理由：埋点与运维数据「写多读少、量大、可丢弃」，与业务库分离便于单独备份/清理；积分是用户核心资产，放 analytics 与 user 同库、同事务。

### 1.2 新增表结构

```sql
-- ===== taichu_analytics：积分 =====
credit_accounts (
  user_id        INTEGER PRIMARY KEY REFERENCES users(id),
  balance        INTEGER NOT NULL DEFAULT 0,   -- 积分余额（整数，1 积分 = N tokens）
  total_consumed INTEGER NOT NULL DEFAULT 0,
  total_recharged INTEGER NOT NULL DEFAULT 0,
  created_at, updated_at
)
credit_transactions (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id   INTEGER NOT NULL,
  delta     INTEGER NOT NULL,                   -- 正=入账（充值/手动/退款），负=消费
  type      TEXT NOT NULL,                      -- consume | recharge | manual | refund
  tokens    INTEGER,                            -- consume 时关联的 token 数
  amount    REAL,                               -- recharge 时关联的充值金额（元）
  ref       TEXT,                               -- 关联键（如 jobId / 小鹅通订单号）
  note      TEXT,
  created_at
)

-- ===== taichu_ops：埋点 / 后台 / 错误 =====
events (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  event_name TEXT NOT NULL,                     -- 如 page_view / case_create / llm_call / error
  user_id    INTEGER,                           -- 可空（匿名访客）
  case_id    INTEGER,
  session_id TEXT,
  props      TEXT,                              -- JSON 负载（字段随事件而异）
  ip         TEXT, user_agent TEXT,
  created_at
)  -- 索引：(event_name, created_at)、(user_id, created_at)

admin_users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  username TEXT UNIQUE NOT NULL, password_hash TEXT NOT NULL,
  role TEXT NOT NULL DEFAULT 'admin',           -- admin | operator | viewer
  created_at, last_login_at
)
admin_audit_logs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  admin_user_id INTEGER, action TEXT,           -- 如 reset_password / edit_prompt / change_api_key
  target_type TEXT, target_id TEXT, detail TEXT,  -- detail JSON
  created_at
)
error_reports (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  error_code TEXT, message TEXT, detail TEXT,
  user_id INTEGER, case_id INTEGER,
  source TEXT,                                  -- frontend | backend
  stack TEXT,                                   -- JSON：堆栈/上下文
  created_at
)
```

### 1.3 数据保存口径（现有表语义固化）

| 数据 | 表 | 说明 |
|---|---|---|
| 用户信息 | `users` + `refresh_tokens` | 密码哈希 + 刷新令牌，不存明文 |
| 排盘结果 | `charts.chart_json` | 全量 chart 落库（唯一事实源） |
| 排盘内容（切片/各法） | `method_results.result_json` + `validation_json` | 按 method_key + phase 分存，缓存复用 |
| 校准 / 对话 / 任务 / 路由 | `calibrations` / `conversations` / `jobs` / `route_decisions` | 幂等落库，进度不只在内存 |

## 2. 完整的产品埋点方案

### 2.1 目标

可回答：**多少人来了、走到哪一步流失、每次算命的 token 成本、哪里报错、各法耗时**。

### 2.2 采集架构（前端 + 后端双通道，统一写 `events` 表）

```
[前端 index.html] --track(event, props)--> POST /api/events （批量、防抖、异步不阻塞）
[FastAPI middleware] --自动记录每个 /api 请求--> events（path/method/status/latency/user_id）
[LLM client]       --每次 chat 成功/失败--> events（llm_call：model/tokens/latency/method_key）
```

### 2.3 核心事件清单

| 事件名 | 来源 | props 关键字段 |
|---|---|---|
| `page_view` | 前端 | page（landing/auth/onboarding/...） |
| `auth_register` / `auth_login` | 后端 | 结果、耗时 |
| `case_create` / `paipan` | 后端 | degraded_methods、chart_version |
| `dqc_start` / `dqc_done` | 后端 | jobId、9 法耗时、失败法 |
| `calibration_submit` | 后端 | feedback 条数、fit |
| `predict_start` / `predict_done` | 后端 | jobId、路由方法、耗时 |
| `revise` / `archive_view` | 后端 | — |
| `llm_call` | LLM client | method_key、model、prompt_tokens、completion_tokens、latency、成功/失败 |
| `error` | 前后端 | error_code、message、context |

### 2.4 埋点数据流与查询

- **写入**：前端 `POST /api/events`（可匿名，带 session_id）；后端 middleware + LLM 自动埋点。
- **查询**：后台报表（见 §3）直接聚合 `events`，MVP 用 SQL 聚合即可（数据量小时）。
- **漏斗**（核心转化）：`auth_register → case_create → paipan → dqc_done → calibration_submit → predict_done`。
- **成本**：聚合 `llm_call` 的 tokens → 对应积分/金额。
- **分期**：MVP 自研 `events` 表 + 简单聚合；数据量上来后再评估 ClickHouse / PostHog / Umami。

## 3. 简单的后台管理系统

### 3.1 定位与边界

- **独立于 C 端**：`/admin/*` 前缀，管理员认证（`admin_users` 表 + 独立 JWT）。
- **前端**：独立 `frontend/public/admin.html`（复用免构建 CDN React 模式，不混入 C 端）。
- **权限分级**：`admin`（全部）/ `operator`（运维，不含 prompt 编辑）/ `viewer`（只读报表）。

### 3.2 功能与实现要点

**(a) 查看埋点报表**
- 路由：`GET /admin/reports/{metric}` → 聚合 `events`。
- 报表项：DAU/新注册、转化漏斗、LLM token 与成本趋势、错误率 Top、各法耗时 P50/P95。
- MVP 直接 SQL 聚合 + 简单图表（Chart.js / 内联 SVG）。

**(b) 执行运维动作**
| 动作 | 路由 | 实现 |
|---|---|---|
| 更换 API key | `POST /admin/ops/llm-key` | 写 `backend/.env` 的 `TAICHU_LLM_API_KEY`（或运行时配置项）+ 记 audit |
| 重置用户密码 | `POST /admin/ops/users/{id}/reset-password` | 重设 `users.password_hash`（临时密码） + audit |
| 重置用户档案 | `POST /admin/ops/users/{id}/reset-case` | 删该 case 的 charts/method_results/calibrations/conversations（保留 user 与积分）+ audit |

> 所有运维动作必须写 `admin_audit_logs`（谁、何时、对谁、做了什么）。

**(c) 查看/修改 method prompt**
- `GET /admin/prompts` 列出 9 个 `method-prompts/*.md`（含修改时间）。
- `GET /admin/prompts/{key}` / `PUT /admin/prompts/{key}` 读写文件。
- 修改后记 audit + 版本（可存 `prompts/method-prompts/.versions/{key}.{ts}.md` 做回滚）。

**(d) 查看用户会话与档案**
- `GET /admin/users?q=` 搜索用户 → `GET /admin/users/{id}/cases` 列 case → `GET /admin/users/{id}/cases/{caseId}` 复用 `build_archive`（chart + 校准 + 对话 + 方法结果）。
- 人工判断错误：对话异常、method-result 空、降级异常 → 标注重跑/修正。

### 3.3 后台鉴权与安全

- `admin_users` 独立于 C 端 `users`；登录走独立 `/admin/login`。
- 后台所有接口强制 `admin_token` + 角色校验；写动作一律 `admin_audit_logs`。

## 4. 积分系统

### 4.1 模型

- **1 积分 = N tokens**（N 为可配置常量，如 `CREDIT_PER_TOKEN = 1000`，即 1 积分 = 1000 tokens；最终按 self-run 成本定）。
- 用户账户 `credit_accounts.balance`；所有变动记 `credit_transactions`（不可变流水）。

### 4.2 计费与扣减流程

```
方法模块/校验/修正 → chat() 返回 usage.total_tokens
  → credit_service.consume(user_id, tokens)
      → delta = -ceil(tokens / CREDIT_PER_TOKEN)
      → 余额不足：抛「积分不足」错误（错误码 5002），该次 LLM 不执行
      → 余额足够：扣 balance + 写 transactions(type=consume, tokens, ref=jobId)
  → 若扣费失败但 LLM 已调用：记 error 事件，进入对账（不吞）
```

### 4.3 充值渠道

| 渠道 | 方式 | 实现 |
|---|---|---|
| 小鹅通充值 | 小鹅通订单回调 webhook | `POST /api/credits/webhook` 验签 → `recharge(user_id, amount)` → 按定价折算积分 + 写 transactions(type=recharge) |
| 手动分发 | 后台运维 | `POST /admin/credits/manual` → `manual` 入账 + audit |

### 4.4 拦截点与提示

- 前端发起任何需要 LLM 的动作前，可 `GET /api/credits/balance` 预检；不足则引导充值。
- 后端在 `chat()` 前做余额校验（硬拦截），返回统一错误码，前端弹「积分不足，去充值」。
- 免费额度：新用户注册赠送少量积分（如 50 积分）做冷启动（可配置）。

## 5. 报错与错误代码体系

### 5.1 统一错误信封（兼容现有 `{code, message, detail}`）

```json
{ "code": 5002, "message": "积分不足", "detail": "余额 3 积分，本次需 12 积分" }
```

### 5.2 错误码分段（1xxx 起，语义化）

| 段 | 含义 | 示例 |
|---|---|---|
| 0 | 成功 | `0` |
| 1xxx | 通用 | `1001 参数错误` `1002 资源不存在` `1003 冲突` `1004 限流` |
| 2xxx | 认证/鉴权 | `2001 未登录` `2002 token 过期` `2003 无权限` |
| 3xxx | case/档案 | `3001 case 不存在` `3002 未排盘` |
| 4xxx | 排盘/方法 | `4001 排盘参数无效` `4002 方法降级` |
| 5xxx | LLM/积分 | `5001 LLM 服务不可用` `5002 积分不足` `5003 计费异常` |
| 9xxx | 系统 | `9000 内部错误` `9001 数据库错误` |

### 5.3 实现

- 后端：定义 `app/errors.py`（错误码枚举 + 异常类 `BizError(code, message, detail)`）；全局 exception handler 把 `BizError`/`HTTPException`/未知异常统一转成 `{code,message,detail}` 信封。
- 前端：`api()` 响应拦截统一处理——按 `code` 映射友好文案（含错误码，方便用户截图反馈）；`9xxx`/`5xxx` 显示「稍后重试」并上报 `error_reports`。
- 维护：错误码文档化（本表即契约），新增错误码须同步，便于后端定位。

## 6. 实施分期（建议）

| 期 | 内容 | 依赖 |
|---|---|---|
| **P1（运营最小闭环）** | ① `taichu_ops` 库 + `events` 表 + 埋点采集（前端 track + 后端 middleware + LLM 埋点）② 统一错误码 + 错误上报 ③ 后台最小版（报表 + 用户档案查看 + prompt 查看/编辑） | 仅需新增表 + 少量路由 |
| **P2（收费闭环）** | ④ 积分（credit 表 + 计费 + 余额拦截 + 手动分发）⑤ 后台运维动作（换 key/重置密码/重置档案） | 依赖 P1 的 ops 库 + 错误码 |
| **P3（自动化/增强）** | ⑥ 小鹅通 webhook 充值 ⑦ 报表可视化增强 ⑧ 埋点迁移评估（ClickHouse/PostHog） | 依赖 P2 |
