# 积分系统 · 开发方案（给研发）

> 状态：开发方案（待实现）｜ 日期：2026-09-06
> 换算：**1 积分 = 1000 tokens**（DeepSeek V4 flash）
> 依赖：`docs/架构设计-产品化扩展.md` 的 §1（表结构）、§4（积分）、§5（错误码）

---

## 1. 概览

把 DeepSeek token 用量抽象为「积分」，用户消耗积分获得 AI 服务；积分未来经小鹅通充值或后台手动分发补充。

- 消耗：所有 **LLM 调用**（断前尘 9 分析+9 校验、预测 5 分析、修正对话、单法直问）。
- 不消耗：排盘（确定性计算）、校准打分（纯代码）。
- 计费粒度：每次 LLM 调用后按 `usage.total_tokens` 扣 `ceil(tokens / 1000)` 积分。

## 3. 数据模型（放 `taichu_analytics` 库）

```python
class CreditAccount(Base):
    __tablename__ = "credit_accounts"
    user_id = Column(Integer, ForeignKey("users.id"), primary_key=True)
    balance = Column(Integer, default=0)          # 当前积分（整数）
    total_consumed = Column(Integer, default=0)   # 累计消耗
    total_recharged = Column(Integer, default=0)  # 累计充值（含手动/赠送）
    created_at / updated_at

class CreditTransaction(Base):
    __tablename__ = "credit_transactions"
    id = Column(Integer, primary_key=True, autoincrement=True)
    user_id = Column(Integer, ForeignKey("users.id"), index=True)
    delta = Column(Integer)          # 正=入账，负=消费
    type = Column(String(16))        # consume | recharge | manual | refund | free
    tokens = Column(Integer)         # consume 时关联 token 数
    amount = Column(REAL)            # recharge 时关联金额（元）
    ref = Column(String(128))        # 关联键（jobId / 订单号）
    note = Column(String(255))
    created_at

class SystemConfig(Base):
    """系统级运营参数（后台可动态改，无需重启）。"""
    __tablename__ = "system_configs"
    key = Column(String(64), primary_key=True)   # 如 recharge_rate / free_credit_on_register
    value = Column(String(255))                  # 字符串存值，读取时按需解析为 int/float
    description = Column(String(255))
    updated_by = Column(String(64))              # 修改人（admin 用户名）
    updated_at
```

> `ensure_schema()` 增补 `ALTER TABLE` 幂等迁移（沿用现有 jobs.result_json 的迁移方式）。
> 初始写入默认值：`recharge_rate=10`（1 元=10 积分）、`free_credit_on_register=100`。

## 4. 模块与文件

```
backend/app/credits/
  __init__.py
  service.py      # 核心：balance / consume / recharge / manual / transactions
  router.py       # C 端：GET balance、GET transactions
  webhook.py      # 小鹅通回调：POST /api/credits/webhook（验签）
admin 侧（并入后台管理）：
  app/admin/credits.py  # POST /admin/credits/manual（手动分发）
```

**核心服务 `service.py` 签名**：
```python
def balance(user_id) -> int                          # 查余额（无则建账户返 0）
def check_balance(user_id) -> None                   # 余额<=0 抛 BizError(5002)
def consume(user_id, tokens, ref=None) -> dict       # 扣 ceil(tokens/1000)，记流水
def recharge(user_id, delta, type, note, amount=None, ref=None) -> dict  # 入账
def manual(user_id, delta, note, admin_id) -> dict   # 手动分发 + audit
def transactions(user_id, limit, offset) -> list     # 流水分页
```

## 5. API 契约

| 方法 | 路径 | 说明 | 返回 |
|---|---|---|---|
| GET | `/api/credits/balance` | 查余额（需 JWT） | `{code:0, data:{balance, totalConsumed, totalRecharged}}` |
| GET | `/api/credits/transactions?limit=&offset=` | 流水（需 JWT） | `{code:0, data:{items:[{id,delta,type,tokens,amount,note,createdAt}], total}}` |
| POST | `/api/credits/webhook` | 小鹅通充值回调 | 验签后 recharge，返回小鹅通要求的 ack |
| POST | `/admin/credits/manual` | 运维手动赠送积分（入参 user_id/delta/note） | `{code:0, data:{balance}}` + 写 audit |
| GET | `/admin/config` | 查看运营配置（含 recharge_rate） | `{code:0, data:{recharge_rate, free_credit_on_register, ...}}` |
| PUT | `/admin/config/{key}` | 修改运营配置（如充值折算率） | `{code:0, data:{key, value}}` + 写 audit |

## 6. 计费流程（扣费点 + 拦截点）

### 6.1 扣费点（共 3 处，均已有 user_id 与 usage）

1. **断前尘编排** `run_duan_qian_chen`：
   - 任务开始：`check_balance(user_id)`（余额不足 → job 直接 failed，error=积分不足）。
   - 任务结束：`consume(user_id, get_usage()["total_tokens"], ref=f"job:{job_id}")`（复用现有 usage ledger）。
2. **预测编排** `run_predict`：同上（开始 check，结束 consume）。
3. **同步端点** `revise` / `query/{method_key}`：
   - 调 `chat()` 前 `check_balance(user_id)`。
   - 调 `chat()` 后 `consume(user_id, resp["usage"]["total_tokens"], ref=...)`。

> 说明：`analyze_method` / `validate` 不感知积分（保持纯函数）；计费统一在编排器/端点层做，避免侵入方法模块。

### 6.2 拦截点

- 后端：`check_balance` 在任何 LLM 调用前执行，余额 ≤0 抛 **5002 积分不足**，前端弹「去充值」。
- 前端：发起断前尘/预测/追问前可先 `GET /api/credits/balance` 预检（可选优化，非必须）。

### 6.3 边界情况

- 一次调用 tokens 超过余额 → 允许扣成负数（`balance` 可为负），下次 `check_balance` 拦截；负余额记为待补（运营可视）。
- 扣费失败但 LLM 已调用 → 记 `error` 埋点事件 + 对账日志，不吞。

## 7. 充值

### 7.1 运维空间 · 手动赠送积分（P2 后台，核心运维能力）
- `POST /admin/credits/manual`：入参 `{user_id, delta, note}` → `manual(...)` → 入账 + 写 `admin_audit_logs`（谁、何时、给谁、送了多少）。
- 定位：运营/客服处理用户投诉、活动补偿、灰度赠送的**统一入口**；允许任意正数积分赠送，不依赖充值渠道。
- 管理侧 UI：后台「积分管理」页 → 查用户余额 → 输入赠送数量 + 备注 → 确认。

### 7.2 金数据充值回调（P2/P3，详见 `docs/架构设计-支付系统-金数据.md`）
- 支付渠道改用**金数据「小金商务助手」**（替代原小鹅通方案）。
- 回调三层降级：webhook 自动推送（付费版）→ API 主动轮询 → 手动导出 + 运维手动赠送（免费版兜底）。
- 用户关联：一次性**充值码**（绑定 user_id，解决非手机号注册）。
- 折算：`delta = int(amount * recharge_rate)`，`recharge_rate` 从 `system_configs` 读取（**默认 10 = 1 元 10 积分，后台可动态改，无需重启**）。

## 10. 测试要点

1. `consume`：tokens=2500 → 扣 3 积分（ceil）；tokens=500 → 扣 1 积分。
2. `check_balance`：余额 0/负 → 抛 5002。
3. 编排：余额不足 → job failed；余额足够 → 任务结束余额减少、流水有 consume 记录。
4. `recharge`/`manual`：入账正确、流水 delta 为正。
5. 注册赠送：新用户注册后 balance=free_credit_on_register。
6. 幂等：webhook 同订单重复回调只入账一次。
