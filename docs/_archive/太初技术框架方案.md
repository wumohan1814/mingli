## 1. 产品目标与硬约束（源自产品规划）

- 形态：仅 H5，不做 APP / 小程序；轻量包装层；每用户独立 session 自主完成。
- 第一阶段主钩子：事业运势（"事业运势趋势参考"），不铺"什么都能算"落地页。
- 部署：香港/新加坡轻节点（免 ICP、低延迟、管辖较宽松）。
- 架构即成本：排盘/演算为确定性计算，本地/边缘执行，**不每次调 LLM**；仅"解读 + 修正对话"调模型。
- 内容定性：命理文化 / 国学运势 / 事业运势趋势；**不承诺结果**；禁医疗 / 投资 / 司法预测。
- 数据资产：独立 session + 生辰 + 历史对话 = 可累积的"命理档案"，是第二阶段横向扩展底座。
- 优先级：先量单位经济（自建闭环 self-run 10×），再定获客与定价（R9 把此闸门前置到开发期）。

## 2. 架构范式（模块化单体 MVP / 微服务就绪，R2 + R6 + R8）

### 2.1 模块总览（服务形态）
从"单体状态机 + 子会话串行"重构为**服务形态模块网格**（MVP 同进程，Phase2 可拆物理服务）：
- **排盘基础模块**（共享、确定性、零 LLM）：封装 `paipan`/`slice`/`score`，供所有方法模块取 `chart.json` + 自己 slice。
- **方法模块（并列，非主/子）**：每个方法论一个模块，**MVP 共 9 个**——8 个命盘类（bazi-pattern / ziwei / xizhan / qizheng / qimen-lifetime / wuyun-liuqi / bazi-dayun-liunian / bazi-shensha-nayin）+ 1 个八字专题（`bazi-hunyin-caiyun`，R15/ADR-0003）+ 未来占卜 / 生肖MBTI / 塔罗；持有自己的 method-prompt，输出 `method-result v2`。
- **校验模块（R14）**：断前尘阶段对每法 `method-result` 做规则性校验，产出 `validation.json`，供 `score.py` 的「命题质量」因子使用。独立模块、8+1 法复用、便宜模型、单独计量。
- **路由模块（ADR-0004）**：阶段 4「主问 → 主/辅方法」决策。**路由表配置化、零 LLM**，决策落 `route_decisions` 表留存。
- **任务模块（R16）**：异步任务编排与进度推进，订阅 `MethodAnalysisCompleted` 更新 `jobs` 表。
- **主模块（可选聚合器）**：收各方法结果 → 按 `score.py` 权重 + 置信档做阶段5 合并裁决 → 吉凶直说。**仅当需跨方法合成时才调用**；单方法直问 bypass 它。
- **用户档案模块 + 质疑模块**：双库读写。
- **合规护栏**：横切，所有模块返回前过输出侧硬过滤。
- **进程内事件分发器**：MVP 模块间通信（接口隔离的 in-process dispatcher）；Phase2 升真实事件总线（Redis Streams / Kafka）。

> 模块边界**严格按微服务形状切**（独立 I/O 契约、独立 `method-prompt`、独立 DB 表/路由），因此 Phase2 拆物理服务 = 把模块"拎"成独立进程，**迁移成本已最小化（非零成本）**。这是 R8 相对"直接真·分布式"的核心取舍：MVP 拿扩展设计红利、避分布式开销；Phase2 迁移仍需处理串行语义变异步、至少一次重投激活、网络超时与重试、跨进程鉴权、链路追踪（迁移清单见 §12.7）。

### 2.2 部署拓扑（MVP 单进程）
```
[浏览器]──HTTPS──▶[静态 H5 / CDN]
                    │  REST/JSON (Bearer JWT)
                    ▼
        ┌──── 单一运行时（模块化单体，MVP）────────────┐
        │ [API 网关 / 鉴权 + 限流 + captcha]            │
        │ [主模块(可选聚合器)]                          │
        │ [方法模块 ×N]（并列，服务形态）               │
        │ [排盘基础模块][用户档案模块][质疑模块]         │
        │ [合规护栏(横切, 内嵌各模块返回前)]             │
        │   ◀── 进程内事件分发器（in-process, 接口隔离）──▶│
        └──────────────────┬───────────────────────────┘
                           │ 落库
                           ▼
        用户分析库（按 user_id 逻辑隔离） + 跨用户质疑库
```
- 主模块与方法模块**解耦**：方法模块只向事件分发器发布结果，不直调主模块；主模块订阅合成。
- 单方法直问路径：`H5 → 网关 → 方法模块X`（不经主模块、不触发其他法的 LLM 调用）→ 先查用户库缓存 → 命中即返（零 LLM）。

|---|---|---|---|

## 3. 核心模块详设

### 3.1 H5 前端
- 建档表单（生辰/性别/出生地/经纬度/真太阳时）；盘面/解读渲染；断前尘批量卡片问卷；多轮修正对话。
- 前端**先不暴露**各方法模块入口（R6④），仅暴露"全盘/事业运势"主路径；单方法直问作为内部能力，Phase2 再开放。

### 3.2 API 网关 / 鉴权（R7 + R10）
- **账户 + 多用户隔离（R7）**：注册=用户名/密码（无手机/微信）；登录后签发 **短访问 JWT（15–30min）+ 刷新令牌（7d）**。
- **令牌模型（C12）**：访问令牌为 JWT（含 `userId`，签名校验、服务端零存储、短命）；刷新令牌为服务端存储的 opaque token（`refresh_tokens` 表，§5.3），可过期/清理，但 MVP 不暴露用户侧吊销端点（改密码/注销留运维进库处理）。`Bearer <访问JWT>` → 网关验签名取 `userId` → `caseId`；无 sticky session，任意实例可验、水平扩展无状态。
- **限流 + 失败锁定（R10）**：登录失败计数（如同用户名 60s 内 ≥5 次失败 → 锁定 15min）；同 IP/账号注册与登录频控，防爆破与机器批量。
- **注册 captcha（R10）**：注册接口加图形/滑块验证，阻断脚本批量注册垃圾账号。
- 路由：全盘走主模块，单方法直问走方法模块；所有写操作强制按 `userId` 行级隔离（§5.3）。
- **多用户隔离实现约束（C20，硬约束，列入 TDD 必测）**：
  1. 网关中间件从 JWT 提取 `userId`，**注入所有模块调用与 DB 查询**；禁止任何绕过 `userId` 作用域的直查。
  2. 数据访问统一走 userId-scoped repository：所有 `SELECT/UPDATE/DELETE` 必带 `user_id` 条件（含 `archive` 派生视图）。
  3. 集成测试（否定用例）：用户 A 持自己 token 请求用户 B 的 `caseId`，必须返 403/404，且日志不泄漏 B 的数据。
- 部署注记（C24）：MVP 为**单进程**部署；JWT 无状态与"任意实例可验"是为 Phase2 水平扩展预留，MVP 阶段仅单实例运行。
- 过期策略：访问令牌短命降低泄露窗口；`/api/auth/refresh` 用刷新令牌换发新访问令牌；MVP 不引入用户侧吊销（R7），刷新令牌服务端可整体清理/过期。

### 3.3 进程内事件分发器（R6，MVP）
- MVP：**同进程 in-process pub-sub**（接口隔离的事件分发器），模块间解耦但不跨网络。
- **至少一次 + 幂等（C25，预防性实现）**：单进程内无网络重投/崩溃重递，MVP 阶段幂等属**防御性预留**；Phase2 升真实总线后重复投递真实发生，幂等才成为必需。去重键 `caseId+methodKey+phase+eventId` 两阶段一致，Schema 不变。
- Phase2 升 Redis Streams / Kafka（分区键=methodKey，保序），**事件 Schema 不变（§5.2）**，仅传输层替换。

### 3.4 排盘基础模块（共享）
- 复用 mingli `scripts/`：`paipan.py` → `chart.json`；`slice_chart.py` → 各方法 slice；`score.py` → 契合度/权重。
- 确定性、零 LLM；所有方法模块调用它取自己 slice（注入边界同 Skill：每法只取自己片段）。

### 3.5 主模块（可选聚合器，R6）
- **职责（R11 / C23，跨方法合成器，两阶段统一）**：
  - **断前尘阶段**：订阅 8 法 `MethodAnalysisCompleted` → 按 `confidence_level` 筛选高置信断言 → 按 `domain` 分组 → 合成 **5–10 条问卷断言**返 H5（对应 §4.1 步骤3）。
  - **预测阶段**：按 `score.py` 权重 + `confidence_level` 做**阶段5 合并裁决**（不投票、不二次解读）→ 发布 `SynthesisCompleted` → 吉凶直说 + 末行免责。
- **聚合等待（C11 + C19，按 phase 区分窗口）**：
  - **断前尘（串行）**：8 法依次完成，主模块在**第 8 个 `MethodAnalysisCompleted` 到达即合成问卷**；窗口放宽至 **5min**，仅作单法卡死保护（超时则已完成法参与合成、缺法标记 `degraded` 并提示）。原统一 60s 与串行总延迟（§11 称"数十秒~分钟"）不匹配，故放宽。
  - **预测（并行扇出）**：等齐主/辅法（或降级集合），窗口 **60s**，超时同上降级。
  - 两阶段均以 `caseId+methodKey+phase+eventId` 幂等去重。
- **仅全盘/多方法场景触发**；单方法直问不调用。

### 3.6 方法模块（并列，R6③）
- 每个方法论一个模块，逻辑一致：订阅 `MethodAnalysisRequested`（含自己 slice + 主问/校准反馈）→ 调 LLM（注入自己 method-prompt）→ 产出 `method-result v2` → **【仅断前尘阶段】经校验模块产出 `validation.json`（R14）** → 发布 `MethodAnalysisCompleted`。**落库由用户档案模块统一负责**（订阅 `MethodAnalysisCompleted` 后写库并发布 `RecordPersisted` 供审计/下游，方法模块无需订阅）；**进度上报由任务模块负责**（R16），方法模块不关心自身序号。
- **校验的必要性（R14）**：`score.py` 的「命题质量」因子占契合度 **30%**，直接读取 `validation.json`；缺失恒取 0.5 会使校准权重失去区分度，削弱「可修正」核心卖点。预测阶段不校验，改用 `confidence_level` 纪律兜底。
- 占卜类（六爻/梅花/大六壬/择日）作为未来方法模块，默认不注册到 MVP 路由。
- 前端不暴露单方法入口（R6④），但模块已独立，Phase2 拆物理服务迁移成本已最小化（C21，清单见 §12.7）。

### 3.7 用户档案模块 + 用户分析库（R6③/⑤）
- 读写用户分析库（逻辑隔离：同库按 `user_id` 分区）。
- 落盘：chart、各法 `method-result`、校准记录、对话、报告；支撑缓存复用（§6）。

### 3.8 质疑模块 + 跨用户质疑库（R6⑥）
- 收集用户在对话中提出的"不准/质疑"反馈 → 写跨用户质疑库。
- 后台周期任务：聚合质疑 → LLM 归纳汇总（按 method / domain）→ 写汇总表 → 供方法迭代（更新 method-prompt / 校准权重）。详见 §5.4。

### 3.9 合规护栏（横切，R5）
- 所有模块返回 H5 前过输出侧硬过滤：禁区/确定结论检测 + 强制末行免责 + 占卜门控。

## 4. 关键流程（事件驱动 + 缓存复用）

### 4.1 首次全盘闭环（七阶段 → 事件流）
1. **建档**：H5 → 网关（验 JWT，user 已注册存在）→ 建 case；缺时辰→前三柱低置信。
2. **排盘**：网关 → 排盘基础模块 → `chart.json` + 8 slice；落用户库；降级法记 `degraded_methods`。
3. **断前尘（异步，R16）**：网关建 `job`（total=9）并**立即返 `202 { jobId }`** → 事件分发器**逐个串行**发 `MethodAnalysisRequested`（各法 slice，等上一法 `MethodAnalysisCompleted` 再发下一法，忠实『严禁并行』控成本）→ **9 个方法模块串行分析**（R15）→ 每法产出结果后**立即串行跑一次校验**（R14）→ 各发 `MethodAnalysisCompleted`（任务模块推进进度、用户档案模块落库）→ **主模块（跨方法合成器，R11/C23）**在第 **9** 个到达即按 `confidence_level` 提取高置信断言、按 domain 分组**合成问卷**（5–10 条；聚合窗口 5min 仅作单法卡死保护，见 §3.5）→ 结果随 `GET /api/jobs/{jobId}` 返回。**H5 以代码轮询拉取进度（零 LLM 调用）**。
4. **问卷+校准**：用户逐条 确认/否认/修正 → 写 `校准记录.json` → 质疑模块记反馈 → 排盘基础模块跑 `score.py` → 权重 → 完备判定（主要方法命中率≥0.7 且覆盖≥3 领域 + 用户确认"盘对了"）才放行（C10）。**不完备兜底（复用 Skill §3.4/§4.7）**：① 用户明说"不用对了，直接看"→ 记"用户放弃对盘"，降置信继续；② 系统性不中（≥半数被否认/修正或"全不对"）→ 触发时辰假设检验（±1 时辰重排对比），仍不中则停"盘对不上"、不得进预测；③ 未满足 → 回修时辰/真太阳时或停在"盘对不上"。
5. **预测（异步，R16）**：**路由模块**按权重+配置化路由表（主法全跑、辅法按主问高相关子问题跑；降级法不得入选；用户点名法强制纳入）选出方法集合并落 `route_decisions` → 网关建 `job` 并**立即返 `202 { jobId }`** → 事件分发器**并行扇出** `MethodAnalysisRequested(phase=prediction)`（主/辅法可并行）→ 各法发 `MethodAnalysisCompleted`（**预测阶段不跑校验**，R14）→ 主模块合并裁决 → H5 轮询取结果。
6. **合并裁决**：主模块订阅 → 阶段5 合并 → `SynthesisCompleted` → 吉凶直说 + 末行免责 → 落用户库。
7. **输出+存档**：H5 渲染；全套落用户分析库。
8. **追问修正**：多轮，增量写对话，不覆盖历史。

### 4.2 单方法直问（bypass 主模块，降 token，R6③/⑤）
`H5 → 网关 → 方法模块X`：**不经事件分发器、不经主模块、不触发其他法**，直接 in-process 调用方法模块X（单进程内无网络跳转；与 §4.1 事件驱动路径并列，两者皆进程内）→ 先查用户库缓存：
- **命中** → 直接返回（零 LLM 调用）；
- **未命中** → 方法模块X 跑 → 落库 → 返回。

### 4.3 质疑反馈流（R6⑥）
对话中用户提"不准" → H5 标记 → 网关 → 质疑模块 → 写跨用户质疑库 `feedbacks` → 后台归纳 → `feedback_summaries` → 方法迭代输入。

### 5.2 事件契约（R6；MVP 进程内分发器，Phase2 升总线，Schema 不变）
```jsonc

- **R14**：`validation` 字段**仅在 `phase=duan-qian-chen` 时有值**；`phase=prediction` 时为 `null`。
- **R16**：新增 `JobProgressed { jobId, caseId, completed, total, status }`，由任务模块订阅 `MethodAnalysisCompleted` 后发布。
- MVP 走进程内分发器（in-process pub-sub）；Phase2 仅替换传输层为 Redis Streams/Kafka，Schema 不变。

### 5.5 契约定义（v2.4 修订，R13/ADR-0001；下方章节号仍指 mingli `SKILL.md`，作为**参考**）

> **归属变更**：原 R4/C1 定为「原样复用 mingli Skill 契约」。v2.4 改为——
> **契约由太初自主定义、兼容 mingli 关键字段；实现全部自研，mingli 仅作参考。**
> 兼容是**选择**而非义务。理由：① 原样复用在执行中已丢失步骤（最典型的是校验被整体省略，见 R14）；
> ② Skill 的文件目录形态与产品化需求（多用户、异步、计量）不匹配；③ 排盘正确性由开源库兜底，
> 自研不会引入历法风险。代价：失去"上游升级自动惠及"，改为人工评估同步；排盘回归基线与
> 案例库锚点由 Phase2 提前到 MVP 必做。

**保留的兼容字段（对照参考）**：
- `chart.json` → Skill §0（session-dir 表）/ §1 / §2（纯代码排盘，唯一事实源）。
- `method-result v2` → Skill §3（阶段 2 契约）：`{method, phase, past_propositions[{year_range,domain,claim,confidence_level,confidence_reason,basis}]}`；预测阶段 `conclusions[].direction ∈ {吉,凶,平}`。
- `confidence_level` 枚举 → Skill §3：`high | medium | low | speculative`（归一映射 high≈0.8 / medium≈0.55 / low≈0.3 / speculative≈0.15，仅内部裁决用，不写回 JSON）。
- `校准记录.json` → Skill §3/§4（`score.py` 读取格式：`{propositions:[{method,domain,claim,feedback:confirmed|denied|corrected}]}`）。
- slice key→字段映射 → Skill §0「8 个命盘类方法注册表」（bazi-pattern / ziwei / xizhan / qizheng / qimen-lifetime / wuyun-liuqi / bazi-dayun-liunian / bazi-shensha-nayin，已与框架 §2.1 逐项核对一致）。
- `score.py` 三因子公式 → Skill §4：契合度 = f(命中率, 命题质量, 依据链完整度)；`weight = 0.4 + 0.6 × 契合度`；无反馈方法权重 0.5。
- 以上为跨模块唯一协商点，**禁止私自改字段**；Skill 升级新增字段（神煞/流月）自动惠及产品（C1 收益）。

### 5.6 新增产品契约
- REST 信封：`{ code, message, data, meta:{caseId,stage,degradedMethods} }`；错误 `{ code, message, detail }`。
- 响应投影裁剪：`chart.json` 全量存内部/DB；REST 按前端所需投影。
- token：访问令牌 **JWT 短命**（含 `userId`，签名校验，服务端零存储）；刷新令牌服务端存储（`refresh_tokens`，可过期/清理）；无 sticky session；网关验签名即信。

```
注入边界（硬）：每法只喂自己 slice + 自己 method-prompt。

## 6. 缓存复用策略（R6⑤，用户点5）

- **缓存键**：`user_id:case_id:method_key:phase:chart_version`。
- **首次全盘（按 phase 各一次，C18 + v2.4 修订）**：断前尘 phase **9 法各跑一次 + 9 次校验**（R14/R15）+ 预测 phase 主/辅法各跑一次（**0 校验**）→ 分别落 `method_results`（用户库，`cached=false`，缓存键含 `phase`）→ 主模块分阶段合成（断前尘问卷 / 预测裁决）→ 落 `calibrations`/`report`。
  - **首跑 LLM 调用次数（v2.4）** = 断前尘 **9 次分析 + 9 次校验** + 预测主辅法数次（事业主问为主 3 + 辅 2）≈ **23 次**；校验用便宜模型折算后约 **15.5 次分析当量**。**原 v2.3 口径（~13 次）已作废。**
- **后续复用**：
  - 同方法再问 → 命中缓存 → 直接返回（零 LLM）；
  - 全盘再分析 → 仅主模块轻组合（各法缓存命中）；
  - 单方法直问 → 直连方法模块，先查缓存，命中即返。
- **失效**：`chart_version` 变（重排/修时辰）→ 该 user 下相关缓存失效重算。
- **收益**：当次高缓存命中 + 同步分析，一次调用完成；后续复用省 token 与延迟。
- **成本闸门联动（R9 + C18 + C22 + v2.4）**：缓存复用是主要降本杠杆；self-run 10× 须同时测【首跑全盘总成本（断前尘 phase + 预测 phase）】与【缓存后边际成本】，**闸门以前者为锚**。
  - **计量口径必须含校验调用**（R14）：分析与校验**分开计量**（校验用便宜模型），否则阈值不可信。
  - 切档机制见 §11。

## 8. 身份与数据资产（R5 + R6 + R7）

- **MVP 多用户隔离（R7）**：账户体系仅用户名 + 密码，无手机/微信绑定；注册即建 `users` 行（`username` 唯一、`password_hash` 用 argon2/bcrypt，不存明文）。
- **鉴权**：登录/注册签发 JWT（含 `userId`，无状态、无 sticky session）；所有写操作经网关按 `userId` 行级隔离，A 用户不可读 B 用户档案。
- **不做找回（R7）**：MVP 无忘记密码通道（无手机/邮箱）；忘记密码由运维进库处理（比对/重置 `password_hash`），不暴露明文。
- **双库**：用户分析库（按 `user_id` 逻辑隔离，跨 case 复用 chart/校准历史）+ 跨用户质疑库（方法迭代底座）。
- 数据资产支撑 Phase2 横向扩展（生肖 MBTI / 塔罗打通）、回访节点（月度运势）、收入化后的 LTV；微信/手机号绑定与邮箱找回留 Phase2。

## 11. 风险与开放问题

- **单位经济（R1/R9/R12，C18/C22）**：8 法断前尘 token 成本高 → **成本闸门前置**：self-run 10× 与开发并行。
  - **闸门口径** = 单 case **首跑全盘总成本（断前尘 phase + 预测 phase），且必须计入校验调用**。
  - **阈值已修订（v2.4）**：原 ¥0.3–0.5/case 基于 ~13 次调用估算；现行口径 ~23 次（≈15.5 次分析当量），
    **建议上修为 ¥0.5–1.0/case**，**待实测校准（TODO｜owner=用户，self-run 后回填）**。
  - **降本杠杆**：① 校验用便宜模型（R14）；② 缓存复用（§6）；③ 路由表裁剪辅法（ADR-0004）；
    ④ 降级链 `COST_GATE_MODE = full → lite → minimal`。
  - **切档机制（R12，手动配置）**：配置项 `COST_GATE_MODE = full（完整断前尘 8 法）｜lite（方案C：2–3 法轻量校准）｜minimal（方案A：仅主法+一轮修正）`；self-run 实测后**由人判定切档**，**不做运行时自动切换**（MVP 最简、无误触发）。降级链：full → lite → minimal。
  - 缓存复用是主要降本杠杆（§6）。
- **事件总线复杂度（R6/R8，C21/C25）**：MVP 用进程内分发器已规避异步/网络跳数/至少一次投递的分布式风险（幂等为防御性预留）；Phase2 升真实总线时须激活幂等/保序，并处理串行→异步语义、重投、网络超时重试、跨进程鉴权、链路追踪（清单见 §12.7）。
- **长时编排（v2.4 已闭环，R16）**：**9 法串行 + 每法校验**可达数分钟 → 已定为 `jobId` + **前端代码轮询**（零 LLM），新增 `jobs` 模块与表；硬超时断前尘 10min / 预测 3min。不再是开放问题。
- **依赖与降级**：占星/七政/奇门/五运六气依赖 `mingyu-core`+经纬度；优雅降级。
- **微信分享**：H5 可能限流/封链 → 不依赖单一通道，裸奔阶段不投重内容资产。
- **LLM 越界**：双层护栏兜底；**案例库回归锚点由 Phase2 提前到 MVP 必做**（R13 代价：自研后失去上游兜底，需自行守住提示词质量）。
- **自研质量风险（R13）**：排盘胶水/切片/打分自研 → 必须建**排盘回归基线**（9 法排盘与切片结果快照进 `tests/fixtures`），引擎升级或逻辑改动需回归通过。
- **校验误报风险（R14）**：校验模型太弱会污染「命题质量」→ 需在 `tests/fixtures` 建校验回归锚点；可通过 `TAICHU_VALIDATION_ENABLED` 整体关闭兜底。
- **账号安全（R7/R10）**：MVP 无找回（运维负担，Phase2 消除）；纯用户名/密码无真人验证 → 已加限流/失败锁定/captcha 防爆破与机器注册；JWT 无吊销，泄露窗口受短访问令牌约束。
- **多用户隔离强度**：用户分析库为逻辑隔离（同库按 `user_id`），应用层必须严格校验每行 `userId`；一处越权即串档 → 需网关/服务层强制注入 `userId` 并单测覆盖（参照 §5.3 注释）。
- **Phase2 拆分成本（R8）**：已用服务形态模块边界最小化；拆物理服务时仍须补齐跨进程鉴权/链路追踪，留 Phase2 实施。
