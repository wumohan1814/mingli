# 太初 · Bug 管理表（Bug Tracker）

> 本表是项目 Bug 的**单一事实源**：所有 Bug（真机走查 / 用户反馈 / 测试 / 代码审查 / 后台 error_reports 等渠道发现）一律在此登记、分配 ID、追踪状态；修复后更新状态与 commit。
> 需求管理见 [需求表.md](需求表.md)（REQ 编号）；Bug 修复涉及新增功能 / 工程改造时按 §4 与需求表联动。
> 每次会话收尾前，将本 session 涉及的新 Bug / 状态变更同步回本表。

## 1. 使用说明

1. **登记**：新 Bug 在 §5 表格新增一行，分配 `BUG-<三位序号>`（全局递增 = 现有最大序号 + 1，不复用、不因关闭而重排）。
2. **状态流转**（颜色体系与需求表一致）：

   | 状态 | 含义 |
   |---|---|
   | 🟡 待办 | 已登记，待复现确认 / 待排期修复 |
   | 🔵 处理中 | 正在修复 |
   | 🟠 待验证 | 修复已提交，等测试验证 |
   | 🟢 已修复 | 修复已验证通过（本地 / 线上回归通过） |
   | ⚪ 已关闭 | 不复现 / 重复 / 明确不修 / 已废弃，须在「备注」注明原因 |

   状态流转：🟡 → 🔵 → 🟠（修复提交待验证）→ 🟢（测试验证通过）。🟢 只能由测试组设置。已关闭 Bug 复发 → 以新 BUG 编号重新登记 🟡，备注关联旧条目。
3. **严重度**：

   | 级别 | 定义 | 处理时限 |
   |---|---|---|
   | S0 致命 | 数据丢失/错乱、安全漏洞、全站或支付不可用、资金相关错误 | 立即 |
   | S1 严重 | 主流程（建档/排盘/断前尘/预测/付费解读）不可用或产出错误 | 当日 |
   | S2 一般 | 功能异常但有绕行，或仅影响单模块/单场景 | 排期 |
   | S3 轻微 | 文案、样式、体验、非关键边界问题 | 择机 |

4. **粒度**：一条 Bug 对应一个可复现的缺陷，不混多件事；同一根因的多个表象可合并为一条并列出全部入口。
5. **查重合并**：登记前先与 §5 全部条目（**含 ⚪ 已关闭**）比对——重复 / 同一根因者**不新增行**：新入口、新复现或补充信息并入已有条目（备注留痕，必要时重新打开状态）；与需求表（REQ）已知待办 / 缺陷重叠时归 Bug 并备注关联对应 REQ，避免同事项在需求表与 Bug 表双行漂移。
6. **可执行性保证**：登记 Bug 的描述须达到「开发可直接开始修复」的粒度——复现步骤含环境与前置条件、现象含报错码 / 文案、期望明确、严重度可判；任一项缺失或表述含糊（无法据此定位 / 复现）时，**先向上报方确认补齐后再登记**，不得凭推断补全。

## 2. 登记字段与填写要求

| 字段 | 必填 | 要求 |
|---|---|---|
| 标题 | ✅ | 一句话现象描述，含模块前缀（例：「星座页：出生表单重复提交会创建两个 case」） |
| 模块 | ✅ | 前端 C 端 / 后端 API / 排盘 / LLM / 积分支付 / admin 后台 / 部署运维 / 文档 |
| 严重度 | ✅ | S0–S3，见 §1.3 |
| 现象 | ✅ | 实际发生什么（含报错文案 / 状态码 / 截图路径） |
| 复现步骤 | ✅ | 最小复现路径：环境（线上 https://mingli.example.com 或本地 :8000）、设备与浏览器、前置条件、逐步操作 |
| 期望 | ✅ | 应该是什么行为 |
| 发现 | ✅ | 日期 + 渠道（真机走查 / 用户反馈 / 测试 / 审查 / 后台 error_reports） |
| 修复 | 修复后 | commit 哈希 + 涉及文件 / 版本 |
| 备注 | 条件 | 根因、关联 REQ/BUG、关闭原因、临时规避方案、待复现标记 |

> **登记模板（用户投喂 Bug 时按此给全即可）**
> 标题｜模块｜严重度｜现象（实际发生了什么）｜复现步骤（环境 + 操作）｜期望｜发现渠道

## 3. 管理流程

1. **登记**：任何渠道发现的缺陷先入表（🟡）。信息不全或不可复现时，备注标「待复现 / 待补信息」并写明最可能怀疑点。
2. **排期与处理**：按严重度定优先级；修复须遵循仓库规范——前端改动后跑 `node frontend/scripts/precompile.js` 校验预编译（守护 `<script type="text/babel">` 红线）；改接口 / 表结构先读 `docs/standards/03-接口与数据字典.md`；改动走 commit。完成后填「修复」列并置 🔵。
3. **验证与关闭**：回归验证通过 → 🟢；不通过退回 🔵。确定不复现 / 重复 / 不修 → ⚪ 并注明原因。
4. **发布留痕**：每次发布将本次已 🟢 的 Bug 汇总进 `docs/standards/05-版本迭代记录.md` 的 `### Fixed`。

## 4. Bug ↔ 需求联动

- Bug 修复若同时需要**新增用户可感知功能或明确工程改造** → 先在 [需求表.md](需求表.md) 登记 REQ，Bug 行备注「关联 REQ-xxx」。
- 新需求 / 重构上线后引发的回归缺陷 → 在本表登记 BUG，对应需求行备注「回归见 BUG-xxx」。
- 线上 S0/S1 事故复盘产出的改进项 → 记入需求表或本表，双向留痕。
