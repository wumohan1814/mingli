# 文档模板 · 需求表与 Bug 表

> 定位：需求与 Bug 的**单一事实源**，两份表互为联动。
> 规则摘要：全局递增编号、查重合并、可执行性保证、状态机纪律、🟢 仅测试组可设。

---

## 一、需求表模板

```markdown
# {{项目名}} · 需求表（Requirement Tracker）

> 本表是项目需求的单一事实源：新需求在此登记、分配 ID、追踪状态；开发按表推进，完成后更新状态。
> 每次会话涉及的新需求 / 状态变更，收尾前同步回本表。

## 使用说明
1. **登记**：在对应模块新增一行，分配 `REQ-<三位序号>`（全局递增 = 现有最大序号 + 1，不复用）。
2. **查重合并**：登记前与全表比对；重复 / 高度相似不新增行，并入已有条目（保留原 ID，备注注明"并入于 <日期>：<新增点>"）；部分重叠拆并入最贴近条目或交叉引用。
3. **状态**：🟡 待办 · 🔵 进行中 · 🟠 待验收 · 🟢 已验收 · ⚪ 已归档。
4. **优先级**：P0 阻塞 / P1 高 / P2 中 / P3 低。
5. **粒度**：一条需求对应一个可验收的用户可感知功能或明确的工程改造，不混多件事。
6. **状态流转**：🟡→🔵→🟠→🟢（或 ⚪）。🟢 只能由测试组验收通过后设置；开发完成置 🟠 并备注"待验收"。
7. **可执行性保证**：需求须达"开发可直接照做"——明确动作主体与范围 + 可验收口径（期望行为 / 通过标准）；含糊、缺口径、多义先向需求方确认补齐再登记。
8. **口径演进 supersede**：新需求覆盖旧口径时优先"新行取代 + 旧行保留为历史 + 备注互链（取代 / 取代自 / 被 REQ-xxx 覆盖）"，不删改已验收原文；口径演进导致返工 → 状态退回 🟡/🔵 并注明"返工待开发"。
9. **编号协调**：编号由唯一协调者（需求管理员）统一发放；登记前 grep 现用最大号；撞号冲突顺延并双向留痕；定期审计编号唯一性。
10. **状态与备注联动**：写"已实现 + commit"须同步状态列 🟡→🟠；每次修订后 grep 自检状态列与备注一致；🟠 只挂"已实现待验收"。
11. **派生只读产物（可选配套）**：可配程序生成"状态一览 + CSV 快照"（如 `tools/gen_ledger_snapshot.py`，纯标准库解析 `|` 结构）：md 仍是唯一事实源，产物带生成时间戳 + 一致性校验（重复编号 / 空状态 / 未知状态 → 警告）并标"勿手改"；改源表后重跑刷新。

## 分模块需求登记
### A. <模块名>
| ID | 需求 | 优先级 | 状态 | 备注 |
|---|---|---|---|---|
| REQ-001 | <可验收的功能描述，含范围与验收口径> | P1 | 🟡 | <关联 REQ / 口径演进 / 实现 commit / 待验收> |

## 变更记录
| 日期 | 变更 |
|---|---|
```

> 注：模块名按项目实际划分，如"核心主线 / 付费 / 后台与运维 / 体验优化 / 待办"。

## 二、Bug 表模板

```markdown
# {{项目名}} · Bug 管理表（Bug Tracker）

> 本表是项目 Bug 的单一事实源：所有 Bug（真机走查 / 用户反馈 / 测试 / 审查 / 线上错误报告）一律在此登记、分配 ID、追踪状态。
> 需求管理见需求表（REQ）；Bug 修复涉及新增功能时与需求表联动。

## 1. 使用说明
1. **登记**：新 Bug 新增一行，分配 `BUG-<三位序号>`（全局递增，不复用、不因关闭重排）。
2. **状态流转**：
   | 状态 | 含义 |
   |---|---|
   | 🟡 待办 | 已登记，待复现确认 / 待排期 |
   | 🔵 处理中 | 正在修复 |
   | 🟠 待验证 | 修复已提交，等验证 |
   | 🟢 已修复 | 修复已验证通过 |
   | ⚪ 已关闭 | 不复现 / 重复 / 不修 / 已废弃（备注注明原因） |
   🟡→🔵→🟠→🟢；🟢 仅测试组可设；已关闭复发以新编号重新登记 🟡 并备注关联旧条目。
3. **严重度**：
   | 级别 | 定义 | 处理时限 |
   |---|---|---|
   | S0 致命 | 数据丢失 / 错乱、安全漏洞、全站或支付不可用、资金相关 | 立即 |
   | S1 严重 | 主流程不可用或产出错误 | 当日 |
   | S2 一般 | 功能异常但有绕行，或仅单模块 / 单场景 | 排期 |
   | S3 轻微 | 文案、样式、体验、非关键边界 | 择机 |
4. **粒度**：一条 Bug 对应一个可复现的缺陷，不混多件事；同根因多表象可合并并列出全部入口。
5. **查重合并**：登记前与全表（含 ⚪ 已关闭）比对；重复 / 同根因不新增，并入已有条目（备注留痕）；与需求表重叠归 Bug 并备注关联，避免双行漂移。
6. **可执行性保证**：描述须达"开发可直接开始修复"的粒度；缺复现 / 期望 / 严重度先向上报方确认再登记。
7. **编号协调**：编号由唯一协调者（需求管理员）统一发放；登记前 grep 现用最大号，撞号顺延双向留痕（同需求表）；登记注明证据来源（已核实 / 待复现 / 待确认）。

## 2. 登记字段
| 字段 | 必填 | 要求 |
|---|---|---|
| 标题 | ✅ | 一句话现象描述，含模块前缀 |
| 模块 | ✅ | 前端 / 后端 / ...（项目实际模块） |
| 严重度 | ✅ | S0–S3 |
| 现象 | ✅ | 实际发生什么（含报错文案 / 状态码 / 截图路径） |
| 复现步骤 | ✅ | 最小复现：环境 + 设备 + 前置 + 逐步操作 |
| 期望 | ✅ | 应该是什么行为 |
| 发现 | ✅ | 日期 + 渠道 |
| 修复 | 修复后 | commit 哈希 + 涉及文件 / 版本 |
| 备注 | 条件 | 根因、关联、关闭原因、临时规避、待复现标记 |

> 登记模板（用户投喂 Bug 时按此给全即可）：
> 标题｜模块｜严重度｜现象｜复现步骤（环境 + 操作）｜期望｜发现渠道

## 3. 管理流程
1. 登记（🟡，信息不全标"待复现 / 待补信息"）。
2. 排期处理：按严重度定优先级；遵循仓库规范；完成后填"修复"列并置 🔵。
3. 验证关闭：回归通过 → 🟢；不通过退回 🔵；不复现 / 重复 / 不修 → ⚪ 注明原因。
4. 发布留痕：已 🟢 的 Bug 汇总进版本迭代记录。

## 4. Bug ↔ 需求联动
- Bug 修复需新增功能 / 工程改造 → 先在需求表登记 REQ，Bug 备注"关联 REQ-xxx"。
- 新需求上线引发回归 → 登记 BUG，需求备注"回归见 BUG-xxx"。
- 线上 S0/S1 事故复盘改进项 → 记入需求表或 Bug 表，双向留痕。

## 5. Bug 登记表
| ID | 标题（模块·现象） | 严重度 | 状态 | 发现（日期·渠道） | 修复（commit/版本） | 备注（根因/关联/关闭原因） |
|---|---|---|---|---|---|---|
| BUG-001 | | S2 | 🟡 | 日期·渠道 | | |

## 6. 变更记录
| 日期 | 变更 |
|---|---|
```
