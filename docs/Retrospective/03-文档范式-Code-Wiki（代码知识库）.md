# 文档范式 · Code-Wiki（代码知识库）

> 定位：项目的**常驻代码地图 + 排查手册**——覆盖整体架构、模块职责、关键类与函数、数据模型、依赖关系与运行方式，供**新成员 / 新 Session 上手、跨模块协作、问题排查**使用。
> 一句话：交接文档是"时点快照"（现在到哪、下一步谁做），复盘是"事后经验"（踩了什么坑），**Code-Wiki 是全程常驻的"代码在哪、怎么流转、去哪排查"**。
> 开工阅读顺位：AGENTS → 交接文档 → Code-Wiki → 源码。

## 1. 与相邻文档的分工（防双源漂移）

| 文档 | 它写什么 | Code-Wiki 不重复什么 |
|---|---|---|
| 架构设计 / ADR | 形态与**决策**（为什么这样、技术路线） | 只引用 ADR 索引，不重述决策理由 |
| standards/03 接口与数据字典 | **对外契约**（端点字段 / 表结构 / 缓存键） | 模块职责地图可列"有哪些端点"，字段级契约引用 standards/03 |
| standards/01 命名约定 | 命名规范 | 不复制规范正文 |
| 交接文档 | 时点状态 / 待办 owner / 护栏 | 不写进度；只写稳定的代码事实 |
| AGENTS（统一守则） | 行为准则 + 项目红线速记 | 红线**引用** AGENTS / standards，不整段复制（防双源） |

> 原则：**职责地图归 Code-Wiki，接口契约归 standards，形态与决策归架构 / ADR，红线归 AGENTS 与 standards**——各写一处，Code-Wiki 只做"索引 + 地图"，避免同一事实多处漂移。

## 2. 规则

1. **以源码为准**：头部固定标注"最后更新：<日期> ｜ 以源码为准（<权威代码根>）"；正文与源码冲突时以源码为准并修正文档。
2. **何时建**：项目搭建骨架时建空 Wiki（见 `08-启动检查清单.md`），首个模块落地后开始填充。
3. **何时更新（触发点）**：①新模块 / 新端点 / 新目录落地；②大重构（拆分 / 合并 / 迁移）；③运行方式变化（启动步骤、环境变量、部署）；④每轮 session 收尾顺带核对"职责地图是否与本次改动一致"。**代码落地即更新，不留到"以后补"**（否则与复盘"占位符长期裸露"同病）。
4. **维护方**：写代码的角色（主开发及其子代理）；测试组 / 需求管理发现问题只登记，不直接大改职责事实。
5. **供谁读**：新成员 / 新 Session 接手必读；排查问题时先查 Wiki 定位模块，再读源码。
6. **防漂移检查项**：改动涉及模块/端点时 grep 本 Wiki 对应小节同步；关键路径写后验证存在性；红线 / 契约类内容只引用不复制；"最后更新"日期随每次更新刷新。

## 3. 模板骨架

```markdown
# {{项目名}} · Code Wiki

> 本文档是 {{项目名}} 的代码全景 Wiki，覆盖整体架构、模块职责、关键类与函数、数据模型、依赖关系与运行方式。供新成员上手、跨模块协作与问题排查使用。
>
> 最后更新：<日期> ｜ 以源码为准（<权威代码根，如 backend/app/ + frontend/public/>）

## 目录

1. 项目概览
2. 技术栈与目录结构
3. 整体架构与请求流转
4. 核心模块职责
5. 数据模型与数据库
6. 关键类与函数说明
7. 核心业务流程
8. 依赖关系
9. 配置与运行
10. 关键约束与红线
11. 附录：ADR 决策记录索引

## 1. 项目概览
- 一句话定位（产品做什么、主钩子 / 主流程）。
- 业务形态 / 核心能力 / 变现方式（如有）一览表。
- 核心设计理念 2–5 条（如"确定性计算零 LLM，LLM 只做解读""模块化单体按微服务形状切分"）。

## 2. 技术栈与目录结构
### 技术栈
| 层 | 技术 | 说明 |
|---|---|---|
### 目录结构
```text
<仓库>/            # 目录树；标注：权威运行件（入口）、参考件（不参与运行）、git 忽略区
├── backend/
│   ├── app/       # 应用主体（模块划分）
│   └── ...

│   └── ...

└── ...

## 3. 整体架构与请求流转
- 分层示意（ASCII / 图表）：前端 → 网关 / 中间件 → API 路由 → 业务编排 → 数据层 → 外部依赖。
- 应用启动生命周期（按顺序列启动动作，尤其迁移 / 常驻进程 / 轮询任务 / 关停清理）。
- 请求处理流程（鉴权注入、统一错误信封、路由回退规则）。

## 4. 核心模块职责
- **API 路由层**：`路由文件 | prefix | 职责` 表（一行一个端点族）。
- **每核心模块**：`关键文件 | 职责 | 关键入口函数/类`（可附一小段机制说明，如并发控制、扣费账本隔离、原子推进度）。
- 方法 / 插件类多实例模块：给注册清单（key 列表）+ 一个代表实例的薄封装示例。

## 5. 数据模型与数据库
- 库 / schema 划分表（各库职责）。
- 核心 ORM 模型：`模型 | 库 | 关键字段/关系 | 说明`（或"看源码 + standards/03"的索引，避免全量复制）。
- 关键索引 / FTS / 迁移机制说明（以源码为准）。

## 6. 关键类与函数说明
按域组织（入口与配置 / 核心链路 / 横切），每条：`符号 | 所在文件 | 职责 | 关键行为/契约`。
> 粒度到"排查能定位"即可，不逐行注释；详细实现以源码为准。

## 7. 核心业务流程
- 主链路（用户主线）：逐步列后端阶段与前端步骤。
- 扩展 / 支线流程。
- 异步任务轮询 / 续跑机制。

## 8. 依赖关系
- 内部模块依赖（核心链路方向图 / 文字链）。
- 外部依赖表：`依赖 | 用途 | 来源（pip/node/system/HTTP）`。
- 提示词 / 配置文件依赖（目录 + 用途 + 数量，若为运行关键）。

## 9. 配置与运行
- 环境变量表：`变量 | 默认 | 说明/必填`（敏感项标注"只走 env，严禁硬编码"）。
- 本地启动步骤（装依赖 → 配 env → 启动 → 访问入口）。
- 测试命令 / 一键回归 / 部署方式（指向部署文档，不复制全文）。

## 10. 关键约束与红线
> 只列**指向**（引用 AGENTS / standards 对应节），或抄最关键的 3–5 条纯代码约束（如"入口唯一、某目录不参与运行"）并注明出处——不整段复制红线清单。

## 11. 附录：ADR 决策记录索引
| ADR | 标题 |（列表，指向 adr/ 目录）
```

## 4. 在文档迭代闭环中的位置

```
建项（08：搭骨架，含 Code-Wiki 空壳）
  → 需求/Bug 驱动（07）→ 开发按 AGENTS 落地
  → 代码落地同步更新 Code-Wiki（职责地图）＋ standards（契约/规范）
  → session 收尾：交接文档（05 时点快照）
  → 里程碑后：复盘（抽象经验 → Retrospective）
  → 新 session 开工：AGENTS → 交接 → Code-Wiki → 源码
```

> Code-Wiki 是**穿越交接与复盘之间持续存在的活文档层**：交接可能过时、复盘是回望，只有代码地图跟得上代码本身——它让"新 session 从零啃源码 / 重复排查"这件事消失。
