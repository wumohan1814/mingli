## 1. 文档生命周期约定（交付物中心 → 接入 → 归档）

- **背景**：跨 Session 生产中，文案/美术交付物与在用文档混放，docs 顶层目录膨胀、索引失守，检索成本上升。
- **现象**：交付物（美术回执、文案 JSON、旧方案）散落在 docs 顶层与子目录，已接入的素材与待接入的混在一起，README 索引与实际结构脱节。
- **根因**：缺少「交付物 → 接入 → 归档」的明确流转位置与约定，各 Session 各放各的。
- **方案（需求方拍板，2026-09-09）**：
  1. `docs/exchange/`（交付物中心）：只放**跨 Session 交付、待检查/待接入**的产物（当前：名词白话卡 6 套 JSON）；生产方交付先进这里，开发接入后移出归档。
  2. 协作协议 / 指南等**在用文档回归 docs 主目录**；复盘与 Agent 资产回 `docs/retrospective/`。
  3. **已使用完的素材 → 归档 `docs/_archive/`**（美术回执×3、已接入文案、已上线方案等）。
  4. README 索引重写并写明该套规则；各 Agent 守则的路径引用同步更新。
- **规则**：①生产方交付 → `docs/exchange/`（待接入）；②开发接入完成 → 移出并归档 `docs/_archive/`；③开发中发现**文档过时或已使用完** → 按此约定归档，不留在顶层；④README 索引随结构变更同步。
- **落地检查项**：新交付物先进 exchange；接入后归档；文档索引与实际结构一致；过时文档不进顶层。

## 2. 方案先行 + 待确认单（大需求交互确认模式）

- **背景**：REQ-126（国学导航分层重构）是信息架构级大改，直接编码风险高、返工代价大；需求方明确不懂代码。
- **现象**：若不经确认直接实现大需求，入口布局/数据源/路由等决策点容易做偏，测试验收时整块退回。
- **根因**：交互形态、数据源取舍、范围边界这类"决策点"未在编码前收敛。
- **方案（需求方明确认可此方式有效，并写入工作守则）**：
  1. **先产出方案文档**（现状盘点 + 目标架构 + 迁移映射 + 影响面 + 风险点），附「待确认单」——每项待确认**带默认建议 + 一句话后果**。
  2. 需求方逐项拍板（可整体"按默认"）→ 再进入编码。
  3. 面向需求方沟通**一律大白话**（业务视角讲"改了什么/影响什么/要你定什么"，不堆代码/文件/技术术语）。
- **规则**：涉及交互形态/数据源/范围边界的大改动，先方案后代码；待确认单必须带默认建议；对非技术需求方用业务语言。
- **落地检查项**：大需求编码前有已确认方案；待确认单每项有默认建议；沟通无技术术语堆砌。

## 3. 子代理"半成品失败"的收口处理

- **背景**：多轮委托中，子代理完成全部实现但最终态标记 failed（subagent-2 / subagent-19 两次）。
- **现象**：子代理返回 `failed, error` 且无输出，但 `git status` 显示目标文件已被大改——实现完整，仅因最后门禁/环境步骤失败被标记。
- **根因**：门禁（pytest mkdtemp 沙箱限制、管道被禁）或收尾步骤失败，子代理整体标记失败，掩盖了已完成的实现。
- **方案**：失败后**先查 `git status` / `git diff --stat` 判断是否留下可用产出**；若实现完整，主 Session 自行跑门禁验证 → 收口提交，不盲目重派；若残缺/偏离，按偏离项 review 后决定保留或返工。
- **规则**：子代理失败 ≠ 全盘重来；先盘产出再决定收口或重派；对"额外修复/偏离"项必须读码复核。
- **落地检查项**：failed 子代理先看 diff 规模与内容；门禁由主 Session 复跑确认；偏离项复核后保留。

## 4. 沙箱环境下的测试门禁（pytest / 管道限制）

- **背景**：本开发环境为沙箱（workspace-write / danger-full-access 切换），pytest 与管道命令受限制。
- **现象**：pytest 在受限沙箱下 215 项全 ERROR（`unable to open database file`）；带管道的命令（`cmd | Select-Object`）被沙箱直接拒绝。
- **根因**：①pytest 测试库经 `tempfile.mkdtemp` 建于临时目录，沙箱拒绝写 mkdtemp 目录；②沙箱拦截"捕获子进程输出"的管道。
- **方案**：①pytest 需在 `danger-full-access` 权限下运行（当前会话已是）；②或用 `$env:TMP` 指向工作区可写目录重试；③门禁命令**不带管道**直跑，让 harness 捕获 stdout。
- **规则**：门禁命令不写管道；pytest 遇 mkdtemp 问题用 TMP 指工作区或提升权限；子代理 spec 中预告此环境限制。
- **落地检查项**：pytest 全绿（当前仅余 1 项 fixture 锚点既有失败，见 §6）；门禁输出可读。

## 5. 与需求方沟通（大白话）守则

- **背景**：需求方明确"不懂代码和结构"，且认可"方案先行 + 待确认单"交互方式。
- **现象**：技术汇报（组件名/接口/术语）对非技术需求方不可读，决策效率低。
- **根因**：缺少面向非技术方的沟通口径。
- **方案**：已写入 `agents.md`「与需求方沟通准则」——业务视角讲"改了什么/影响什么/要你定什么"，每项待确认带默认建议；技术点出现先一句大白话解释。
- **规则**：面向需求方一律大白话；待确认单带默认建议；用户认可的方式保持。
- **落地检查项**：汇报无裸技术术语；每项待确认有默认建议。

## 6. 排盘回归 fixture 基线滞后（既有遗留）

- **背景**：`test_fixture_snapshot_anchor` 在本轮多次开发中持续失败（pytest 长期 "1 failed"）。
- **现象**：快照 fixture `chart.json` 的 `western.summary.patterns[0]` 为英文，当前排盘引擎输出中文（西占盘型文案本地化后快照未同步）。
- **根因**：排盘中文化改动（历史批次）后未重生成 fixture 基线；与各开发批次均无关（git stash 隔离验证为既有失败）。
- **方案**：属已知遗留（BUG-007 关联待办）——需测试组或开发在某轮**重新生成 chart.json 快照基线**并核对中文化口径；不属本轮各功能开发引入。
- **规则**：引擎输出口径（语言/结构）变更时，必须同步重生成排盘回归基线；发现 fixture 漂移单独建账，不混入功能批次。
- **落地检查项**：pytest 无"1 failed 长期滞留"；fixture 与引擎口径一致。
