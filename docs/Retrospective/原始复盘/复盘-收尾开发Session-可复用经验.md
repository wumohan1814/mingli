## 二、经验清单

### A. 协作协议（踩坑代价最高，排最前）

**A1. 多角色并行改同一文件必然冲突**
- 现象：开发（我）+ 测试组同时改 `test_admin_prompts.py`；不同 Session 反复把单文件 SPA 的 `<script>` 误改成 `<script type="text/babel">`；edit 工具频繁报「file changed since read」；共享台账 .md 被并发写触发 Windows EIO。
- 根因：多 Session 共享同一工作区与同一单文件真相源（巨型 index.html、需求/Bug 台账），无同步节奏。
- 可复用规则：
  1. **单文件真相源必须串行**；多人要改同一文件时，先约定「commit → push → pull 一版」的检查点节奏。
  2. 编辑前检查文件 mtime/内容；edit 被拒 = 有并发写者，**重新 read 再改**，勿强行覆盖。
  3. 只 `git add` 自己本次改的文件，用显式 pathspec，绝不 `git add -A`（会把并行者的 untracked/M 改动卷进来）。
- 落地检查项：
  - [ ] 开工前 `git status` 全量盘一遍，识别哪些 M/untracked 是并行者的（不碰）。
  - [ ] 每个 commit 前再次 `git status`，确认只含本任务文件。
  - [ ] 与并行者同文件时，高频 push+pull，并保留自己文件的本地副本做 diff。

**A2. 角色/职责边界误判 → 整批需求遗漏（代价最高之一）**
- 现象：我假设「UI/交互改版归 UI 组」，实际 UI 组只产美术素材；UX 路径落实（方向→问题→牌阵链路、entry 扇形、全宽按钮、档案改版等 7 项）是我与子 Agent 的职责，用户澄清前全部未做，测试组大量不合格。
- 根因：交付文档里「组件/交互规范」与「美术素材」混在一起，我误读了「✅ 可生产」= UI 组已实现，实际是「可交给开发落地」。
- 可复用规则：**「谁产出元素」≠「谁落地到代码」**。拿到交付文档先确认「哪部分是别人已入库的产物、哪部分是需要我实现的设计规范」，逐条列责任矩阵再开工。
- 落地检查项：
  - [ ] 交付物清单里每一项，标注「已入库 / 待我实现 / 待他人实现」，歧义先问需求方。
  - [ ] 排期时把「设计规范 → 代码实现」的空档显式列出，不默认有人已做。

**A3. 测试组的测试文件是活的，不是只读**
- 现象：untracked 的测试文件在我读完后被测试组改写（路径穿越用例从 `../../etc/passwd` 改成 `not-a-key`、版本不存在期望从 404 改成 400），我的修复方向因此反了一次。
- 根因：测试文件未 commit、测试组仍在迭代，我基于旧快照做契约判断。
- 可复用规则：读测试/契约文件后，**跑之前再 re-read 一遍**；发现「我的实现 vs 测试期望」矛盾时，先确认测试文件是不是最新，再动实现。
- 落地检查项：
  - [ ] 全量 pytest 前 `git status` 看测试文件是否被并行改动。
  - [ ] 单测失败先区分「测试隔离缺陷」（共享库 + 固定 key 跨用例残留）与「真实契约不符」，前者补清理 fixture，后者才改实现。

**A4. push/部署是异步、需协调的动作**
- 现象：git push 网络 flapping（proxy `192.168.31.55` vs direct 反复切换）；SSH 部署 docker build 中途超时断连；服务器跑旧代码导致测试组复验全错。
- 根因：push 依赖用户开 VPN、服务器部署依赖网络与镜像构建，均非我单方可控。
- 可复用规则：
  1. push 前先确认「需要谁批准/开网」；失败按 proxy/direct 轮流重试，仍败就**明确报告待用户开网**，不空转。
  2. 长构建用 `nohup ... > log &` 后台 + 轮询日志，不用前台 SSH 长命令。
  3. 部署后必须验证链：health + 首页 200 + 用 token 冒烟接口，确认「线上=最新 commit」再宣布完成。
- 落地检查项：
  - [ ] 部署脚本带产物验证（curl health/关键端点）。
  - [ ] 服务器 git log 与远程一致后再 build，避免 build 了旧代码。

### B. 架构设计（按代价高到低）

**B1. 配置/常量名映射陷阱：pydantic-settings 字段名 ≠ 环境变量名**
- 现象：字段 `agent_api_token` 期望读 `TAICHU_AGENT_TOKEN`，实际默认映射为 `TAICHU_AGENT_API_TOKEN`（多了 API），线上 Agent 通道 401 半小时才发现。
- 根因：默认 env 映射 = `env_prefix + 字段名大写`，带 `api` 字样的字段名与注释里的目标名不一致。
- 可复用规则：凡字段名含「缩写拼接」都可能映射错，**显式 `Field(validation_alias="<确切环境变量名>")`**；并加本地 `ENV=xxx python -c "from config import settings"` 断言。
- 落地检查项：
  - [ ] 新增 settings 字段必写 validation_alias + 本地环境变量断言测试。
  - [ ] 部署后先容器内 `printenv` + `settings.xxx` 双重核对再宣布启用。

**B2. SPA catch-all fallback 吞掉 API/admin 的 404**
- 现象：为分享链接加「404 回退 index.html」后，`/admin/prompts/../../etc/passwd` 等非法路径返回前端页面 200，测试断言炸。
- 根因：fallback 未排除 `/api/*` 与 `/admin/*` 前缀。
- 可复用规则：静态 SPA fallback 必须保留后端路由前缀的 404 语义（api/admin 前缀除外），否则路径穿越/非法 key 校验形同虚设。
- 落地检查项：
  - [ ] fallback 里排除所有已注册 API/后台前缀，并加「非法 key 返回 4xx 而非 200 HTML」的测试。

**B3. 巨型单文件前端（无构建）的工程约束**
- 现象：7300+ 行 precompiled React.createElement 单文件，多个 UX 改动串行排队；文案 72 篇内联注入引入 CRLF/LF 混乱；一个括号缺失让子代理卡死循环。
- 根因：无构建、单文件、precompiled 风格 → 所有改动收敛一处，语法错误整页白屏。
- 可复用规则：
  1. 单文件改造必须**串行 + 每步语法自检**（提取主 script → `new Function()` 编译）。
  2. 数据注入用脚本做「与源 JSON 逐字比对」校验，防转义/换行污染。
  3. 前端约定红线（禁 JSX、标签保持 `<script>`）写进每个子任务 spec。
- 落地检查项：
  - [ ] 前端改动统一入口跑一次语法门禁。
  - [ ] spec 里显式声明「禁 JSX / 标签类型」红线。

**B4. 幂等 + 缓存命中是数据型功能的默认设计**
- 现象：星座星盘重复生成、MBTI 分享历史不覆盖、档案查看星盘要求重新生成——三处都靠「幂等键复用 / 缓存命中」修复。
- 根因：早期只做了「写 + 读」，没按「同一实体多入口」设计复用。
- 可复用规则：凡「同一逻辑实体可被多入口触发」的功能（生成盘/判型/分享链接），默认设计幂等键（user+entity+scope）与缓存复用，接口天然可重入。
- 落地检查项：
  - [ ] 新增创建型接口先答「重复调用会怎样」，应有幂等语义或明确报错。
  - [ ] 前端多入口（档案/模块页/菜单）共用同一后端数据时，配直达 + 自动加载，不留「手动重新生成」断点。

### C. 工作定义（按代价高到低）

**C1. goal 工具自动续跑会脱离人工节奏**
- 现象：goal 连续 30 轮「等待子代理→报告→再等」自我循环，无实质进展还持续空转，用户中断叫停。
- 根因：把「长目标」交给自动 continuation，但推进依赖外部（子代理、push 批准、测试组），自动轮只产生噪音。
- 可复用规则：**等待外部依赖的轮次不交给自动 goal**；goal 用于「我能持续推进的里程碑」，依赖用户/他方的步骤显式停下等指令。
- 落地检查项：
  - [ ] 创建 goal 前评估「每轮我是否都能独立推进」；不能则不用自动续跑。
  - [ ] 连续 N 轮无代码/无验证产出即自检是否空转。

**C2. 子代理卡死 = 给精确修复指引而非重启任务**
- 现象：子代理在 index.html 括号缺失上循环，文件长时间不改、语法门禁过不了；我 interrupt 后 send_message 指出「第几行缺哪个右括号」即秒修。
- 根因：子代理看不到我的根因分析，靠试错死循环。
- 可复用规则：子代理卡在**明确的局部错误**（语法/路径/契约）时，先 interrupt 停住，再 send_message 给「精确位置 + 期望形态 + 验证命令」，比新开子代理省一个完整上下文。
- 落地检查项：
  - [ ] 监控子代理产物 mtime，停滞即排查是否卡死。
  - [ ] 卡死的局部 bug 优先精准指引，不整任务重派。

**C3. 每个子任务 spec 必须含「验收口径 + 验证命令 + commit 约定」**
- 现象：有验收口径/验证命令/「带 REQ/BUG id、不 push」约定的子任务全部一次通过；口径含糊的任务出现返工（如文案接入范围、UX 是否含交互链路）。
- 根因：spec 的边界决定子代理交付边界。
- 可复用规则：给子代理的每个任务写死四要素：①目标文件清单 ②验收标准（含「不改什么」）③验证命令（要求贴输出）④commit 消息模板 + push 禁令。
- 落地检查项：
  - [ ] spec 模板含「不触碰文件清单」，防误提交并行者改动。

**C4. 台账状态是「承诺」不是「记录」**
- 现象：需求/Bug 状态被多 session 各自更新，真机退回的细化口径（REQ-039/047 附 4+2 条问题）比状态符号更重要。
- 根因：只看 🟡🔵🟠 符号，忽略备注里的退回细节。
- 可复用规则：状态变更**必须连同退回原因/细化口径一起写**（备注即验收细则）；测试组退回的「细化问题列表」就是下一批任务的 spec 来源。
- 落地检查项：
  - [ ] 处理退回需求前，先读备注全文的细化问题，逐条列实现项再排期。
