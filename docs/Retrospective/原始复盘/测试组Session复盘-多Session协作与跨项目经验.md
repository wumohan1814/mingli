## 二、经验清单（按踩坑代价从高到低）

> 格式：现象 → 根因 → 可复用规则 → 落地检查项

### A. 协作协议类（代价最高：信息不同步直接引发冲突/返工）

**A1 · 多 Session 共享同一工作区 + 同一 git 仓库 = 高频冲突源**
- 现象：我在改 `backend/tests/*` 时，开发组同一时间也在同库提交；我基于旧 HEAD 编辑 `docs/Bug管理表.md`，dev 的 `45fa032` 把我**未提交的改动**直接带走提交；若我再提交即重复/冲突。还出现我读表时表中已有 dev 刚加的行（BUG-011），我差点基于过期快照做状态机判断。
- 根因：无分支隔离，"先 pull 再改"依赖自觉；表/文档是多人同改区；读到的 HEAD 滞后于 dev 的实时写入。
- 规则：
  1. **改任何共享文件前先 `git log -3` + `git status`，确认自己基于最新 HEAD**；提交前再看一次 diff，避免把他人未提交改动混入自己的 commit。
  2. **按文件分区声明主权**（测试组主维护 `backend/tests/`；开发主维护 `backend/app|frontend`）；他方遗留的未提交文件（如 `docs/文字需求*.md`、untracked 目录）**一律不 stage、不 touch**，提交时用路径白名单而非 `git add -A`。
  3. 表状态会滞后于代码（dev 实现了 REQ-051~056 却未回写 🟠）：**先核对 commit 再判断状态**，不因表旧而漏验、不因代码在而越权置状态。
- 检查项：
  - [ ] 动共享文件前 `git log -1` + `git status`（是否有人在我上次之后提交）
  - [ ] 提交命令仅含我的文件（显式路径），提交 message 带 REQ/BUG 编号
  - [ ] 状态机动作前向需求方确认口径（🟢 归属测试，但 🟠 应由开发置，越级需备注说明）

**A2 · 用户真机反馈 = 高价值但非结构化 → 需"复现→根因→细化成文"三步才可执行**
- 现象：用户反馈"登录报错显示登录信息已过期"→ 我先本地 API 复现（后端返回 401「用户名或密码错误」）→ 定位根因（前端 `api()` 对任意 401 统一拦截）→ 才登记 REQ-049（带修复口径）；反馈"分享链接空白"→ 本地复现正常 → 不武断下结论，登记"待复现+需补抓 console"。
- 根因：用户描述的是**表象**，缺分层（前端/后端/环境）；直接照单登记会产出不可执行条目。
- 规则：**收到任何缺陷/需求描述，先过「三层归因」**（前端逻辑 / 后端 API / 环境），用最小复现验证后再落表；落表必须含「现象+根因+期望」，达不到可执行粒度就先标"待复现/待补信息"。
- 检查项：
  - [ ] 缺陷登记前是否已本地最小复现（curl/TestClient，非纯脑补）
  - [ ] 表中备注是否含根因层（前/后端/环境）供开发直接定位
  - [ ] 无法复现的条目是否明确标"待复现 + 需要的补充信息"

**A3 · S0/S1 新发现必须当轮分流，不能混进"常规验收通过"**
- 现象：用户在无痕走查中发现 MBTI 分享越权（S0 数据泄露）；若我笼统把"本轮都通过了"直接收口，S0 会被淹没。
- 根因：安全类缺陷与功能验收是不同处置节奏；"用户说都好了" ≠ "全部安全"。
- 规则：**真机反馈收口前做一次"S0/S1 扫描"**；发现安全/资金/数据类问题单独分流（登记→状态跟踪→推动优先修复→线上风险提示），与功能 🟢 分开走。
- 检查项：
  - [ ] 收口消息是否单列"S0/S1 未闭环项"（不混入 🟢 列表）
  - [ ] 对疑似越权/泄露问题是否至少做"后端端点审查是否干净"的只读复核，把排查面收敛后交给开发

**A4 · 文档黑板机制的时序盲区：状态流转依赖"谁改谁通知"**
- 现象：REQ-044 口径被 dev 更新为 v2，但 v2 只有文档无实现代码；若我按文档置状态会误判"已实现"。
- 根因：文档先于实现更新（口径先行是好事），但状态字段没区分"口径已定"与"已实现"。
- 规则：**状态=实现进度，口径变更≠实现完成**；看到 🔵/🟡 且 commit 含 docs 时，先查是否有对应 feat commit 再判断。
- 检查项：
  - [ ] 判断某需求"可验收"前，确认存在对应 `feat/fix` commit 而非仅 `docs`
  - [ ] 状态备注里写明"口径已定，待实现" vs "已实现，待验收"

### B. 架构设计类（代价次高：契约不一致在测试层反复引爆）

**B1 · "业务错误码 ≠ HTTP 状态码"是最贵的一条契约认知**
- 现象：后台删除不存在资源返回 HTTP 400 + `code=1002`；后台 reset-case 跨用户返回 HTTP 404 + `code=3001`。我两次断言失败（先按 REST 直觉断言 404 遇到 400，再断言 400 遇到 404）。
- 根因：项目错误码体系分 1xxx（通用→400）/2xxx（鉴权→401/403）/3xxx（case→404）/5xxx（LLM→502）；**HTTP 状态只是粗分，body.code 才是语义**。
- 规则：**断言一律以 `code` 为准、不赌 HTTP**；测试框架里先读项目的 `code_to_http` 映射表再写断言；把该映射沉淀为知识库供全组复用。
- 检查项：
  - [ ] 新端点测试前先查该异常走哪个错误码段 → 推 HTTP
  - [ ] "资源不存在"断言写成 `code == 1002/3001` + 对应 HTTP，二者都显式断言（暴露映射错误）

**B2 · SPA fallback + 深层路由：静态资源必须根绝对路径**
- 现象：分享页 `/mbti/share/{token}` 白屏——vendor 脚本用相对路径 `./vendor/*`，在深层路由被解析成 `/mbti/share/{token}/vendor/*` → fallback 返回 index.html（text/html）当 JS 执行 → React 未加载。
- 根因：单页应用 history 路由下，相对路径基准随 URL 层级变化。
- 规则：**SPA 静态资源一律根绝对路径 `/vendor|/assets|/...`**；fallback 应排除 `/api` `/admin` 等非前端前缀（防未注册接口回退 HTML 造成假 200）。
- 检查项：
  - [ ] 上线清单含：静态资源相对路径排查（`./`、`../`）
  - [ ] fallback 规则排除 API/admin 前缀
  - [ ] 真机含"深层路由直达 + 无痕窗口"两种打开方式

**B3 · 双数据源/双快照并存的功能，合并前先做"分层降险"比对**
- 现象：档案内"占星盘"与完整盘面"占星盘 tab"来自不同快照（natal vs charts.western），出现展示不一致、重复生成、点查看跳回重生成。
- 根因：同一语义数据存在两份实现/两份落库，缺唯一事实源。
- 规则：**合并双实现前先产出"分层方案+风险清单"**（前端共享渲染层 / 展示层收敛 / 数据层统一），明确各层改动量与暂缓项，再让测试按层验收。
- 检查项：
  - [ ] 是否存在同一数据的多份渲染/落库？是否评估过一致性风险（时点差/降级/空值）？
  - [ ] 合并是否分层落地并标注"暂缓项不阻塞验收"？

**B4 · 配置单例 + 环境变量注入的时序陷阱（单跑绿、混跑红）**
- 现象：agent 测试单文件跑 8 全绿，全量跑全挂（8 个 setup/断言失败）。
- 根因：`config.settings` 是模块级单例，首次 import 定格；`integration/test_e2e_flow.py` 顶层 `from app.main import app` 在收集期先于我的 env 注入，导致 token=""；单跑时本文件先执行所以假绿。
- 规则：**依赖配置的测试用 autouse fixture + `monkeypatch.setattr(settings, key, val)`，绝不在模块顶层 `os.environ` 注入**（顶层 import 顺序不可控）；排查口诀"单跑绿混跑红 → 先查模块收集顺序/单例定格"。
- 检查项：
  - [ ] 测试是否触碰全局配置/环境？若是 → fixture 注入而非顶层 env
  - [ ] 新测试至少跑一次"全量"验证（单跑通过不等于混跑通过）

### C. 工作定义类（代价可控，但决定返工量与推进速度）

**C1 · 角色用"一份交接文档"锚定，能消除大量边界歧义**
- 现象：测试组一切动作（职责/命令/已知问题/纪律）以 `docs/测试组交接文档.md` 为唯一依据，启动即收敛，几乎无"我该不该做 X"的摇摆。
- 根因：无角色契约时，agent 常高估/低估自己的改动边界（如擅自修产品代码）。
- 规则：**开工先写"角色 charter"**：我负责什么（主维护区）、我不碰什么（业务代码只登记不修）、纪律（mock LLM、隔离库、白名单文件）；写进仓库并让需求方确认。
- 检查项：
  - [ ] 角色 charter 是否含「禁止事项」（如：不改 backend/app、不真调 LLM、不 stage 他人文件）
  - [ ] 是否明确"验收标准 = 表状态 + 需求方确认"而非自判

**C2 · 目标用"表 + 状态机 + 口径"表达，返工主要来自口径含糊**
- 现象：第一轮验收清单（A~J）与用户理解有偏差 → 部分项退回重做；第二轮清单按"复验点+关联 commit"逐条给出，一次通过率高。REQ-049 因我先本地复现给了修复口径，开发可直改。
- 根因：需求/缺陷的"可验收口径"（期望行为）缺失时，双方各按自己想象验收。
- 规则：**所有任务落表必须带"可验收口径"**（期望行为/通过标准）；给需求方/协作方交付清单时每条附「复验点 + 证据 commit」；含糊先问，不猜。
- 检查项：
  - [ ] 我发出的清单每条是否含"期望可观察行为"
  - [ ] 对依赖外部确认的口径，是否显式提问而非默认

**C3 · 环境约束前置声明 + 分工，避免"卡在不能做的事上"**
- 现象：沙箱无 TLS 凭证连不了线上、无真实浏览器做 UI 走查；若不自知会卡死或假装验证通过。
- 根因：agent 环境能力边界与任务需求不匹配。
- 规则：**开工即声明能力边界**（能自动验 API/逻辑、不能真机 UI/外网），与需求方约定分工（我出清单+自动验，对方真机验），并记录"环境需特殊权限/网络"的已知项。
- 检查项：
  - [ ] 是否已声明环境限制并给出替代方案（清单、分工、转人工项）
  - [ ] 需要额外权限的操作是否一次性说明理由（如 pytest 需 full-access）

**C4 · 中断/恢复机制：小步提交 + 恢复三查**
- 现象：多次被打断（装环境、跑测试、真机中途）；恢复时若只凭记忆续跑会基于过期状态操作（曾差点重复提交 Bug 表）。
- 根因：长任务无检查点，恢复成本高。
- 规则：**每完成一个可独立验证的块就 commit**（补测一个 commit、表收口一个 commit）；被打断后恢复按"三查"：`git log/status`（拿最新）→ 表状态（谁动了什么）→ 待办清单（todo_write），再决定下一步。
- 检查项：
  - [ ] 是否有可恢复的 todo 清单与最近 commit 锚点
  - [ ] 恢复后第一动作是否为 git/表状态核对而非直接执行
  - [ ] 环境性陷阱（沙箱权限/端口/服务残留）是否记入知识库供续跑直接用
