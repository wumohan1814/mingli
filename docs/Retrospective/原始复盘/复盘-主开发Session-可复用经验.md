## 二、经验清单（按踩坑代价降序）

### A. 架构设计类（代价最高）

**A1. 接任何 LLM 前先做「最小真调冒烟」，核对响应结构**
- 现象：DeepSeek V4 Flash 是推理模型，`json_mode` 下 JSON 落在 `reasoning_content`，`content` 为空 → 客户端误判失败，8+ 法断前尘集体报「content 为空」。
- 根因：对"推理模型"的输出结构假设错误（以为结果必在 content）。
- 规则：新接 LLM 的第一动作是真调一次，逐字段核对响应（content / reasoning_content / usage / cache_hit），再写解析层；解析层对空 content 做 reasoning_content 回退。
- 检查项：解析函数是否有 content 为空回退；冒烟用例覆盖模型返回结构差异。

**A2. LLM 重试与失败必须有「硬上限 + 快速失败」**
- 现象：单次 LLM 失败后，编排器 9 法逐个重试（每法多轮尝试），观感"一直重连"，token 计费失控。
- 根因：单法失败只 continue、无连续失败检测、重试次数无感知。
- 规则：①重试次数设硬上限（本项目 1 原始 + 1 重试 = 2 次）；②串行编排器对"连续 N 个方法同一类错误"判服务不可用、立即停并标记失败；③失败原因要落 job.error 供前端展示。
- 检查项：重试上限可配置且默认为 1；编排器有连续失败快速中止；前端 failed 态展示可读原因。

**A3. 计费口径先于用量统计确认**
- 现象：初期只记 prompt/completion/total，但 DeepSeek 按「缓存命中/未命中/输出」+ 峰谷时段分开计费，成本算不准。
- 根因：把计费想成单一 token×单价，未确认缓存命中字段与峰谷规则。
- 规则：接入前向厂商/文档确认完整计费口径（计费字段、缓存命中、峰谷、并发上限）；usage 记录完整字段（含 cache_hit）；成本脚本按真实定价（可配置单价/时段）。
- 检查项：usage 含 `prompt_cache_hit_tokens`；成本脚本支持峰谷与缓存命中；单价可配置。

**A4. 第三方库产出的用户可见数据，要检查语言本地化**
- 现象：占星盘「格局」全是英文（mingyu-core 的 `patterns` 输出 `kite: Ceres, Juno`）。
- 根因：库的中文化只覆盖主体字段，漏了 summary/patterns 等子结构。
- 规则：接入产生用户可见文本的第三方库后，遍历全部输出字段抽检语言；对漏网英文做映射/本地化层。
- 检查项：用户可见字段语言一致性抽查；对英文残留有映射表。

**A5. 跨源数据聚合必须有「归一化层」，输出维度靠 prompt+代码双保险**
- 现象：综合解读板块标题全是「事业」（主问事业 → 各法 domain 是「事业总断/事业/财运/事业合作」细碎变体，合成层直接当标题）。
- 根因：①聚合层未把 LLM 的自由 domain 归一到固定领域标签；②prompt 未约束结论覆盖多领域。
- 规则：任何"把异构来源归并为有限类别"的地方都要有归一化映射（关键词→固定标签）；要模型产出多样化时，既要 prompt 显式要求、也要代码层兜底归并。
- 检查项：聚合前有 domain 归一化；prompt 有领域覆盖约束；验收时核对板块类别是固定集合。

**A6. 免责等框架性文字放 UI 层，绝不混进数据内容**
- 现象：免责被后端追加进 report.summary/description，显示在综合解读正文里（位置错）；去掉后旧缓存仍残留，难清理。
- 根因：把"合规文字"当数据处理（往内容里 append），而非 UI 统一渲染。
- 规则：免责/版本号/水印等框架文字由 UI 统一组件（footer/模板）渲染；数据字段保持纯净。若曾污染，须重新生成数据或做剥离逻辑。
- 检查项：内容字段不含免责字样；免责只在 UI 统一位置出现。

### B. 协作协议类

**B1. 子代理任务必须「拆到能在合理轮次内落地」，设无产出干预点**
- 现象（多次）：method-prompts 一次重写 9 份、端到端测试等大任务，code_flash 连续多轮无文件落地（读大参考+写长内容卡住），主会话空等浪费轮次。
- 根因：任务范围过大（输入输出都大）、无进度检查。
- 规则：①任务拆小（1 个文件/1 页/≤3 份同类产出）；②每个子代理任务设"落地检查点"，连续 N 轮无文件产出即 interrupt + 分析 + 拆小重派；③并行任务间文件不重叠。
- 检查项：任务描述可在一轮内开始落文件；有超时干预机制；并行任务文件集不相交。

**B2. 前后端并行时，「契约文本」必须写全字段，主会话逐字段验收**
- 现象：后端 list_cases 未返回 name，前端已展示 `c.name` → 名字恒为默认；契约漏字段。
- 根因：并行子代理只按各自理解实现，契约缺字段清单导致两端不对称。
- 规则：并行前后端任务，由主会话写"契约文档"（含每个接口/字段的精确清单与返回示例），两端子代理照契约实现，主会话完成时逐字段核对。
- 检查项：契约含完整字段清单；验收对照契约逐字段 grep/断言两端一致。

**B3. 子代理「额外修复」要主会话复核（好 bug 也可能夹带坏改动）**
- 现象：子代理顺手修了 `datetime` 未 import 的真实 bug（有价值），但也可能顺手改偏。
- 规则：子代理报告里标"契约偏离/额外修复"的项，主会话必须读代码复核后再保留。
- 检查项：验收时对子代理声称的"额外修复/偏离"逐条人工确认。

**B4. 长任务不能依赖短生命周期 token；要预设断点续跑/恢复入口**
- 现象：断前尘 30–60 分钟，access token 30min 过期把用户踢出 → 前端不记得 caseId → 重跑重花钱。
- 根因：前端 401 直接踢出、无自动续期；无"继续之前档案"入口。
- 规则：长任务类产品，前端必须有 token 静默续期（refresh 链）；后端任务独立于请求 token（编排器独立 session 跑完落库）；产品提供"档案列表/继续"入口让用户恢复，而非重头再来。
- 检查项：401 自动 refresh + 同步更新 refresh_token；长任务结果落库可查；有历史列表/继续入口。

### C. 工作定义类

**C1. 主会话角色：定契约/拆任务/评审/验收；不写底层；不空转**
- 现象：用户多次明确"尽量避免亲自完成，拆小交 code_flash，可接受长等待、不要空转浪费 token"。
- 规则：主会话专注架构/契约/验收与"人工注意点"的集中记录；子代理运行期间不重复轮询（等完成通知）；被多次 interrupt 的重复动作是空转信号。
- 检查项：主会话不手写底层实现；不 busy-poll；有进度信号时才检查。

**C2. 把「人判断/人实测/人决策」的点集中成一个活文档**
- 现象：人工验证点散落对话，用户问"还剩什么要人工验证"。
- 规则：维护《人工注意点/操作手册》类文档：标清谁做（人/机器）、怎么做、通过标准、是否延后；随迭代更新状态，作为交接与收尾依据。
- 检查项：有集中的人工注意点清单；每项有 owner/状态/通过标准。

**C3. 验收前先问"两端契约是否一致 + 字段是否齐"**
- 现象：子代理完成但字段漏（同 B2）、行为与契约偏（免责位置、板块分类）。
- 规则：验收 checklist = 契约字段逐项核对 + 行为对需求逐条对照 + 回归测试全绿 + 真调抽检。
- 检查项：验收有 checklist 而非"看起来能用"。

**C4. 诚实声明能力边界（尤其 agent 无实时流）**
- 现象：用户以为我能实时看后端日志/token 消耗。
- 规则：明确说明：我能事后查库/读文件，不能实时看用户终端流；让用户"跑完告诉我，我读库给数据"。不臆测、不假装看见。
- 检查项：能力边界在关键处（成本/日志/运行态）主动声明。
