## 二、经验清单（按踩坑代价降序）

### A. 协作协议（代价最高：并发写同一文件）

1. 现象：编辑报 "file changed since read"；随后的一次 commit 把并发会话的未提交内容误装入自己消息（BUG-011 提交装入"真机复验收口"；REQ-098 提交装入"行序整理"）。
   根因：多 session 共写同一黑板上，无锁；编辑与 commit 不在同一时点校验 staged 内容。
   规则：凡多人共用文档，commit 前必须 `git add` 后核对 `git diff --cached`（stat+抽样）与消息一致；编辑失败即视为别人在写，先 `git status` 再决定，绝不盲提。
   检查项：commit 前 staged diff 是否恰等于本次意图；失败编辑后是否有人已改；必要时 amend 修正误标消息。

2. 现象：同一条 old_string 连续两次 edit → 行被拼接/重复（REQ-083 并入 REQ-081 行）。
   根因：第二次 edit 的 old_string 已被第一次消费/错位，patch 仍按旧快照落盘。
   规则：同一 anchor 只做一次插入；插多行用「唯一尾串一次替换为整段」；行内编辑后做结构自检（grep 每 ID 恰好 1 行）。
   检查项：编辑后 `grep '^\| ID'` 行数、相邻行首；避免用整行全文作 old_string 的大替换连发。

3. 现象：PowerShell `Get-Content` 默认按 ANSI/GBK 解 UTF-8 中文 → 整表乱码，需 `git checkout` 恢复。
   根因：中文 UTF-8 文件被错误编码读写。
   规则：中文文件只经编辑器工具修改；确需脚本处理时必须显式 `[System.IO.File]::ReadAllLines/WriteAllLines + UTF8Encoding(false)`，或改用受控编辑。
   检查项：脚本写文件前备份/`git status`；写完立即 read 抽检中文。

4. 现象：远端 push 失败（schannel 无凭据、代理不可达、token 为 JWT 非 PAT）。
   规则：push 前先确认凭据/代理与仓库可用；secret 不打印不进日志；无法 push 时明确告知阻塞并本地 commit 收尾。
   检查项：`git fetch` 先行；远程配置与凭据 helper；必要时用户提供凭据再推。

5. 现象：需求编号被并发占用（REQ-049/078/079/080 冲突），被迫顺延并备注。
   规则：黑板编号分配前先 `grep` 当前最大号；占用冲突时立即改号并留痕，勿复用。
   检查项：登记前查 max；冲突后更新引用与被引用方备注。

### B. 工作定义（角色/目标/约束 → 减少返工）

1. 现象：口语需求含糊（「必选」「文案待我补」「优化」），直接落表会让开发无从执行或做错方向。
   规则：需求/Bug 先澄清再登记：缺口追问到「验收标准/现象-期望/严重度」可测为止；大量或歧义输入先给归类草案+选项式提问，一次问清。
   检查项：每条含 验收口径；歧义处有问过的问题与答案留痕。

2. 现象：同根因/同屏问题重复上报（生肖空白、选档案 UI、塔罗按钮等多次出现），以及整批内容重复粘贴两遍。
   规则：登记前查重合并：并入既有行（保留最早 ID+备注「并入于」），跨模块同源问题合并并列出各入口；收到重复批次应识别并合并，不新增行。
   检查项：新增前对全表 grep 关键词；重复上报仅在原行备注追加新入口/新现象。

3. 现象：「开发说做完 ≠ 需求完成」；验收需第三方；有阶段返工（如 REQ-044 v2→v2.1、REQ-051→085/087）。
   规则：状态机约定「🟢 仅测试组可设」；需求中途改口径 = 新 REQ 或回退原行并备注「取代/以 x 为准」，保留历史描述不删改原文；用「权威口径行」防双行漂移。
   检查项：改口径时给「取代/取代自」链接；保留历史；不私自置 🟢。

4. 现象：文案交付后开发不知如何接入（六爻文案补齐）。
   规则：内容型交付附带「呈现指引」：必须项（接入点/数据/合规/无占位残留）+ 自由项（开发自选并说明）+ 兜底（不确定先提问、不得搁置）。
   检查项：新文案/素材交付必须含接入点与验收约束。

5. 现象：高成本实现被口头启动（动画/记忆/Prompt/换图）。
   规则：设「开发门禁」：先交方案书/素材表/评估（资源压力、并发存储等），需求方审批后才编码；把门禁写进需求行。
   检查项：关键项备注是否有「方案经审批后开发」。

6. 现象：同界面大量 UI 微调（排布/文案/图标）口头堆积。
   规则：以「聚合 REQ + 关联旧行」方式成批登记（一个主题一条，备注列旧行 ID），避免 30+ 微单行；但对主流程阻断问题（如建档保存失败）仍要独立 S1 Bug 立即可见。
   检查项：批量输入先分类「Bug(阻断/回归)/聚合 REQ/备注更新」再写表。

### C. 架构设计（决策/权衡/陷阱）

1. 现象：真 URL 子路径 vs 多 HTML vs hash 之争、PWA 是否要做/多重、SW 缓存造成旧资源。
   规则：决策先摆「方案对比表+本项目代价」（收益/改动/风险/与既有 fallback 与绝对路径的约束），用户拍板后落 REQ/ADR；缓存类功能必须配套更新/失效机制（入口网络优先、版本化清缓存、素材热更清 URL）。
   检查项：凡引入缓存/SW 类先答「发布后如何变新」。

2. 现象：前端「文案/命名」类全局口径多次被用户随口词污染后又要求重写。
   规则：涉及对外话术的文字，标注「以需求方/品牌定稿为准」，开发不自行定调；产品文案与工程说明分层存放。
   检查项：对外文案来源是否单一权威（品牌/需求方确认）。

3. 现象：资源受限(2C1G)下想引重方案（向量库/独立服务）。
   规则：硬约束先行（进程数/库/机器规格/许可），再选轻方案（单 SQLite FTS5+异步外部 LLM），参考项目只借鉴可嵌入部分。
   检查项：方案书含资源压力与并发评估、参考代码「哪些采纳哪些不采纳」清单。

4. 现象：合规红线（趋势参考/不作建议/免责）易被新文案稀释；第三方 skill 素材带模型指令尾巴。
   规则：任何文案/Prompt 需求默认带合规基线（话术词表+免责尾注）；外采素材标注来源/许可与改写规则（去指令语）。
   检查项：新文案是否有趋势参考句与免责；素材出处可追溯。
