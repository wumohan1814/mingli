## 1. 子代理 LLM 模型路由（本日最大坑）

- **现象**：开发子代理连续 5+ 次"failed, error、零产出"（阵型示意×2、大工程×2、小任务×1），用户提示"模型调错"。显式指定某供应商/模型也失败；**omit 全部路由参数（继承主会话模型）后成功**。
- **根因**：子代理的默认 LLM 路由与主会话不一致（走了另一接入点的模型），导致不可用/失败；显式传参也可能因工具传参契约与预期不符而失败。
- **规则**：①派子代理**默认 omit provider/model**（继承主会话配置），不手动指定；②子代理连续失败且零产出时，**先诊断模型路由/环境**（list_subagent_models、询问用户），不盲目重试或无限重派；③失败模式区分——"半成品可收口"（实现完成、finalize 失败）vs"零产出"（环境/路由问题）。
- **落地检查项**：子代理默认路由可用；连续失败先查路由/余额/环境；spec 不强制指定模型。

## 2. SQLite 保留字列名（生产故障级坑）

- **现象**：新增 `cases.default` 列（默认档案），本地 pytest 全绿，但**线上部署后 web 容器反复重启**——日志 `sqlite3.OperationalError: near "default": syntax error`（`ALTER TABLE cases ADD COLUMN default ...`）。
- **根因**：`default` 是 SQLite 关键字，裸 ALTER 语法错误。本地测试库经 `create_all` 新建（SQLAlchemy ORM 自动加引号），**掩盖了问题**；线上老库走 `ensure_schema` 的裸 ALTER 才暴露。
- **规则**：①新增列名先查目标 DB 保留字（SQLite：default/order/group 等）；②裸 SQL 迁移对保留字列名加引号；③**数据库迁移测试必须覆盖"既有 schema + 增量 ALTER"路径**，不能只测新建库（本地与生产差异是这类 bug 的温床）。
- **落地检查项**：新列名无保留字；迁移语句对关键字加引号；有老库迁移回归用例；部署前本地用"已有库"冒烟 ensure_schema。

## 3. 部署故障定位与验证链

- **现象**：首次部署后 web 容器 `Restarting`，用户反馈"部署不行"；`docker compose logs web` 定位到 SQL 错误。
- **根因**：容器启动时 ensure_schema 失败 → 应用启动失败 → 容器重启循环；caddy 正常（反代不依赖应用）。
- **规则**：①部署后**先看容器状态 + 应用日志**定位根因，不猜；②验证链固定：health + 页面 200 + 容器稳定（无 Restarting）+ **线上 commit = 最新 commit**；③长部署后台跑（SSH + docker compose up -d --build），完成后验证再宣布。
- **落地检查项**：部署脚本带产物验证；容器异常先看日志；验证链五步齐全。

## 4. git 代理配置（push 失败排查）

- **现象**：`git push` 报 `Connection reset` / `Could not connect to github.com:443`，但用户说网络通（全局 VPN）。
- **根因**：系统代理开在局域网地址（Windows 注册表 ProxyEnable/ProxyServer），**git 默认不走系统代理**、环境变量 HTTP(S)_PROXY 未设 → git 直连失败。
- **规则**：push 失败先查：①`git config http.proxy`；②Windows 系统代理（注册表 `HKCU\...\Internet Settings`）；③常见代理端口。配 `git config --global http.proxy http://<proxy>` 后重试。
- **落地检查项**：git 代理配置与系统代理一致；`git ls-remote` 连通后再 push。

## 5. 大工程拆小块（降低单子代理失败率）

- **现象**：塔罗两段式（REQ-129）一次性派给单子代理 → 零产出失败；拆成"后端槽位 → 取牌段 → 读牌段"逐个小块后成功。
- **根因**：超大任务（重构 2 万行单文件前端 + 新交互）超出单子代理可靠执行范围（context/复杂度）。
- **规则**：大工程按"后端独立件 → 前端阶段件（状态机/数据流先定，UI 后接）"拆分；**先定数据流契约**（如 lastTarotPickStream 供下段消费），分段实现、段段可验证可提交；每段 spec 给足代码坐标（行号/组件名）。
- **落地检查项**：任务拆到"单段可 review + 可提交"；段间有数据流契约；spec 含现状坐标。

## 6. 文案 key 化与兼容别名（文案管理专项）

- **现象**：全站约 2700 处硬编码中文；UI_COPY 只收部分；直接全量迁移风险高。
- **方案**：REQ-128 分阶段（阶段0 名词卡 key 化试点 + key 规范入 standards/01 §12 → 阶段1 框架层迁入 TC_COPY 总表）；迁移时 `const UI_COPY = TC_COPY.ui` **兼容别名**保住旧引用，新增 key 走规范。
- **规则**：文案统一管理**增量推进**（建体系 + 新功能遵守 + 存量按模块迁）；数据文件与代码分离（pairs.js/term-cards.js/ui-copy.js）；兼容别名降低迁移回归。
- **落地检查项**：key 规范入规范文档；新文案进总表；兼容别名存在；precompile 通过。

## 7. 台账状态列纪律（备注与状态同步）

- **现象**：多处需求"备注写了已实现 + commit，但**状态列仍 🟡**"（REQ-084/127/129/135 均出现），且被并行需求管理员编辑后可能回退。
- **根因**：更新备注时遗漏状态列；多 Session 共写需求表时状态被覆盖/恢复。
- **规则**：①改备注「已实现」时**必须同步状态列 🟡→🟠**；②台账变更后 `grep` 自检状态列；③发现状态列与备注不一致（含并行编辑造成）→ 立即修正并 commit，不静默。
- **落地检查项**：每个"已实现"备注对应 🟠 状态列；台账 commit 前自检。
