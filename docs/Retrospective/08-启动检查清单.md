# 启动检查清单（首个 Agent · 引导式建项脚本）

> 定位：下一个项目启动时，交给**首个 Agent（建项 Agent）** 的引导式脚本。
> 该 Agent 先**通读本资产包全部文档**（`README.md`、`01-项目准则.md`、`02-AGENTS-统一（三角色合一）.md`、`05/06/07` 文档范式与模板），
> 再按本清单**逐条向用户提问确认**——确认一条、落盘建立一条，最终把项目骨架（文档体系 + 协作协议 + 角色边界 + 工程基线）搭好。

## 0. 建项 Agent 的前置动作与总规则

**开工前**：
1. 通读 `README.md` 与本包全部 01–07 文档，理解状态机、commit 规范、责任矩阵、交接文档三件套。
2. 从下方 §1–§5 挑出**与当前项目相关**的项，整理成一张"待确认问题清单"（可以跳过明显不适用的项，但要向用户说明跳过原因）。

**提问总规则（铁律）**：
- **缺的信息必须问，不臆测**：任何无法确认的信息明说不可知，不编造、不默认。
- **一次一条**（或一组强相关项）：逐条问、逐条确认，不要一次抛一大堆。
- **每条给"默认建议 + 后果"**：让用户能快速"确认 / 否决 / 改"，降低决策成本。
- **回答后先 diff 再落盘**：先复述"你新增了什么、改了哪些旧结论"，确认无误再写入文件。
- **确认即落盘**：每确认一项，立刻建立/更新对应文件或配置，不攒到最后。

**建立顺序**：§1（角色）→ §2（协作文档）→ §3（工程基线）→ §4（外部依赖）→ §5（范围）→ §6（收尾产出交接文档）。

## 1. 项目与角色（先问，决定后续一切）

### 1.1 项目名与定位
- **目的**：后续所有文档的 `{{项目名}}` 占位、目录、标题都以此为准。
- **你要做的**：确认后把项目名填入所有要建立的文档。
- **向用户确认**：
  1. 项目叫什么名字？（一句话，用于文档标题与 `{{项目名}}` 替换）
  2. 一句话定位：这个产品/项目是做什么的？（默认建议：先给一句最朴素的功能描述，营销话术后续再补）
  3. 工作目录 / 仓库路径是什么？

### 1.2 参与方与角色清单
- **目的**：锁定"谁在玩"，避免角色边界误判导致整批需求遗漏（参见准则 3.2）。
- **你要做的**：列出全部参与方，并明确每个是"人"还是"Agent Session"、各自**产什么、落地什么**。
- **向用户确认**：
  1. 参与方有哪些？（默认建议至少包含：用户=需求方、开发、测试组、需求/Bug 管理；可选：UI/美术、文字/文案、运维）
  2. 每个参与方是"人"还是"Agent"？（例如：美术素材是用户另外找人产，还是 Agent 产）
  3. **谁产元素、谁落地代码**？——尤其确认：美术/文字组只产素材，交互与代码落地归开发？（默认建议：是）
  4. 每个模块/每类事项的 **owner** 是谁？

### 1.3 决策权边界（owner 模式）
- **目的**：避免 Agent 替用户拍板白做（参见准则 3.11）。
- **你要做的**：把"用户拍板项"与"Agent 自主项"列成清单。
- **向用户确认**：
  1. 哪些决策**必须你拍板**？（默认建议：产品范围、付费点、合规边界、视觉风格、对外文案）
  2. 哪些决策 Agent 可**自主推进**？（默认建议：技术选型细节、实现方式、命名、测试用例设计）
  3. 用户决策项的默认动作 = 出方案占位等确认，对吗？（默认建议：对）

## 2. 协作与文档体系

### 2.1 文档根目录与文件清单
- **目的**：文档是唯一黑板，先把"黑板摆在哪"定下来。
- **你要做的**：建立文档目录与空文件骨架。
- **向用户确认**：
  1. 文档根目录用 `docs/` 还是别的？（默认建议：`docs/`）
  2. 需要建立哪些文件？（默认建议：需求表、Bug 表、Session 交接文档、协作守则、测试知识库、开发日志、Retrospective 复盘目录、standards 规范目录、adr 决策目录、`docs/exchange/` 跨 Session 交付物中心、**Code-Wiki（代码知识库）骨架**）

### 2.2 状态机（🟡→🔵→🟠→🟢）
- **目的**：状态即沟通，先约定状态机，双方才在同一语义下协作。
- **你要做的**：把状态机写进协作守则，并确认与默认一致。
- **向用户确认**：
  1. 状态机沿用默认的 🟡 待办 / 🔵 进行中 / 🟠 待验收·待验证 / 🟢 已验收·已修复 / ⚪ 已归档·已关闭？（默认建议：沿用）
  2. **🟢 仅测试组可设、开发最多置 🟠**，这条铁律确认保留？（默认建议：保留）

### 2.3 编号与 commit 规范
- **目的**：让 `git log` 能当聊天记录用。
- **你要做的**：把编号与 commit 约定写进协作守则。
- **向用户确认**：
  1. 需求 / Bug 用 `REQ-<三位序号>` / `BUG-<三位序号>` 全局递增编号？（默认建议：沿用）
  2. commit 消息格式沿用 `feat/fix/test(模块): 描述（REQ-xxx / BUG-yyy）`？（默认建议：沿用）
  3. 只 add 本任务文件、绝不 `git add -A`，确认？（默认建议：确认）
  4. 台账编号由谁统一发放？（默认建议：需求管理员唯一发放——登记前 grep 现用最大号、撞号顺延双向留痕、定期审计唯一性）
  5. 口径修订必须联动状态（返工退回 🟡/🔵、🟠 只挂已实现待验收）？（默认建议：是）

### 2.4 push / 部署批准人与网络前提
- **目的**：push/部署是异步、需协调的动作，先把规则定死（参见准则 1.3）。
- **你要做的**：把批准人、网络前提写进协作守则。
- **向用户确认**：
  1. 谁批准 push / 部署？（默认建议：测试组验收通过 + 你明示后才 push）
  2. 是否有网络前提（如需要你开代理/VPN 才能 push）？（默认建议：说明现状）
  3. push 失败怎么处理？（默认建议：轮换重试，仍败则明确报告等你开网，不空转）

### 2.5 交接节奏
- **目的**：跨 session 唯一记忆（参见准则 3.7）。
- **你要做的**：约定每轮收尾 checklist，并建立交接文档骨架（按 `05-文档范式-交接文档.md`）。
- **向用户确认**：
  1. 每轮 session 收尾是否强制走"git pull → 更新状态 → 交接追加 → commit → push"？（默认建议：是）
  2. 交接文档是否含"状态快照 + 待办(owner) + 勿回滚护栏"三件套？（默认建议：是）

## 3. 工程基线

### 3.1 技术栈选型
- **目的**：锁技术栈，避免后续选型返工。
- **你要做的**：把选型与版本写进 standards 技术栈清单。
- **向用户确认**：
  1. 后端 / 前端 / 数据库 / 部署分别用什么？（若已定则直接记录；未定则先列候选 + 默认建议再确认）
  2. 有没有强制约束（服务器资源、沙箱限制、离线环境等）？（默认建议：逐条说明现状）

### 3.2 单文件真相源 / 权威运行件清单
- **目的**：单一事实源，防文档互相矛盾（参见准则 2.11）。
- **你要做的**：产出"权威清单"，逐项核对文件/入口确实存在。
- **向用户确认**：
  1. 每个模块的**权威运行件**是哪个文件/入口？（如：前端以哪个文件为准，`src/` 是否只是参考）
  2. 是否存在"文档与事实相反"的隐患点？需要当场标"以 X 为准"。

### 3.3 前端红线与语法门禁（若适用）
- **目的**：单文件/预编译产物改坏会整页白屏（参见准则 2.9、开发 Prompt §1.2）。
- **你要做的**：把红线与门禁命令写进开发规范。
- **向用户确认**：
  1. 前端是否有"禁 JSX / 标签类型固定 / 免构建"等红线？（默认建议：若有则逐条列明）
  2. 每次改动后是否强制跑语法门禁命令？（默认建议：是）

### 3.4 配置字段显式映射约定
- **目的**：字段名 ≠ 环境变量名，防线上 401/配置错误（参见准则 2.8）。
- **你要做的**：约定"新增配置字段必写显式映射 + 本地断言"。
- **向用户确认**：
  1. 是否强制"新增配置/环境变量字段必须显式映射 + 本地断言测试"？（默认建议：是）

### 3.5 幂等与缓存默认约定
- **目的**：数据型功能默认可重入（参见准则 2.10）。
- **你要做的**：约定"同一实体多入口的功能默认幂等键 + 缓存复用"。
- **向用户确认**：
  1. 新增创建型接口是否默认要求先答"重复调用会怎样"？（默认建议：是）

## 4. 外部依赖与成本

### 4.1 LLM / 外部服务接入
- **目的**：接任何 LLM 前先真调冒烟（参见准则 2.1–2.3）。
- **你要做的**：建立"接入前核对清单"，确认后写进架构/标准。
- **向用户确认**：
  1. 是否接 LLM / 外部 API？用哪个模型 / 服务？
  2. 模型是否推理型？响应结构落在哪个字段？（默认建议：先最小真调一次，逐字段核对再写解析）
  3. 计费口径（字段 / 缓存命中 / 峰谷 / 并发上限）是否已确认？（默认建议：接入前向厂商确认完整口径）
  4. 重试上限与快速失败阈值？（默认建议：重试默认 1 原始 + 1 重试 = 2 次）

### 4.2 第三方库盘点
- **目的**：选库先盘点仓库现成能力，只按增量缺口引入（参见准则 2.14）。
- **你要做的**：盘点仓库已有依赖能力，列出候选库差集。
- **向用户确认**：
  1. 候选库与仓库现有能力的**差集**是否为空？（默认建议：差集为空则跳过并留档理由）
  2. 第三方库产出的用户可见文本，是否已约定抽检本地化？（默认建议：是）

### 4.3 外部链接 / 仓库可信性验证
- **目的**：外部依赖写进方案前先验证可信性（参见准则 3.8）。
- **你要做的**：验证存在性 / 维护 / license，不可及则给兜底。
- **向用户确认**：
  1. 外部链接/仓库是否可访问、license 是否允许复用？（默认建议：逐条验证，不可及就"机制自研 + 内容多源改写"兜底）

### 4.4 免责 / 框架文字放 UI 层（若适用）
- **目的**：框架性文字不混进数据（参见准则 2.7）。
- **你要做的**：约定免责/版本/水印由 UI 统一组件渲染。
- **向用户确认**：
  1. 是否有免责声明/协议/水印类文字？（默认建议：有则约定放 UI 统一组件，不写进业务数据字段）

## 5. 需求与范围

### 5.1 首个里程碑范围 + 不做清单（决策表）
- **目的**：启动即定义"不做清单 + 约束决策表"（参见准则 3.9）。
- **你要做的**：建立决策表（范围 / 不做清单 / 引擎 / 付费 / 合规），并登记首个里程碑需求。
- **向用户确认**：
  1. 首个里程碑要交付什么？（拆成可勾选的闭环）
  2. **明确不做 / 暂缓**的清单？（默认建议：列出来，防止新需求悄悄推翻旧前提）

### 5.2 确定性计算机会 / LLM 边界
- **目的**：确定性计算先行，LLM 只保留必要步骤（参见准则 2.4）。
- **你要做的**：逐功能标注"确定性层 / LLM 层"。
- **向用户确认**：
  1. 每个功能是否先答"能否确定性计算 + 内置文案"？（默认建议：是）
  2. 哪些 LLM 调用点是付费/计量的？（默认建议：接入计量与扣费）

### 5.3 合规边界（若适用）
- **你要做的**：把合规红线写进决策表与 prompt 约定。
- **向用户确认**：
  1. 是否有合规/监管红线？（默认建议：有则逐条确认，冻结进约束决策表）

## 6. 收尾：建立项目骨架并交验

**全部确认完毕后，你要产出/落盘**：
1. **协作守则**（按 `06-文档范式-协作守则.md`）：状态机、编号、commit、分工边界、收尾 checklist。
2. **需求表 + Bug 表**（按 `07-文档模板-需求与Bug.md`）：空表骨架 + 使用说明。
3. **交接文档**（按 `05-文档范式-交接文档.md`）：写入本次建项的"状态快照 + 待办(owner) + 勿回滚护栏"。
4. **Code-Wiki 骨架**（按 `03-文档范式-Code-Wiki（代码知识库）.md`）：建空壳（目录 + 头注"最后更新 / 以源码为准"），首个模块落地后开始填充；约定"代码落地即更新"。
5. **standards / adr**：技术栈清单、接口字典占位、命名约定；首个里程碑的 ADR（如有决策）。
6. **复盘目录**：建好 Retrospective 目录，供三个 Agent 定期沉淀（见 AGENTS 的"定期复盘"节）。

**最后向用户确认**：
1. 把上述骨架清单读一遍，是否有遗漏？（默认建议：逐项过一遍）
2. 下一步是否由"开发 Agent"按 `02-AGENTS-统一（三角色合一）.md` §2 角色块接手首个里程碑？
