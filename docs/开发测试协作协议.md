# 太初 · 开发 / 测试 Session 协作协议

> 背景：开发（本 Session）与测试（新 Session）是两个**独立的会话**，彼此看不到对方的过程与对话。双方唯一的共同通道是**同一个 Git 仓库**。本协议约定：通过仓库内的文档 + commit 约定，实现异步、可追溯、无冲突的协作。
> 关联：`docs/需求表.md`（REQ）｜ `docs/Bug管理表.md`（BUG）｜ `docs/测试组交接文档.md`｜ `docs/Session交接文档.md`。

---

## 1. 核心原则（三条）

1. **文档是唯一黑板**：任何「要对方知道 / 要对方做」的事，都写进仓库文档（需求表 / Bug 表 / 交接文档），**不靠口头、不靠记忆**。
2. **状态即沟通**：REQ / BUG 的状态流转就是双方的对话——谁改状态，就代表「这件事现在轮到谁」。
3. **commit 可追溯**：所有代码提交在 message 里带 `REQ-xxx` / `BUG-xxx` 编号，用 `git log` 即可还原「哪个需求/哪个 bug 由谁、何时、怎么改的」。

---

## 2. 共享载体（沟通媒介清单）

| 载体 | 内容 | 主要维护方 |
|---|---|---|
| `docs/需求表.md` | 需求（REQ）+ 优先级 + 状态 + 验收标准 | 开发登记，测试确认验收 |
| `docs/Bug管理表.md` | 缺陷（BUG）+ 严重度 + 状态 + 复现步骤 | 测试登记，开发修复，测试关闭 |
| `docs/测试组交接文档.md` | 测试组工作说明、真机走查清单、已知问题 | 测试组 |
| `docs/Session交接文档.md` | 每轮 Session 的总结 + 下一步 | 双方各自收尾更新 |
| **Git commit message** | 代码变更记录（带 REQ/BUG 编号） | 开发（业务代码）/ 测试（测试代码） |

---

## 3. 状态机与责任人（关键）

### 3.1 需求 REQ（谁在动，看状态就知道）

| 状态 | 含义 | 由谁设置 | 下一个动作 |
|---|---|---|---|
| 🟡 待办 | 已登记，未开发 | 开发（或任意） | 开发组开始 → 🔵 |
| 🔵 开发中 | 开发组正在实现 | 开发 | 开发完成 → 备注写「待验收」 |
| 🟠 待验收 | 开发完成，等测试验收 | 开发（🔵 后置备注） | 测试组验收 |
| 🟢 已验收 | 测试通过、已上线 | **仅测试组** | 结束 |
| ⚪ 已归档 | 明确不做/暂缓 | 开发 | — |

> 约定：**🟢 只能由测试组设置**（验收通过才算完成）；开发组最多设置到 🔵 + 备注「待验收」。这保证「开发说做完 ≠ 需求完成」。

### 3.2 Bug BUG（谁在动，看状态就知道）

| 状态 | 含义 | 由谁设置 | 下一个动作 |
|---|---|---|---|
| 🟡 待办 | 测试登记，待修复 | 测试 | 开发组认领 → 🔵 |
| 🔵 处理中 | 开发组正在修复 | 开发 | 修复提交 → 备注写「待验证」 |
| 🟢 已修复 | 测试验证通过 | **仅测试组** | 结束 |
| ⚪ 已关闭 | 不复现/重复/不修 | 测试（注明原因） | — |

> 约定：**🟢 只能由测试组设置**（修复已验证才算关闭）；开发组最多设置到 🔵 + 备注「待验证」。

---

## 4. 协作工作流（一个需求的完整循环）

```
开发组                         测试组
  │ 登记/认领 REQ-xxx 🟡          │
  │ 开发 → 🔵                     │
  │ 完成 → 备注「待验收」          │
  │  commit: feat ... REQ-xxx     │
  │                               │ 读需求表，看到「待验收」的 REQ
  │                               │ 按验收标准真机/自动化验收
  │                               ├─ 通过 → REQ 置 🟢
  │                               └─ 不通过 → 登记 BUG-yyy 🟡（关联 REQ-xxx）
  │ 读 Bug 表，认领 BUG-yyy 🟡     │
  │ 修复 → 🔵 → commit fix BUG-yyy │
  │                               │ 验证修复 → BUG 置 🟢 / ⚪
  │                               │ 回归 → REQ 置 🟢
```

**一个 Bug 的循环**：测试登记 🟡 → 开发认领 🔵 → 修复提交「待验证」→ 测试验证 🟢/⚪。

---

## 5. 沟通约定（让 git log 能当聊天记录用）

1. **commit message 必须带编号**：
   - 新功能：`feat(模块): 描述（REQ-xxx）`
   - 修 Bug：`fix(模块): 描述（BUG-yyy）`
   - 测试：`test(模块): 描述（覆盖 REQ-xxx / 验证 BUG-yyy）`
2. **每轮收尾必做**（双方各自）：
   - 更新本 Session 涉及的 REQ / BUG 状态；
   - 在 `docs/Session交接文档.md` 追加一段「本轮做了什么 + 待对方做什么」。
3. **交接触发**：当 REQ 备注出现「待验收」或 BUG 备注出现「待验证」时，**对方下一轮先处理这些**。

---

## 6. 分工边界与冲突避免

| 事项 | 开发组 | 测试组 |
|---|---|---|
| 业务代码（backend/app、frontend/public/index.html） | ✅ 改 | ❌ 不改（发现 Bug 只登记 + 附复现/测试） |
| 测试代码（backend/tests/） | 可补 | ✅ 主维护 |
| 需求表 / Bug 表 / 交接文档 | ✅ 可改 | ✅ 可改 |
| 简单文案/样式 Bug 修复 | ✅ | 可提 PR，由开发确认 |

**避免同一文件冲突**：
- 双方**不同时改同一份代码文件**；文档（需求表/Bug 表/交接文档）是冲突高频区，约定「先 pull 再改、改完尽快 commit」。
- 测试组改文档前先 `git pull` 拿到开发组最新状态，改完立即 commit，减少并发冲突。

---

## 7. 单轮 Session 收尾 Checklist（双方通用）

- [ ] `git pull`（拿到对方最新状态）
- [ ] 更新本 Session 涉及的 REQ / BUG 状态（含「待验收/待验证」备注）
- [ ] 在 `docs/Session交接文档.md` 追加本轮总结
- [ ] commit（message 带 REQ/BUG 编号）
- [ ] push（让对端可见）

---

> 一句话总结：**状态写在表里、结论写在 commit 里、交接写在文档里；谁改状态谁负责下一步通知（通过状态本身）。**
