# 太初 · 横向扩展实施方案（评估 + 数据库/埋点/后台 + 执行步骤）

> 定位：`docs/架构设计-横向扩展.md` 的**落地实施方案**（增量，不推翻现行 9 法主线）。
> 本文只覆盖「后端逻辑方案」：数据库、埋点、运维后台、执行步骤与验收。UI 侧由 `docs/UI元素清单-横向扩展.md` 独立承载（另由 UI Agent 准备）。
> 关联：`docs/架构设计-横向扩展.md`（架构决策 D1–D8）｜ `docs/流程图.mmd`（导航流）｜ `docs/架构设计.md`（现行基线）。

## 1. 评估结论（可行性与复用判断）

**结论：可行，且边际成本趋零。** 理由：

1. **确定性引擎零新增依赖**：`backend/paipan-node/vendor/mingyu-core/dist/` 已内置塔罗/生肖/占星/起卦/雷诺曼全部确定性函数（见架构设计 §2 表），`package.json` **无需新增任何 npm 依赖**。
2. **复用现有四件套**：双运行时（Python FastAPI + Node 常驻 :9317）、LLM 客户端（`chat`）、积分（`consume`/`check_balance`）、埋点（`record_event`）全部复用，新增的 `*/interpret` 端点只是「现有 `revise`/`query` 计费模式的复制」。
3. **LLM 边界清晰**：排盘/抽牌/起卦/计分 = 确定性 = 零 LLM 零扣费；只有「串成解读」调 LLM 且可选付费（D4）。这与现行积分语义完全一致（D5）。
4. **数据隔离范式现成**：新增表全部 `user_id` 行级隔离，复用现有 `get_user_id_from_token` 鉴权 + `_get_owned_case` 模式。

**关键风险与缓解**（详见 §6）：MBTI 题库/文案建设量、塔罗美术缺失、起卦类目合规、前端页面数量多。

## 2. 数据库方案（4 张新表，进 `taichu_analytics` 库）

### 2.1 迁移机制
- 现有 `Base.metadata.create_all(checkfirst=True)`（`main.py` lifespan）对**新表幂等建表**，**无需 ALTER**（与 `register_limits` 等新表同法）。
- 新表 ORM 加进 `backend/app/models/analytics.py`，并同步 `backend/app/models/__init__.py` 导出。

### 2.2 ORM 设计（SQLAlchemy，对齐现有风格：`Column/Integer/String/Text/JSON/DateTime/ForeignKey`，`default=datetime.utcnow`）

```python
class TarotReading(Base):
    __tablename__ = "tarot_readings"
    id = Column(Integer, primary_key=True, autoincrement=True)
    user_id = Column(Integer, ForeignKey("users.id"), nullable=False, index=True)
    spread_type = Column(String(32), nullable=False)   # single/three/love/career/decision
    question = Column(Text, nullable=True)             # 用户占问方向/问题（可选）
    draw_json = Column(JSON, nullable=True)            # 牌阵 + cards[]（确定性，含 keywords/element/archetype/reversed）
    interpretation_json = Column(JSON, nullable=True)  # LLM 综合解读（可选付费，缓存于此）
    created_at = Column(DateTime, default=datetime.utcnow)

class AstrologyReading(Base):
    __tablename__ = "astrology_readings"
    id = Column(Integer, primary_key=True, autoincrement=True)
    user_id = Column(Integer, ForeignKey("users.id"), nullable=False, index=True)
    chart_json = Column(JSON, nullable=True)           # {natal, fullScope:{natal,yearly,monthly,daily}}（确定性）
    scope = Column(String(32), nullable=True)          # natal|transit|solar_return|secondary|firdaria
    reading_json = Column(JSON, nullable=True)         # LLM 深度解读（可选付费，缓存于此）
    created_at = Column(DateTime, default=datetime.utcnow)

class MbtiResult(Base):
    __tablename__ = "mbti_results"
    id = Column(Integer, primary_key=True, autoincrement=True)
    user_id = Column(Integer, ForeignKey("users.id"), nullable=False, index=True)
    answers_json = Column(JSON, nullable=True)         # 逐题选项（如 [1,0,1,...]）
    scores_json = Column(JSON, nullable=True)          # 四维分 {"E":..,"I":..,"S":..,"N":..,"T":..,"F":..,"J":..,"P":..}
    type = Column(String(8), nullable=True)            # 如 "INTJ"
    created_at = Column(DateTime, default=datetime.utcnow)

class Divination(Base):
    __tablename__ = "divinations"
    id = Column(Integer, primary_key=True, autoincrement=True)
    user_id = Column(Integer, ForeignKey("users.id"), nullable=False, index=True)
    case_id = Column(Integer, ForeignKey("cases.id"), nullable=True, index=True)  # 起卦关联国学档案（雷诺曼可为空）
    method = Column(String(32), nullable=False)        # liuyao|meihua|xiaoliuren|ssgw|lenormand|...
    seed_json = Column(JSON, nullable=True)            # 报数/时间/摇卦结果（确定性输入）
    result_json = Column(JSON, nullable=True)          # 卦象/课式/签文（确定性）
    interpretation_json = Column(JSON, nullable=True)  # LLM 断卦/深度解读（可选付费，缓存于此）
    created_at = Column(DateTime, default=datetime.utcnow)
```

### 2.3 设计要点
- **缓存语义**：`interpretation_json` 即「interpret 结果缓存」——重复请求命中（模块 + 输入指纹）→ 零 LLM 零扣费，直接返回缓存；与现有 `MethodResult` 缓存思路一致。
- **生肖不落库**：生肖流年是纯函数现算（零 LLM 零状态），不建表；如需复看走 `events` 埋点（`zodiac_fortune`）。
- **divinations.case_id 可空**：起卦要求关联国学档案（`case_id` 非空）；雷诺曼复用此表但 `case_id=NULL`。
- **索引**：`user_id` 全部建索引（行级隔离 + 后台按用户查询）；`divinations.case_id` 建索引（按档案聚合）。

## 3. 埋点方案（11 个新事件）

### 3.1 事件清单 + 中文映射（补进 `backend/app/admin/router.py` 的 `EVENT_NAME_ZH`）

| event_name | 中文名 | 触发点 | 埋点通道 |
|---|---|---|---|
| `guoxue_hub_view` | 国学HUB浏览 | 前端进入国学 HUB 页 | 前端 `POST /api/events` |
| `xishi_hub_view` | 西式HUB浏览 | 前端进入西式 HUB 页 | 前端 |
| `zodiac_fortune` | 生肖流年 | 后端 `POST /api/zodiac/fortune` 成功 | 后端 `record_event` |
| `divination_cast` | 起卦 | 后端 `POST /api/divinations` 成功落库 | 后端 |
| `divination_interpret` | 断卦解读 | 后端 `POST /api/divinations/{id}/interpret` 成功 | 后端 |
| `tarot_draw` | 塔罗抽牌 | 后端 `POST /api/tarot/draw` 成功落库 | 后端 |
| `tarot_interpret` | 塔罗解读 | 后端 `POST /api/tarot/readings/{id}/interpret` 成功 | 后端 |
| `lenormand_draw` | 雷诺曼抽牌 | 后端 `POST /api/divinations`（`method=lenormand`）成功 | 后端 |
| `astrology_chart` | 星座星盘 | 后端 `POST /api/astrology/chart` 成功落库 | 后端 |
| `astrology_interpret` | 星座解读 | 后端 `POST /api/astrology/charts/{id}/interpret` 成功 | 后端 |
| `mbti_score` | MBTI判型 | 后端 `POST /api/mbti/score` 成功落库 | 后端 |

### 3.2 埋点实现约定
- 后端确定性端点（zodiac/divination/tarot/astrology/mbti）在**成功落库/返回前**调 `record_event(event_name, user_id=user_id, case_id=..., props=...)`，失败静默（复用 `app/events/service.py`）。
- `props` 建议：`zodiac_fortune={zodiac,year}`；`divination_cast={method,case_id}`；`tarot_draw={spread_type}`；`astrology_chart={scope}`；`mbti_score={type}`；`*_interpret={id,tokens}`。
- interpret 的 LLM 消耗由现有 `llm_call` 自动埋点覆盖（`client.py` 已埋），无需重复埋 token；`credit_consume` 由积分扣费流水独立记录，也不用重复埋。
- 中文映射补进 `EVENT_NAME_ZH` 后，后台 event 分布报表**自动**显示中文名（`_event_zh` 未收录则原样英文，不丢数据）。

## 4. 运维后台方案

### 4.1 MVP（复用，零新增后台端点）
- **事件分布报表**：11 个新事件进 `events` 表后，现有 `reports/*` 的 event 聚合自动纳入（补 `EVENT_NAME_ZH` 中文映射即可）。
- **LLM 成本报表**：`llm_call` 事件已按 `model/tokens` 聚合，interpret 的 LLM 调用自动计入成本，无需新端点。
- **积分流水**：`credit_transactions` 已含 interpret 的 `consume` 流水（ref 见 §7），后台 `credits/transactions` 复用。

### 4.2 Phase2 后台端点（**留端口，不实现**）

> 决策：MVP 只固化路由路径与语义约定，**不注册、不实现**；靠 events + 现有报表监控。待运营确认有看数需求再补代码。

- 预留用户级 readings 查看（只读聚合，复用 admin 鉴权）：
  - `GET /admin/users/{id}/tarot-readings`
  - `GET /admin/users/{id}/astrology-readings`
  - `GET /admin/users/{id}/mbti-results`
  - `GET /admin/users/{id}/divinations`
- 预留统计报表：MBTI 类型分布、塔罗牌阵使用频次、起卦方法分布。

## 5. 执行步骤（Phase A–D，含依赖与验收）

> 顺序原则：先「零 LLM 确定性」后「LLM 付费解读」；先「复用现有档案」后「新档案体系」；每 Phase 可独立上线、可回滚、不回归 9 法主线。

### Phase A —— 范式跑通（两个 HUB + 生肖，**零 LLM**）
- **A1** `server.mjs` 加 `/zodiac`；`api/zodiac.py` 端点 + 注册 `main.py` + `EVENT_NAME_ZH` 补 `zodiac_fortune`。
- **A2** 前端「国学预测 HUB」页（九法合一/生肖/起卦三卡片）+ 国学入口改指向 HUB；`guoxue_hub_view` 埋点。
- **A3** 前端「西式占卜 HUB」页（星座/塔罗/雷诺曼/其他四卡片）+ 西式入口改指向 HUB；`xishi_hub_view` 埋点。
- **A4** 生肖结果页 + 皮肤。
- **验收**：两大 HUB 可进入、生肖流年报告正确渲染、埋点落库、9 法主线回归通过（24 条测试）。

### Phase B —— 起卦（六爻/梅花/小六壬/观音灵签）
- **B1** `server.mjs` 加 `/divination`（四方法分发）。
- **B2** `api/divination.py`：起卦落库（关联 case_id）+ 断卦 interpret（LLM + 即时扣费 + `interpretation_json` 缓存）；`divination_cast`/`divination_interpret` 埋点。
- **B3** 前端：起卦方式选择页 + 卦象结果页 + 六爻摇卦/梅花报数交互。
- **B4** `prompts/interpret/divination.md` 断卦 prompt。
- **验收**：四法起卦结构正确、断卦扣费 + 缓存命中零扣费、`user_id`/`case_id` 隔离、LLM 失败按已消耗 token 扣。

### Phase C —— 西式占卜（塔罗 + 雷诺曼）
- **C1** `server.mjs` 加 `/tarot`；`api/tarot.py`（draw + interpret）。
- **C2** 前端：塔罗方向/牌阵选择 + 逐张翻牌 + 结果页（卡面占位）；`tarot_draw`/`tarot_interpret` 埋点。
- **C3** `prompts/interpret/tarot.md`。
- **C4** 雷诺曼：`api/divination.py` 加 `method="lenormand"` 分支 + 前端抽牌/结果页 + `lenormand_draw` 埋点 + `prompts/interpret/lenormand.md`。
- **验收**：塔罗牌阵/雷诺曼牌义确定性渲染、interpret 扣费与缓存正确。

### Phase D —— 星座 + MBTI
- **D1** `server.mjs` 加 `/astrology`（natal + fullScope）；`api/astrology.py`（chart + interpret）+ 法达查表（`paipan/firdaria.py`）。
- **D2** 前端：星盘 SVG 圆图 + 盘型 tab（本命/行运/日返/次限/法达）+ 解读页；`astrology_chart`/`astrology_interpret` 埋点。
- **D3** MBTI：`mbti/`（`questions.json` 题库 + `types.json` 文案 + `scoring.py` 判型）+ `api/mbti.py` + 前端答题/结果页；`mbti_score` 埋点。
- **D4** `prompts/interpret/astrology.md`。
- **验收**：星盘各盘型确定性正确、法达序列正确、MBTI 判型边界（缺题/全 A/全 B）、星座解读扣费正确。

### 并行建议
- A 可与 UI 准备并行；B/C/D 依赖 A 的范式（HUB 页 + 埋点 + Node 端点模式）。
- 后端（Node 端点 + Python router）与前端（页面）可按 Phase 内并行，由不同 Agent 分工。
