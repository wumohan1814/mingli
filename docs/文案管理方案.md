# 太初 · 文案统一管理方案（方案稿 · 待需求方确认）

> 背景：用户提出——全项目硬编码文字应有单独管理位置（数据库或文档），可在运维后台查看，目的是统一管理文本 + 为国际化（i18n）铺路。
> 关联：REQ-048（prompt 后台热改，已实现）｜ REQ-037（UI 文案体系，UI_COPY）｜ REQ-127（名词白话卡，内容文案）｜ `docs/standards/01`。
> 日期：2026-09-09 方案稿，待确认后立项实施。

---

## 0. 结论速览（先读）

| 项 | 建议 |
|---|---|
| 管什么 | 分三层：界面文字 / 内容文字 / AI 提示词 |
| 放哪 | 界面文字→前端文案总表；内容文字→独立数据文件；AI 提示词→维持 REQ-048 |
| 后台 | 先**只读「文案中心」**（列表/搜索/导出）；编辑是否开放待定 |
| i18n | 现在**不做双语言**，只搭"文字与代码分离 + 每条有编号"的架子铺路 |
| 实施时点 | 建议当前功能批次收尾后作**专项**；新功能从即日起遵守编号规范 |

## 1. 现状盘点（2026-09-09）

| 载体 | 规模 | 现状 |
|---|---|---|
| 前端界面文案 `UI_COPY`（index.html 内联） | 部分集中 | 已有按钮/提示常量，但全站仍有约 **2700 处硬编码中文**散落 |
| 内容文案 | 1 个数据文件 | `frontend/public/data/pairs.js`（792 对）；六爻词条/塔罗牌义/MBTI 16 型等部分内联在 index.html 常量 |
| AI 提示词 `backend/prompts/` | 26 个 .md | **已支持后台热改 + 版本回滚（REQ-048）** |
| 后端中文标签 | 少量 | `EVENT_NAME_ZH` / `METHOD_ZH`（代码内） |

## 2. 目标

1. 所有**面向用户的文字**有一个统一视图（后台可查、可审、可导出）。
2. 改一处、全局生效（消灭同义重复硬编码）。
3. 为 i18n 铺路：文字与代码分离 + 每条文案有稳定编号（key）。

## 3. 方案（三层，避免"一锅端"）

### L1 · 界面文字 → 前端「文案总表」（TC_COPY）
- 把 `UI_COPY` 扩展为全站界面文案总表 `TC_COPY`（index.html 内联常量或独立 `data/ui-copy.js`），按 **key 命名规范**组织。
- key 规范：`ui.<模块>.<动作|状态>`，如 `ui.button.start`、`ui.tip.loading`、`ui.error.network`（对齐 REQ-037 既有 UI_COPY 命名习惯）。
- **增量收口**：新功能文案一律进表；存量 2700 处按页面/模块逐批迁移（不一次改完，控回归风险）。

### L2 · 内容文字 → 独立数据文件
- 牌义/卦辞/配对说明/名词白话卡等"内容"按模块放 `frontend/public/data/`（或 `frontend/public/content/`），每模块一个文件（现有 `pairs.js` 即为先例）。
- key 规范：`content.<模块>.<条目>`（如 `content.liuren.tianshen`）。
- 后台只读展示各数据文件的条目清单。

### L3 · AI 提示词 → 维持 REQ-048
- 26 个 prompt 已后台热改 + 版本回滚，**不改动**；后台「文案中心」可加一个只读入口列出 prompt 清单（指向既有提示词管理台）。

## 4. 后台「文案中心」形态（先只读）

| 能力 | 建议 |
|---|---|
| 列表 | 按分类（界面/内容/提示词）列出全部文案 key + 当前值 + 所属模块 |
| 搜索 | 按 key / 中文内容搜索 |
| 导出 | 导出当前全量文案（JSON/CSV）供审阅或文案组使用 |
| 编辑 | **默认不做**（界面文字编辑易改坏页面）；如需求方要，后期对 L2 内容数据做"替换式热更"（类似 REQ-048 prompt 编辑 + 版本回滚），L1 界面文字编辑不建议 |

## 5. i18n 准备（现在不做双语言）

- 本期只做：**文字与代码分离 + 全量 key 化 + 单点替换**。
- 将来加语言 = 加一套 key→文案 的映射文件（如 `data/ui-copy.en.js`），运行时按语言取表；架构上不留障碍（避免文案直接拼在 JSX 里）。
- 不做：语言切换 UI、动态语言检测、双语内容同时维护。

## 6. 分步实施（建议）

| 阶段 | 内容 | 时点 |
|---|---|---|
| ① 建体系 | 定义 TC_COPY 骨架 + key 规范 + 后台「文案中心」只读面板（读 L1 清单 + L2 数据文件 + L3 提示词清单） | 当前功能批次收尾后专项 |
| ② 新功能遵守 | 从即日起新功能文案进 TC_COPY / 数据文件（当前占卜/改版批次即执行） | 立即 |
| ③ 存量迁移 | 按模块逐批迁移 2700 处硬编码到 TC_COPY | 专项期间低优先逐批 |
| ④ i18n 铺路 | 语言映射文件机制（架构预留，不实现双语言） | ② 之后 |

## 7. 影响面与风险

- 主要改 `frontend/public/index.html`（文案收敛）+ 新增 `frontend/public/data/ui-copy.js`（如采用）+ `frontend/public/admin.html`（文案中心面板）。
- 风险：存量 2700 处迁移可能引入文案漏改/错改 → **增量进行、每批 precompile + 冒烟**；不一次大改。
- 不做运行时从数据库拉界面文案（避免前端耦合后端 + 请求开销），界面文案以静态资源为主，后台只读查看。

## 8. 待确认单（带默认建议）

1. **范围**：默认「建体系 + 新功能遵守 + 存量增量迁移」。（否决 → 只建体系不迁存量）
2. **后台编辑**：默认「先只读查看 + 导出；编辑以后对内容数据再做」。（要编辑 → 我按 REQ-048 模式做 L2 热更编辑）
3. **i18n 时点**：默认「现在不做双语言，只铺路」。（要双语言 → 需另排期）
4. **实施时点**：默认「当前功能批次（黄历/太乙/皇极/塔罗/首页改版）收尾后专项」。（要插队 → 影响当前开发节奏，需你确认）
