# 项目准则（跨项目复用）

> 本文档是下一项目的**最高工程准则**，涵盖开发、架构、交互三方面。
> 冲突优先级：**用户口头指令 > 本文档 > 项目文档**。
> 每条准则附"落地检查项"，可直接抄进验收清单。
> 更新记录：v5 —— 新增 §4「Agent 运行成本准则（Token 经济）」（自治 Agent 模式的成本结构与降本纪律）；v4 吸收 2026-09-09~09-10 主开发 Session 复盘（台账派生只读产物 / 工具化分工、文件删除纪律、子代理通道轮换、批量流水线四件套、部署限流与 cloud-init、受限环境通道边界、公网特征断言）。

## 0. 总纲（三条）

1. **委托实现**：架构 / 契约 / 拆分 / 审查 / 验证归主负责人，底层代码实现委托子代理完成。
2. **文档是唯一黑板**：任何"要对方知道 / 要对方做"的事都写进仓库文档，不靠口头、不靠记忆。
3. **状态即沟通**：需求 / Bug 的状态流转就是各方的对话；谁改状态，谁负责让下一步责任方知道。

## 1. 开发准则

### 1.1 角色与委托
- 主开发不直接写底层实现，专注架构决策、契约定义、子任务拆分、审查、验证、git 与部署。
- **"别人生产了元素" ≠ "已落地代码"**：拿到任何交付文档先列**责任矩阵**（已入库产物 / 待我实现 / 待他人实现），歧义先问，禁止默认他人已做。
- **角色 charter**：开工先写角色契约（主维护区 / 禁止事项 / 纪律 / 验收标准 = 表状态 + 需求方确认），写进仓库并让需求方确认。
- 检查项：主开发不手写底层实现；不 busy-poll（子代理运行期间不重复轮询，等完成通知）。

### 1.2 子任务 spec 四要素
- 每个子任务必含：①目标文件清单（含"禁碰清单"）②验收标准（含"不改什么"）③验证命令（要求贴输出）④commit 消息模板 + push 禁令。
- **spec 给足代码坐标**：现状文件 / 行号 / 组件名 / 函数名，降低子代理试错。
- **大单文件场景**：每批 ≤2 项；prompt 强制"先 grep 定位锚点再精准 read、禁止整文件通读"+"验证只跑一次即停报告"。
- **代码注释挂需求编号 + 关键口径**，便于实现回溯与验收对账。
- 检查项：spec 模板含"不触碰文件清单"。

### 1.3 提交与推送
- 逐步提交：每完成一批就更新台账状态 + 本地 commit，让测试组可同步测试。
- commit 消息必带 `<REQ-xxx>` / `<BUG-yyy>` 编号；只 add 本任务文件（显式 pathspec），**绝不 `git add -A`**。
- **commit 前核对 `git diff --cached`（stat + 抽样）只含本人变更、与消息一致**；发现错标（误装他人未提交内容 / 消息与内容不符）立即 `--amend` 并如实汇报，绝不掩饰。
- push 需批准：未经测试组验收通过 + 用户明示，**禁止 push**；push 前确认网络前提，失败轮换重试，仍败则明确报告等用户开网，不空转。
- 检查项：每个 commit 前 `git status` + staged diff 核对；每批一个 commit（可随时回退 / 串行下一批）。

### 1.4 状态机纪律
- 状态流转 🟡→🔵→🟠→🟢；🟢 仅测试组（验收方）可设，开发方最多置 🟠。
- 状态变更连同退回细则 / 细化口径一起写进备注；**备注即下一批任务的 spec**。
- **状态与备注必须联动**：写"已实现 + commit"时同步把状态列 🟡→🟠；口径修订导致返工时状态退回 🟡/🔵 并注明"返工待开发"；🟠 只表示"已实现待验收"，不能挂未开发的条目。
- 检查项：台账 commit 前 `grep` 自检状态列与备注一致；不一致立即修正，不静默。

### 1.5 验收与诚实
- 验收 checklist = 契约字段逐项核对 + 行为对照需求逐条过 + 回归全绿 + 真调抽检。
- **验收三步亲验，不信自述**：亲读关键 diff → 跑语法 / 测试 → 线上 / 行为探测；子代理报告只是线索，不是结论。
- **判断"可验收"前确认存在 `feat/fix` commit**，而非仅 `docs`（口径变更 ≠ 实现完成）。
- 不得臆测：无法确认的信息明说不可知，不编造；诚实声明能力边界（能事后查库 / 读文件，不能实时看他人终端流）。
- 检查项：验收有 checklist 而非"看起来能用"。

### 1.6 子代理卡死与停滞预案
- 监控子代理产物 mtime 停滞 → 判断卡死 → `interrupt` 停止 → `send_message` 给"精确位置 + 期望形态 + 验证命令"，不整任务重派。
- **设停滞阈值**：>10–15 分钟零写盘即判停滞；中断前确认磁盘无半成品（可安全放弃）；中断后保留 agent 可 re-scope 复用，或直接新派小批。
- 检查项：卡死的局部 bug 优先精准指引；大任务先试点小批。

### 1.7 等待、目标与空转
- 等待外部依赖（子代理 / 测试组 / push 批准）期间，停下等结果，不空转、不伪造进展。
- goal / 自动续跑只用于每轮都能独立推进的里程碑；依赖外部的轮次显式停下等指令。
- **长任务定义可验证的完成判据**（文件 / 测试 / 部署 / 台账逐项取证后才标完成），不靠感觉收敛。
- **中途新增需求按优先级排队成新批**，不与在制批混合（先全量读台账拿完整清单再排程，避免漏项）。
- 检查项：连续 N 轮无代码 / 无验证产出即自检是否空转。

### 1.8 子代理失败诊断与收口
- 派子代理**默认继承主会话配置**（omit 全部模型路由参数），不手动指定供应商 / 模型——显式指定可能因路由或工具传参契约不符而失败。
- 子代理**连续失败且零产出**时，先诊断模型路由 / 环境 / 余额（查可用模型清单、问用户），**不盲目重试或无限重派**。
- 失败分两类处理：**半成品可收口**（实现已完成、仅收尾失败 → 查 `git status` / `diff` 判断，主 Session 复跑门禁收口，不重派）vs **零产出**（环境 / 路由问题 → 诊断后重派）。
- **子代理通道失败 → 轮换通道**（如 code_flash → subagent_fork），不吊死在单一通道。
- **spec 明示子代理自包含**：遇歧义按最合理默认决策、禁止停下来等确认（减少中途失败）。
- 检查项：子代理默认路由可用；连续失败先查路由 / 余额 / 环境；spec 不强制指定模型。

### 1.9 大工程拆分与并行边界
- 大工程按"后端独立件 → 前端阶段件"拆分：**先定段间数据流契约**（状态机 / 接口 / 数据流先定，UI 后接），分段实现、段段可 review、可提交、可验证。
- 拆分粒度：单段在合理轮次内可开始落文件、可独立验收；连续 N 轮无产出即干预。
- **并行边界 = 文件所有权不相交**：并行任务的文件集合两两不相交；后端多文件可并行，前端单文件永远是流水线（一批完成即提交，再派下一批）。
- **同文件批量开发流水线**：改动同一文件的子任务**强制串行**（一个子代理回报 → 主代理验证 → commit → 才派下一个）；每批验证四件套 = `diff --stat` 看范围 → hunks 位置核对越界 → 残留标识符 grep → 门禁（预编译 / 语法）；派发时给「禁碰清单」（刚完成区域 / 无关区域），子代理交付报告须自查"未触碰禁碰清单"。
- 检查项：派发前画"任务 → 文件"矩阵确认无交集；每段 spec 含现状坐标。

### 1.10 部署、数据与高风险操作纪律
- 部署失败**先看进程 / 容器状态 + 应用日志**定位根因，不猜（容器重启循环常见根因 = 启动期迁移 / schema 失败）。
- 部署验证链：health + 页面 200 + **进程稳定（无重启循环）** + 关键接口冒烟 + **线上 commit = 最新 commit**。
- **部署验证走公网真入口**：先弄清容器网络拓扑（服务是否仅内网、由反代对外，本机直连端口可能无效）；"线上 = 最新"用**新版特征断言**（页面 / 资源含本次 commit 引入的独有字符串）证明——镜像内常无 .git，git 内省不可用；健康检查与页面状态码**分开确认**，防"API 通但页面旧"假阳性。
- push 网络排查：git 默认不走系统代理；失败先查 `git config http.proxy`、系统代理设置与常见代理端口，**先实测再批量重试**（避免 N 次超时空等）；不盲信"VPN 开了"这类进程级前提。
- **数据修复与代码修复分轨**：线上脏数据就地修（快，先备份 / 记录改动量）、根因代码修复走正常发布（稳），两者独立追踪、独立验证。
- **能锁死的操作**（SSH / 防火墙 / DNS / 数据改动）先备逃生通道与备份；改配置先 `.bak`，失败可恢复。
- **服务器配置必须进 git**：先本地改 + commit + push，再上服务器 pull / apply；服务器手改后立即 commit 回仓库，防被 pull 覆盖。
- **小内存主机（≤2G）构建镜像必须限流**：`docker build --memory=<峰值预算> --memory-swap=<含 swap>`；部署脚本内置限流参数，避免裸跑无限流构建（构建超限只失败、不拖垮宿主）；长构建一律后台 + 日志轮询，**轮询间隔 ≥45s，不 busy-poll**。
- **云主机自动配置代理会覆盖手动改动**（如 cloud-init 每次重启重生成网络配置，手动 netplan 修改不持久）：持久化修改必须**禁用其接管**（如 `99-disable-network-config.cfg`），改后立即生效 + **重启后再复验**；配置类改动同步运维文档并标"勿回滚 / 勿改回"。
- **受限环境先摸清通道边界**（哪些端口 / 协议可用、哪些目录可写、哪些进程通道可用）：TLS 不通时——变更 / 推送交用户侧执行（给一条可粘贴指令）；验证走可用通道（如 SSH 到远端本地验证）；git 配置用 `git -c <key>=<val>` 命令级覆盖（不写配置文件）；无法从受限环境观测的项诚实声明"需用户侧确认"。
- **跨 shell 远程命令**（PowerShell↔bash 等）：统一用 ASCII、避免中文与嵌套引号；curl `-w` 格式串用单引号防本地解释；复杂配置内容 base64 编码传输；远程命令先小步验证再组合。
- 检查项：部署脚本带产物验证与限流参数；异常先看日志；重启后复验关键配置（DNS / 证书 / 上游）。

### 1.11 存量大范围改造（增量推进 + 兼容别名）
- 大范围替换（全站硬编码文案 / 常量 / 命名）**禁止一次性全量迁移**：分阶段"建体系 + 新功能遵守 + 存量按模块迁"。
- 数据与代码分离（文案 / 配置独立成文件）；迁移期提供**兼容别名**保住旧引用，降低回归面。
- **"结构先上、正文后补"必须登记显式跟踪项**（责任人 / 轮次），交付物附"接入待办清单"；发布前 grep 占位文案兜底核查。
- 检查项：key 规范先入规范文档；新内容走新体系；占位符 / 空表清单清零或有排期。

### 1.12 工具化分工：确定性交程序，判断归 Agent
- **确定性工作一律交脚本**：切字段 / 解析 / 生成 / 校验 / 格式化等确定性输出由程序完成（标准库即可），Agent 只读产物做审计与判断（找异常 / 定下一步）；**不用 LLM 做确定性生成**（慢、非确定、需复验）。
- **"结构化 ≠ 双份事实源"**：要 CSV / 看板时，不建第二份事实源（双写必漂移）——用程序从唯一事实源**派生只读产物**（如"状态一览 + CSV 快照"，带生成时间戳 + 一致性校验：重复编号 / 空状态 / 未知状态 → 警告），产物标"勿手改"，改源表后重跑刷新。
- 检查项：台账改后跑派生脚本；产物含时间戳；警告为 0（编号唯一、状态合法）。

## 2. 架构准则

### 2.1 接外部服务先做"最小真调冒烟"
- 新接 LLM / 第三方服务 / 第三方库，第一动作是真调一次，逐字段核对响应结构，再写解析层。
- 解析层对关键字段缺失做回退（如推理模型的 `reasoning_content` 回退）。
- 检查项：解析函数有关键字段回退；冒烟用例覆盖结构差异。

### 2.2 重试与失败：硬上限 + 快速失败
- 重试次数设硬上限；串行 / 编排器对"连续 N 次同类错误"判服务不可用、立即停并标记失败。
- 失败原因落错误字段供前端展示。
- 检查项：重试上限可配置；编排器有连续失败快速中止；失败态展示可读原因。

### 2.3 计费 / 成本口径先于用量统计
- 接入前确认完整计费口径（计费字段、缓存命中、峰谷、并发上限）；usage 记录完整字段。
- 成本口径必须含"辅助调用"（校验、伴随调用），第一天就把全部调用类型纳入计量并分开配档。
- 检查项：usage 含缓存命中字段；成本脚本支持峰谷与缓存命中；单价可配置。

### 2.4 确定性计算先行，LLM 只保留必要步骤
- 每个 feature 先答"能否确定性计算 + 内置文案"；LLM 只保留"把确定事实串成解读"一步。
- 检查项：有确定性方案段落；每个 LLM 调用点接计量与扣费。

### 2.5 用户可见数据要检查本地化 / 结构
- 第三方库产出的用户可见文本，接入后遍历全部输出字段抽检语言；对漏网项做映射 / 本地化层。
- 检查项：用户可见字段一致性抽查；对残留有映射表。

### 2.6 跨源聚合必须有归一化层
- 任何"把异构来源归并为有限类别"的地方都要有归一化映射（关键词 → 固定标签）。
- 要模型产出多样化时，既要 prompt 显式要求，也要代码层兜底归并。
- 检查项：聚合前有归一化；prompt 有覆盖约束；验收时核对输出类别是固定集合。

### 2.7 框架性文字放 UI 层，不混进数据
- 免责 / 版本号 / 水印等由 UI 统一组件渲染；数据字段保持纯净。曾污染则重新生成或做剥离。
- 检查项：内容字段不含框架文字；框架文字只在 UI 统一位置出现。

### 2.8 配置 / 常量名显式映射
- 字段名含"缩写拼接"可能映射错：显式声明别名映射（如 `validation_alias`）+ 本地断言。
- 检查项：新增配置字段必写显式映射 + 本地断言；部署后双重核对再启用。

### 2.9 路由 / 回退保留后端语义
- 静态 SPA fallback 必须排除后端路由前缀（api / admin 等）的 404 语义；静态资源一律根绝对路径（防深层路由相对路径解析错误）。
- 检查项：fallback 排除所有已注册前缀，非法 key 返回 4xx 而非 200 HTML。

### 2.10 幂等 + 缓存命中是数据型功能的默认设计
- 凡"同一逻辑实体可被多入口触发"的功能，默认幂等键（user + entity + scope）+ 缓存复用，接口天然可重入。
- **幂等拦在任务入口**：触发端点先查已有 running / pending（确定性任务可含 succeeded）再建，返回既有 id；落库用"查同键 → 更新否则新增"，键必须唯一。
- 检查项：新增创建型接口先答"重复调用会怎样"；多入口共用同一数据时配直达 + 自动加载。

### 2.11 单一事实源
- 任何"形态 / 状态"只允许一个权威声明；交接时给"权威清单"并逐项核对文件 / commit 存在性。
- 发现冲突当场标"以 X 为准"，不静默。
- **双数据源 / 双快照并存**：合并前先做"分层降险"比对（共享渲染层 / 展示层收敛 / 数据层统一），标注各层改动量与暂缓项，测试按层验收。
- 检查项：权威运行件写入文档；文档引用的文件实际存在。

### 2.12 长任务四件套
- 长任务必有：可轮询状态、进行中任务复用（幂等）、重启后恢复（已完成子步零成本复用）、按子步计量。
- **对无状态外部依赖，"续接"落地为"断点缓存 + 幂等入口 + 显式状态机 + 轻量上下文提示"**，并尽早向需求方说清边界。
- 检查项：重复点击只建一个任务；孤儿任务有失败 / 恢复语义；已成功子步重跑不重复扣费。

### 2.13 常驻服务 + 保真降级链
- 高复用重依赖走常驻；保留降级路径；分层各自容错，"正确性优先、不阻断主链"。
- 检查项：重复加载的重依赖常驻化；降级路径字节级保真；任一层失败自动回退并告警。

### 2.14 选库先盘点仓库现成能力
- 引入外部依赖前先盘点"已在仓库里的能力"；外部库只按**增量缺口**引入，差集为空则跳过并留档理由。
- 检查项：列出现有依赖能力清单；每个候选标注差集；跳过的写理由。

### 2.15 数据迁移与保留字（老库路径测试）
- 新增列名 / 表名前先查目标数据库保留字（SQLite：default / order / group 等）；裸 SQL 迁移对保留字加引号。
- **迁移测试必须覆盖"既有 schema + 增量 ALTER"路径**，不能只测新建库——ORM 建新库会自动加引号，掩盖裸 SQL 迁移问题；本地与生产库形态差异是这类 bug 的温床。
- 检查项：新列名无保留字；迁移语句对关键字加引号；有老库迁移回归用例；部署前用"已有库"冒烟迁移。

### 2.16 并发改造前置：审计共享可变状态
- 改并发前先开一张"共享可变状态清单"（全局变量 / session / 账本 / 计数 / 自增列），逐项写清隔离策略（如按 task 隔离）或串行化。
- 数据库并发写先开 WAL + busy_timeout；"查缓存 → 落库"必须原子或幂等。
- 检查项：并发改造前清单逐项过；计费 / 计数 / 幂等逻辑不依赖未隔离的模块级状态。

### 2.17 阶段式长流程：后端显式状态字段
- 阶段式流程（多步串联）后端在每阶段完成时写显式状态字段；前端主操作按钮按状态机分支导航，**不用计数 / 布尔近似推断阶段**。
- 检查项：每个"阶段完成"同步更新后端状态；主按钮穷举全部状态分支。

### 2.18 发布与运行环境（本地 ≠ 生产）
- **不进 git 的构建产物必须显式进镜像或构建期生成**（.gitignore 排除会悄悄丢失运行时依赖）；环境差异（DNS / 时区 / 跨境网络 / 容器 DNS ≠ 宿主机）先探测后部署，不假设与本地一致。
- 服务器每个非临时配置必须有对应 commit；pull 前 `git status` 干净。
- 检查项：部署前核对镜像依赖清单；目标机实测 DNS / 上游连通；容器内 `getent hosts` 目标域名可解析。

## 3. 交互准则（多角色协作）

### 3.1 多角色并行改同一文件必然冲突
- 单文件真相源必须串行；多人改同一文件先约定"commit → push → pull 一版"的检查点节奏。
- 编辑前检查文件 mtime / 内容；edit 被拒 = 有并发写者，**重新 read 再改**，勿强行覆盖。
- 只 add 自己本次改的文件；共享文档是冲突高频区，先 pull 再改、改完尽快 commit。
- **中文文件只经受控编辑 / 显式 UTF-8 读写，禁用整文件 shell 覆写**（PowerShell 默认编码会致乱码）；误写用 `git checkout` 恢复后小步重做。
- 检查项：开工前 `git status` / `git log -3` 全量盘一遍；改任何共享文件前确认基于最新 HEAD。

### 3.2 责任矩阵：谁产元素 ≠ 谁落地代码
- 交付文档里"组件 / 交互规范"与"素材"常混在一起；先逐条标注"已入库 / 待我实现 / 待他人实现"。
- 排期时把"设计规范 → 代码实现"的空档显式列出，不默认有人已做。
- 检查项：交付物清单每一项都有责任标注；歧义先问需求方。

### 3.3 契约文本必须写全字段
- 前后端 / 多角色并行时，主会话先写"契约文档"（每个接口 / 字段的精确清单 + 返回示例），各方照契约实现。
- **横切决策前置**：路由 / 计费 / 命名 / 数据模型等全站口径，先出"契约文档 + 显式决策清单"让需求方逐项拍板，结论写入台账备注作为现行约束。
- 检查项：契约含完整字段清单；待拍板横切项先固化进台账 / 契约。

### 3.4 测试 / 契约文件是活的，不是只读
- 读测试 / 契约文件后，跑之前再 re-read 一遍；发现"我的实现 vs 测试期望"矛盾时，先确认文件是不是最新。
- 检查项：全量跑前 `git status` 看测试文件是否被并行改动；单测失败先区分"测试隔离缺陷"与"真实契约不符"。

### 3.5 交付物末尾固定"带默认建议的待确认单"
- 每个决策点给"默认建议 + 后果"供确认 / 否决；用户回复后先 diff"新增了什么、改了哪些旧结论"再落文档。
- 工程性 / 重方案需求：先给"方案对比表（含代价 / 风险 / 推荐）"→ 需求方拍板 → 再登记 REQ（含验收目标与明确不做项）。
- 检查项：开放问题都带推荐项；回复后先 diff 再落文档。

### 3.6 高 churn 期不要过早固化编号文档
- 需求震荡期用"单页结论清单"交流；连续 ≥2 轮无结构变化再固化编号文档；逻辑方案与 UI 方案分文件隔离。
- 检查项：交叉引用指向"稳定结论"而非章节号。

### 3.7 共享工作区 = 跨 session 唯一记忆
- 会话上下文不跨 session，只有落盘可传；每 session 结束更新"状态快照 + 待办(带 owner) + 勿回滚护栏"。
- 新 session 先读交接再动手；**断点恢复先核对磁盘 / 文件实际状态，不信任 job 注册表 / 后台任务表**。
- 检查项：结束前更新交接；待办标 owner；护栏单独一节。

### 3.8 外部依赖先验证可信性
- 外部依赖写进方案前验证存在性 / 维护 / license；不可及就"机制自研 + 内容多源改写"兜底。
- 检查项：链接可访问；license 允许；有零依赖兜底方案。

### 3.9 启动即定义"不做清单 + 约束决策表"
- 验收 / 禁止 / 边界写成决策表；新需求先对照，冲突则显式修订而非悄悄改。
- **高风险 / 高成本实现设"开发门禁"**：先交方案书 / 素材表 / 评估（资源、并发、存储），需求方审批后才编码；门禁写进需求行。
- 检查项：决策表含范围 / 引擎 / 付费 / 合规；关键项备注含"方案经审批后开发"。

### 3.10 里程碑 = 可勾选闭环 + 四层测试
- 每阶段最小可独立验证闭环；单测 / 集成 / 端到端 / 回归四层；回归不破坏旧链。
- 检查项：每里程碑可独立上线验证；含回归；owner / 阻塞标清。

### 3.11 角色与决策权分离（owner 模式）
- 动工前问清"用户拍板项 / 自己自主项"；用户决策项的默认动作 = 出方案占位等确认。
- 检查项：每开放项有 owner；自主边界明确；阻塞项显式挂起并记录。

### 3.12 小步交付 + 三行小结锚点
- 每个交付 1–2 段方案 + 默认建议，自包含可评审；轮尾留"当前结论 / 待办 / 待确认"三行。
- **每完成一个可独立验证的块就 commit**；被打断后恢复按"三查"：git log / status（拿最新）→ 表状态（谁动了什么）→ 待办清单，再决定下一步。
- 检查项：恢复时不重读全文即可接上。

### 3.13 诚实声明能力边界
- 明确说明能做什么、不能做什么（尤其日志 / 运行态 / 成本 / 外网 / 真机浏览器等实时信息）；不假装看见。
- 环境约束前置声明并约定分工（我能自动验 API / 逻辑、不能真机 UI / 外网 → 出清单 + 自动验，对方真机验）。
- 检查项：能力边界在关键处（成本 / 日志 / 运行态 / 权限）主动声明。

### 3.14 共享台账是"单点争用"：默认并发写者存在
- 台账（需求表 / Bug 表）= 单一事实源 + 单点争用；把并发写当默认前提而不是例外。
- 编辑纪律：动共享台账前先 read 锚点；用**短且唯一**的锚点串，插多行用"唯一尾串一次替换为整段"；同一锚点只做一次插入。
- 撞 EIO / "file changed since read" = 有并行写者：**重读再改**，不强行覆盖、不无限重试。
- **EIO 报错 ≠ 一定没写入**：报错后重读确认目标行是否已落盘，避免重复插入或误判失败。
- 检查项：每条编辑后 `grep` 目标 ID 恰好一行；EIO 后重读目标行；关键行（编号 / 状态 / 变更记录）写后自检。

### 3.15 编号唯一发放（防撞号）
- 需求 / Bug 编号由**唯一协调者**（需求管理员）统一发放，多写者各自记"现用最大号"会在并发窗口撞号。
- 登记前 `grep` 现用最大号；发现撞号**冲突顺延**并在两处备注留痕（保留先登记 / 已落盘者，另一方顺延）；定期审计编号唯一性。
- 检查项：登记前 grep max；插入后 grep 确认唯一；变更记录注明顺延原因。

### 3.16 口径修订必须联动状态
- 每次登记 / 修订需求或 Bug 必须同步写对状态：口径演进导致**返工 → 状态退回 🟡/🔵** 并在备注注明；🟠 只挂"已实现待验收"；🟢 仅测试组可设。
- **登记后要追踪实况**：不能凭"刚登记 = 还没开发"的假设——登记后跟进并行开发是否已动工 / 完成，按实况修正状态与备注。
- 每批收尾做一次"我涉足条目"的状态审计。
- 检查项：落表后 grep 列出涉足行状态列对照实际阶段；状态变更连同理由写进备注。

### 3.17 先复述理解再落表
- 收到口语化 / 引用历史上下文的需求时，先用自己的话**复述理解**（业务视角：你要什么 → 对用户影响）→ 列出疑问（带默认建议）→ 需求方确认 → 才落表。
- 需求引用了没有出处的内容（他人历史对话 / 文档），**明说"这段原始描述我没有"**，请对方说明或指位置；宁可标注"待需求方确认"，不推断成文。
- **关键需求（安全 / 权限 / 暴露边界类）必须复述"最终目标"并问清目标场景**（谁能访问、从哪访问），不抠字面。
- 检查项：落表前存在"复述 + 待确认单"；引用历史上下文有出处；未确认项在备注标"待需求方确认"。

### 3.18 核实现状再登记（证据来源标注）
- 登记涉及现状 / 数字 / 文件内容的条目前，先读源码或文档核实；与用户描述冲突以实测为准并备注"已核实"。
- 无法定位的标"待复现 / 待补信息"并写明疑点；每条登记注明证据来源（已核实 / 待复现 / 待确认）。
- **缺陷登记前先本地最小复现 + 三层归因**（前端逻辑 / 后端 API / 环境），落表含"现象 + 根因 + 期望"，达不到可执行粒度先标"待复现"。
- 检查项：登记证据来源注明；无法证实不落为事实。

### 3.19 用户反馈收口前做 S0/S1 扫描
- 真机 / 批量反馈收口前做一次"S0/S1 扫描"：安全 / 资金 / 数据类问题**单独分流**（登记 → 状态跟踪 → 优先修复 → 线上风险提示），不混入功能 🟢 列表。
- 对疑似越权 / 泄露问题至少做只读复核（如后端端点审查是否干净），把排查面收敛后交给开发。
- 检查项：收口消息单列"S0/S1 未闭环项"；"用户说都好了" ≠ "全部安全"。

### 3.20 交付闭环：呈现指引 + 接入跟踪
- 内容型交付（文案 / 素材）附**呈现指引**：必须项（接入点 / 数据 / 合规 / 无占位残留）+ 自由项（开发自选并说明）+ 兜底（不确定先提问、不得搁置）。
- "结构先上"项登记显式跟踪（责任人 / 轮次）；交付物附接入待办；发布前 grep 占位符兜底。
- **对外话术标注权威来源**（品牌 / 需求方定稿），开发不自行定调；产品文案与工程说明分层存放。
- 检查项：新交付单确认落在交付物中心并附接入点与验收约束。

### 3.21 口径演进用"supersede"，不破坏已验收历史
- 需求口径演进优先**"新行 supersede + 旧行保留为历史 + 备注互链（取代 / 取代自）"**，避免破坏已验收记录与验收历史混淆。
- 检查项：需求变更先问"新增行还是改旧行？"；supersede 双向可追溯；不私自置 🟢。

### 3.22 跨角色可见性告知
- 改了对方不可见的东西（配置 / 环境 / 服务器 / 网络），必须写进共享文档并主动告知"改了什么、为什么"——对方只能基于可见信息推断，缺告知就会猜，猜就错。
- 检查项：排查对方报错前先查"最近谁改了相关配置 / 变更记录"。

### 3.23 文件删除与"待确认"生命周期
- **删除工作区文件前，先查交付回执 / 需求单 / 文档索引**是否登记过该路径——并行期出现的"陌生文件"可能是他人刚交付的产物，仅凭文件名 / 体积臆断归属是事故。
- 并行 Session 活跃期间，对非本任务产出的文件**只读不删**；确需清理先标注"待确认"。
- 交付物 / 素材默认走"**待确认 → 暂存区 → 确认后纳入**"生命周期：未确认前不纳入项目。
- 误删后优先查**产出方缓存 / 生成脚本**能否重建（能重建则损失为零），再考虑请对方重交。
- 检查项：删除命令前 grep 过文档索引？该路径是否在他人交付回执资产清单？能否从缓存 / 脚本重建？

## 4. Agent 运行成本准则（Token 经济）

> **适用前提**：项目采用**自治 Agent 模式**（主 Agent + 子代理 + 并行 Session 全自动跑完软件工程）。此模式下 token 消耗与"人 + 代码助手写 MVP"**不是一个量级**——这是模式使然，不是单纯的浪费，但必须被治理。
> 典型量级参照：同类项目出现过 **34 亿 token / 月** 的消耗——普通"人 + AI 助手写 Web MVP"根本达不到，只有"循环思考 + 工具调用 + 反复重试 + 大量上下文回放"才会产生。

### 4.1 成本结构（钱烧在哪，四层）
1. **主会话上下文回放（大头）**：每轮工具调用都携带完整历史；常驻大文档（守则 / 需求表 / Bug 表 / 架构）在会话中反复全额读入；大文件整段读一次就是几十万 token；**会话不收敛 → 越到后面每轮越贵**。
2. **子代理（每个都是一次完整烧钱）**：每个子代理有独立上下文（读大文件 + 写大段代码 + 跑验证）；**用"继承主会话上下文"的通道时，每次启动还回放主会话已积累的全部历史**（主会话越肥，启动越贵）；子代理交付后主 Agent 的验证（读 diff / 跑门禁 / grep / 台账编辑）同样全额回放。
3. **并行 Session**：每个并行角色（美术 / 文案 / 需求管理 / 测试）独立消耗；素材类反复迭代（重出图、重跑、rejected 帧）尤其密集。
4. **反复重试与循环**：通道失败重试、构建卡死重启、排查试错——**每次失败 = 全量上下文回放 + 新输出**。

### 4.2 与"人 + 助手"模式的差异（为何量级不同）
| 维度 | 人 + 代码助手 | 自治 Agent 模式 |
|---|---|---|
| 上下文 | 单轮问答，用完即弃 | 长会话 + 每轮回放全部历史 |
| 文件访问 | 人只看需要的几行 | 框架可能整段读入大文件（MB 级） |
| 执行者 | 1 人 + 1 助手 | 主 Agent + N 子代理 + 并行 Session 同时烧 |
| 失败成本 | 人看一眼重敲 | 完整重试 = 全量回放 |
| 轮数 | 几十轮 | 数百轮工具调用 |

> 结论：不是"用 AI 写代码"，而是"**让一个自治 Agent 团队替你做完整软件工程**"（架构 / 拆任务 / 派活 / 验收 / 台账 / 部署全自动），每一层都吃 token——这是模式的设计使然，应在启动时就向需求方说明。

### 4.3 降本纪律（可执行）
1. **会话收敛**：里程碑 / 阶段结束就开新会话（清空回放），不让一个会话拖几百轮；跨会话上下文由交接文档 + 待办承接。
2. **大文件纪律**：禁止整文件通读——**先 grep 精确定位锚点，再只读命中行**；子代理 spec 直接给文件 / 行号 / 符号。
3. **子代理通道**：优先用**独立上下文**的通道（省掉继承回放）；通道不可用要**修**，不将就。
4. **失败先诊断再重试**：每次盲目重试都是全量回放成本；先判类型（半成品可收口 / 环境问题 / 契约不符）再动手。
5. **常驻文档精简**：每轮注入的守则 / 速览 / 索引越长，累计成本越高——定期瘦身，只留"必须每轮知道"的信息。
6. **并行按需**：并行 Session 只在真正独立的活上开，能串则串。
7. **精确计量交给账本**：不靠"感觉"估 token——用量与成本以厂商账单 / usage 账本为准（确定性统计交程序，见 §1.12），Agent 只做量级判断与降本动作。
