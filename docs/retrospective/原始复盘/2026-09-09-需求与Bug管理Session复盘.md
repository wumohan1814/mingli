## 二、经验清单（按踩坑代价从高到低）

### A. 共享台账并发写（代价最高：写入冲突 + 内容丢失 + 撞号）

**A1. 多 Session 高频共写同一文件 → EIO / 文件已变 / 内容被覆盖**
- 现象：落表过程中多次报 `ReplaceFileW EIO (Win32 1175)` 与 `file changed since read`；一次"变更记录"行被并行写覆盖丢失（当时未察觉，事后审计发现缺失需补回）。
- 根因：需求表 / Bug 表是共享单文件，主开发 Session 与需求管理 Session 同时高频追加/整段写，无锁、无串行化；surgical 编辑与对方写操作在同一文件上撞车。
- 可复用规则：
  1. 动共享台账前先 `read` 锚点，用**短且唯一**的 old_string，插多行用「唯一尾串一次替换为整段」。
  2. 撞 EIO / 文件已变 = 有并行写者：**重读再改，不强行覆盖、不无限重试**；必要时稍等再落。
  3. **EIO 报错 ≠ 一定没写入**：报错后要重读确认该行是否已落盘，避免重复插入或误以为失败。
  4. 涉及关键行（编号 / 状态 / 变更记录）的编辑，写后 `grep` 自检。
- 落地检查项：每条编辑后 grep 目标 ID 恰好 1 行；EIO 后重读目标行；变更记录行写后抽查是否存在。

**A2. 全局唯一编号并发漂移 → 撞号（REQ-132 双行）**
- 现象：我登记"档案下拉"用 REQ-132，并行 Session 同时把 REQ-132 给了另一个需求，表内一度出现两条 REQ-132。
- 根因：无单一发号器，多写者各自记"现用最大号"，并发窗口内撞号；登记与落表之间无跨 Session 的领取动作。
- 可复用规则：编号由唯一协调者（需求管理员）统一发放；登记前 `grep` 现用最大号；发现撞号**冲突顺延**并在两处备注注明（保留先登记/已落盘者，另一方顺延）；后续审计定期校验编号唯一性。
- 落地检查项：登记前 `grep '^\| REQ-' | tail`；插入后 `grep` 确认唯一；变更记录里注明顺延原因。

### B. 登记与状态机（用户本轮明确指出）

**B1. 口径更新与状态未联动 → 返工项停在"待验收"**
- 现象：REQ-084 口径已定稿为"返工 = 需要开发去做"，但我没把状态从 🟠 待验收 退回 🟡 待开发；用户指出"这是需要开发去开发的，不是等验收"；同时另一条开发已完成但状态仍停在 🟡（应为 🟠 待验收）。
- 根因：把"内容/口径修订"和"状态机"当成两件事分开处理，漏了联动；对状态语义把握不准（🟠=已实现待验收，不等于"还需要开发"；口径变更→返工必须退回 🟡/🔵）。
- 可复用规则：**每次登记 / 修订需求或 Bug，必须同步写对状态**（🟡 待开发 / 🔵 开发中 / 🟠 待验收 / 🟢 已验收）；口径演进导致返工 → 状态退回 🟡/🔵 并在备注注明"返工待开发"；🟢 仅测试组可设。每批收尾做一次"我涉足条目"的状态审计。
- 落地检查项：落表后 `grep` 列出涉足行状态列，对照实际阶段修正；状态变更连同理由写进备注。

**B2. 先复述理解再落表（需求方硬性要求）**
- 现象：用户质疑"你确定你理解我什么意思吗？开发能理解这条需求吗？"——我基于用户片言 + 旧需求推断登记"太初先生 Q 版"桌面宠物式，未先复述、也未点明"原始对话我没有"。
- 根因：收到口语化/引用历史上下文的需求时，跳过"确认理解"直接落表；引用了没有出处的内容却未明说。
- 可复用规则：**每条需求先用自己话复述理解（业务视角：你要什么 → 对用户影响）→ 列出疑问（带默认建议）→ 需求方确认 → 才落表**；需求引用了我没有的历史对话/文档时，明说"这段原始描述我没有"，请对方说明或指位置；不确定绝不硬写（宁可标注待确认也不推断成文）。
- 落地检查项：落表前存在"复述 + 待确认单"；引用历史上下文有出处；未确认项在备注标"待需求方确认"。

**B3. 三通道拆解 + 查重归口（可复用做法）**
- 现象：用户一批批量反馈（独立页 / 交互重做 / 工具新增 / 后台问题等），拆成 Bug / 需求 / 口径变更三通道；对"已含于既有需求"的归口不新增（如起卦独立页归口导航重构、塔罗扇形/阵型归口两段式需求），对同页多处改聚合一条（如择日 v2），样式类归 Bug。
- 根因/规则：批量口语反馈先给"拟条目表 + 关联 + 待澄清点"，按三通道拆解；**先查重全表（含已归档）再登记**；归口项在既有行备注标"归口于 REQ-xxx"，避免双行漂移与重复登记；同主题多表象聚合、阻断/回归独立高优。
- 落地检查项：新条目先 grep 全表查重；归口/聚合决策让需求方拍板（带默认）后落表。

**B4. 核实现状再登记，不凭印象**
- 现象：用户报"某 prompt 空白 / 某 prompt 太长含全法"，我读盘核实发现"空白"实际非空（469 行）、"太长含全法"的是另一文件、用户说的那个其实很小——据此纠正描述并登记，无法证实处标"待复现"。
- 规则：涉及现状/数字/文件内容的登记，先读源码或文档核实；与用户描述冲突以实测为准并在备注注明"已核实"；无法定位标"待复现 / 待补信息"并写明疑点。
- 落地检查项：每条登记的证据来源注明（已核实 / 待复现 / 待确认）。

**B5. 交付物（素材/文案单）流程**
- 现象：塔罗/雷诺曼素材需求单、文案交付等跨 Session 交付物按约定进 `docs/exchange/`（待确认/待接入），接入后归档；开发侧已在此位置产出示意与素材单供需求方确认。
- 规则：跨 Agent / Agent↔需求方 的交付类文档统一进 `docs/exchange/`；接入完成或确认后按约定归档，并同步索引。
- 落地检查项：新建交付单时确认落在 `docs/exchange/`；确认/接入后更新状态与索引。

## 四、可复用结论

1. **多 Session 协作下，台账是"单一事实源 + 单点争用"**：所有写入都要"短锚点 + 撞写重读 + 写后自检 + 编号唯一"，把并发冲突当默认前提而不是例外。
2. **状态机是协作的语言**：口径一变，状态必须跟着变（返工=退回待开发）；"待验收"只表示"已实现等验收"，不能用来挂"还没开发"的条目。
3. **登记前先让对方确认我理解对了**，尤其当需求引用了我没有的上下文——这是需求管理 Session 的立身之本，比登记速度重要得多。
4. **所有对外结论要么有出处、要么标"待确认/待复现"**，不凭印象、不编造、不脑补。
