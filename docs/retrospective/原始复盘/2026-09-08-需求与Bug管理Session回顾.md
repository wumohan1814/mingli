## 二、经验清单（按踩坑代价从高到低排序）

### A. 协作协议（代价最高：曾致文档损坏、误提交他人成果）

**A1. 并发共写同一文档 → 行并错位 / 整表损坏 / 全文件乱码**
- 现象：多人异步同时编辑需求表，多次出现行被并成一条、REQ-083 并入 REQ-081 行内；一次 PowerShell 整文件覆写把 UTF-8 按 ANSI 重解码，全表乱码。
- 根因：①表格单文件高并发无锁；②用 shell 整文件读写（编码隐患）；③大 old_string 编辑易踩并发 mtime 检查。
- 可复用规则：**共享文档由唯一协调者串行落地；禁用整文件 shell 覆写；编辑用最小锚点；改前 read、失败即 git checkout 恢复后小步重做**。
- 落地检查项：编辑前 read → 编辑用短且唯一 old_string → commit 前 `git diff --cached --stat` 核对规模与内容 → 消息与内容必须一致。

**A2. commit 抢跑并打包了他人未提交成果 / 消息与内容不符**
- 现象：我编辑失败后仍执行 `git add && commit`，把并行 Session 未提交的真机复验更新以「BUG-011」消息提交（内容却是别的事）。
- 根因：编辑与提交未绑定校验；未先查 `git status/diff`。
- 可复用规则：**任何 commit 前必须确认 staged diff 只含本人变更；发现错标立即 `--amend` 改消息并如实汇报，绝不掩饰**。
- 落地检查项：`git status` → `git add <仅目标文件>` → `git diff --cached` 人工核对 → commit。

**A3. 全局唯一 ID 在并发下漂移 / 行被重排**
- 现象：REQ-078~080 编号被并行占用，我方条目顺延（081/095 等）；多次行序整理造成排序混乱。
- 根因：无单一发号器；多写者各记各的 max。
- 可复用规则：**全局递增编号由唯一协调者发放；写入前先 grep 现用最大编号；冲突顺延并在备注注明**。
- 落地检查项：登记前 `grep '^| REQ-\d' | tail`；插入后复核唯一性。

**A4. 状态即沟通，但「谁有权置终态」易被越界**
- 现象：协议规定 🟢/⚪ 仅测试组可设、开发最多 🟠+备注；多次出现我或并行方代设/回退。
- 可复用规则：**状态机与责任人写进表头；每次状态变更标注操作者与理由；越界即按协议纠正而非另立规则**。
- 落地检查项：设置终态前确认身份权限；备注写「谁、何时、为何」。

### B. 架构 / 文档决策（代价次高）

**B1. 口径演进直接改写已验收行 → 验收历史混淆**
- 现象：REQ-027/040/051/064 等多行被反复 v1/v2/v3 改写；部分旧口径与最新指示冲突。
- 可复用规则：**演进优先「新行 supersede + 旧行保留为历史 + 备注互链」，避免破坏已验收记录**。
- 落地检查项：需求变更时先问「新增行还是改旧行？」；supersede 必须双向可追溯。

**B2. 技术方案问答未先给权衡表就落 REQ → 反复返工**
- 现象：SPA 路由、PWA、背景热更等若先讨论（多页 vs 单页+history、缓存/更新机制、是否引入向量）会显著减少登记返工。
- 可复用规则：**先给「方案对比表（含代价/风险/推荐）」→ 用户拍板 → 再登记 REQ（含验收目标与不做项）**。
- 落地检查项：登记工程性需求前先输出 2~3 方案权衡；REQ 里写明「决策依据 + 明确不做」。

**B3. 大文案库与「占位先行」策略分离**
- 现象：64 卦大意、星座 72 篇、生肖关系文案等体量大，全文一次交付阻塞开发。
- 可复用规则：**结构化 + 占位先行、正文后补并列为独立跟踪项；成稿文档作为验收附件**。
- 落地检查项：每条文案型需求标注「结构先行 or 全文成稿」及后补跟踪位置。

### C. 工作定义（角色 / 目标 / 约束）

**C1. 投喂是口语化大段描述 → 缺结构化登记导致漏项**
- 现象：多轮「大段走查反馈」中，积分 Banner 项曾漏登记，后被用户提醒补上。
- 可复用规则：**收到批量口语需求先拆分候选条目 + 查重映射表让用户拍板，再逐条落表**。
- 落地检查项：先输出「拟条目表（含关联/冲突/待澄清）」→ 确认后登记；逐条对勾防漏。

**C2. 三铁律写入表头：可执行性 / 查重合并 / 开发门禁**
- 现象：含糊描述与同根因重复条目多次出现；美术/动画/记忆/路由类「先方案后开发」约束若不在行内，开发易越界。
- 可复用规则：**登记前确认验收口径与入口位置；同根因多表象合并列入口；重方案型需求把门禁写进备注**。
- 落地检查项：每条含「现象/期望/验收/入口」；重复先 grep；方案型加「先交方案→审批→开发」。

**C3. 中断恢复与收尾协议**
- 现象：多次被打断后上下文依赖「git log/status + 需求表尾部」快速恢复。
- 可复用规则：**每轮收尾固定动作：pull → 更新黑板 → diff 审查 → commit（带编号）→（有凭据再 push）→ Session 交接文档追记**。
- 落地检查项：被打断后先做一次环境快照（log/status/表尾）再继续；长会话定期 commit 防止丢失。

## 三、下一项目启动检查清单（可跨项目直接套用）

1. **黑板先行**：建立「单一事实源」两张表（需求/Bug）+ README 索引；字段、状态机、严重度/优先级写进表头。
2. **发号唯一**：REQ/BUG 编号由唯一协调者发放；写入前 grep 现用 max；冲突顺延留痕。
3. **三铁律成文**：可执行性保证（先确认后登记）、查重合并（同根因合并/supersede 标注）、开发门禁（方案→审批→开发）。
4. **Git 协作红线**：改前 read；禁用整文件 shell 覆写（编码）；commit 前 `diff --cached` 与消息一致性核对；抢跑/错标立即 amend + 如实汇报。
5. **并发防抖**：共享表格文档由协调者串行 commit；双方不同时改同一文件；文档提交后尽快 push（确认代理/凭据可用再承诺 push）。
6. **角色终态权**：写入「谁能置终态」；状态变更附带操作者与理由。
7. **方案先行**：工程性/重方案需求先给权衡表与验收目标（含明确不做项）再登记。
8. **文案占位分离**：大文案结构先行、正文后补并挂跟踪项。
9. **收尾模板**：pull → 更新表 → diff 审查 → commit(带编号) → Session 交接文档追记。
10. **中断恢复**：被打断后先 `git log/status` + 读表尾建立快照再继续。
