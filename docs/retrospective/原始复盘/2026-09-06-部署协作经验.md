## 二、经验清单（按踩坑代价从高到低）

### 架构设计

**E1 · 海外服务器的 DNS 必须用当地可达的 DNS，且改动后必须验证 SSH（最高代价：差点失去访问）**
- 现象：新加坡 ECS 的 DNS 从阿里云内网 100.100.2.136 改成国内 223.5.5.5 后，SSH 全部连不上（TCP 通但 banner 超时）。
- 根因：新加坡跨境访问国内 DNS 超时；sshd 的 UseDNS 对客户端 IP 反解析卡死，banner 不发。
- 可复用规则：① 海外节点用海外 DNS（8.8.8.8/1.1.1.1），禁用国内 DNS；② sshd 加 `UseDNS no`；③ 任何网络改动后用**新连接**验证 SSH。
- 落地检查项：`grep nameservers /etc/netplan/*.yaml` 是海外 DNS？`grep ^UseDNS /etc/ssh/sshd_config` = no？改动后能从新终端 ssh 连？

**E2 · 生产服务器的配置改动必须立即进 git**
- 现象：服务器上直接改的 Caddyfile（bb3a 反代，未 commit）被一次 `git pull` 覆盖丢失，服务中断，排查半天。
- 根因：服务器手改配置与 git 不同步，任何 pull/重置都会回滚。
- 可复用规则：配置先本地改 + commit + push，再上服务器 pull/apply；或服务器改后立即 commit 回仓库。
- 落地检查项：服务器每个非临时配置，是否有对应 commit？pull 前 `git status` 是否干净？

**E3 · 高频重组件要做常驻服务 + 降级 + 限流**
- 现象：排盘每次 subprocess 起新 Node 进程，冷启动 7s、多用户并发内存叠加。
- 根因：进程级冷启动 + 依赖库重复加载。
- 规则：高频调用的重计算（天文/星历/大模型等）做成常驻 HTTP/RPC，留 subprocess 降级路径，加信号量限流。
- 落地检查项：核心计算是否常驻？故障是否有降级？并发是否有上限？

**E4 · Docker 容器 DNS ≠ 宿主机 DNS（split-DNS 丢失）**
- 现象：宿主机能解析 Tailscale MagicDNS（.ts.net），Caddy 容器内 `no such host` → 502。
- 根因：Docker DNS（127.0.0.11）转发不经过宿主机的 split-DNS 路由。
- 规则：容器内依赖域名时，用 IP + 显式 SNI/`tls_server_name`，或给容器配正确 DNS；别假设容器能解析宿主机能解析的域名。
- 落地检查项：`docker exec <c> getent hosts <域名>` 能否解析？

**E5 · 证书自动续期隐含网络/DNS 依赖**
- 现象：Caddy 在 DNS 故障期短暂走 Let's Encrypt staging，修复后自动回正式。
- 规则：证书签发/续期依赖「公网可达 + DNS 正常」；改动网络/DNS 后必须复验证书仍在正式环境、续期路径通。
- 落地检查项：证书在 `acme-v02`（正式）目录？到期续期依赖的 DNS/端口是否稳定？

### 协作协议

**E6 · 多 session/多角色并行，共享文件与配置改动要「立即同步 + 标注防回滚」**
- 现象：我插入交接文档的内容被另一个 session 整篇重写覆盖；Caddyfile 被 pull 覆盖。
- 根因：多写者改共享资源，无同步协议。
- 规则：跨 session 的配置/文档改动快速 commit；在文档里显式写「⚠️ 勿回滚/勿覆盖」+ 原因。
- 落地检查项：关键配置/文档是否有防覆盖机制（git 即时 commit + 醒目标注）？

**E7 · 跨角色协作，改了对方看不到的配置必须主动告知，否则对方只能猜（猜就错）**
- 现象：杭州 agent 看新加坡 403 猜「上游错指 8443」，实际是我按用户要求加的白名单（403 是预期）。
- 根因：对方看不到我的配置，基于不完整信息推断。
- 规则：跨机器/角色改动把「改了什么、为什么」写进共享文档；对方报错时先查「最近谁改了相关配置」再猜。
- 落地检查项：排查对方报错前，是否查过对方/自己的配置变更记录？

**E8 · 子代理大任务易卡「读文件」阶段，须拆小**
- 现象：method-prompts ×9、端到端测试等大任务数轮不落地文件，interrupt 后拆成小任务才推进。
- 根因：单任务输入（读 N 份大参考）+ 输出过大。
- 规则：按「输入量小、产出聚焦」拆子代理任务；卡住先分析（是否读了过量文件）再 interrupt 拆小，不盲目重试。
- 落地检查项：任务需读多少文件？产出是否聚焦到 1–3 个小交付？

### 工作定义

**E9 · 关键需求要复述「最终目标」确认，而非抠字面（安全/权限类尤其）**
- 现象：「只允许通过 Tailscale 访问」被理解为「客户端必须开 Tailscale」，实际是「回程走隧道、客户端公网可达」——导致加错白名单、差点改错 DNS。
- 根因：字面歧义，未验证最终目标。
- 规则：动工前用一句话复述最终目标让用户确认；安全/权限/暴露边界类需求必须问清「目标场景」。
- 落地检查项：是否复述过最终目标？安全边界（谁能访问、从哪访问）是否确认？

**E10 · 角色与约束先定死，再开始**
- 现象：明确「主会话只做架构/契约/评审/验收，底层交 code_flash，任务拆小、不空转」后，协作效率显著提升。
- 规则：项目启动时定义：谁做什么、不做什么；验收标准（测试/冒烟）；禁止事项（如主会话不手写底层、不反复 install）；中断恢复机制。
- 落地检查项：角色分工？验收标准？禁止事项？中断后如何恢复（谁能接手）？

**E11 · 高风险（可锁死）操作前准备逃生通道 + 备份**
- 现象：禁用 SSH 密码登录前先验证密钥登录成功才改配置；改 sshd_config 前先备份。
- 规则：能锁死的操作（SSH、防火墙、DNS）先备好逃生路径（VNC、密钥、备份）；改配置先 `.bak`。
- 落地检查项：此操作失败如何恢复？是否有备份？
