## 二、经验清单

### 类目一：架构设计（按踩坑代价从高到低）

**1. 部署环境 ≠ 本地环境，是最贵的隐藏雷区**
- 现象 → 根因 → 规则 → 检查项
- 现象：本地全绿，线上排盘 5 法全降级、LLM 502、SSH banner 超时。
- 根因：`.gitignore` 把 `vendor/mingyu-core/dist` 与 `node_modules` 排除 → git 不携带 → 镜像缺运行时依赖；容器 DNS 用错；宿主机 DNS 被改成本地不可达的国内 DNS。
- 可复用规则：**一切"不进 git 的构建产物"必须显式进镜像或在构建期生成**；环境差异（DNS/时区/跨境网络）须先探测后部署，不假设与本地一致。
- 落地检查项：部署前逐项核对 `.dockerignore`/`Dockerfile` 覆盖全部运行时依赖；用目标服务器实测 DNS 解析与上游连通性。

**2. 改并发前，先审计共享可变状态**
- 现象：断前尘串行→并行的改造中，逐法扣费不准、SQLite 报 `database is locked`、同一 method 被并发重复落库。
- 根因：LLM usage 账本是模块级 dict（并发串扰）；SQLite 未开 WAL/busy_timeout；「查缓存→落库」非原子。
- 可复用规则：**凡涉及计费/计数/幂等/账本的逻辑，在引入并发前逐项确认共享状态被隔离（如 `contextvars` 按 task 隔离）或串行化**；SQLite 并发写先开 `WAL + busy_timeout`。
- 落地检查项：并发改造前开一张「共享可变状态清单」（全局变量、session、账本、自增列），逐项写清隔离策略。

**3. 幂等拦在任务入口，不靠缓存碰运气**
- 现象：用户刷新/重进 → 同一 case 冒出 3 个 running job → 同一 method 扣 3 次费、`method_results` 多出 6 行重复。
- 根因：创建 job 的端点无幂等检查；并发下缓存命中失效（job A 未落库时 job B 查到空）。
- 可复用规则：**异步任务的触发端点必须先查已有 `running/pending`（确定性任务可含 `succeeded`）再建**；落库用「查同键→更新否则新增」且键要唯一。
- 落地检查项：每个「点一下就建后台任务」的端点，必须有幂等分支与返回既有 `jobId` 的路径。

**4. 无状态外部依赖的「续接」，要翻译成数据层可恢复机制**
- 现象：需求方要「服务器重启后让 LLM 继续生成」，但 DeepSeek `chat/completions` 无状态，无法续接生成到一半的响应。
- 根因：「session/续接」被理解为对话续接，实际只能做到缓存跳过已完成 + 上下文注入 + 任务状态机恢复。
- 可复用规则：**对无状态依赖，把「续接」落地为「断点缓存 + 幂等入口 + 显式状态机 + 轻量上下文提示」，并尽早向需求方说清边界**，避免按错误预期设计与返工。
- 落地检查项：任何「恢复/续跑」设计前，先书面确认外部依赖是否支持真正的状态续接。

**5. 长流程必须有后端显式状态字段，前端按状态机导航**
- 现象：断前尘跑完但未校准的用户，点「继续」直接进预测长 loading，跳过了校准站。
- 根因：后端 `case.status` 未随断前尘/预测更新；前端用 `methodCount` 近似推断阶段。
- 可复用规则：**阶段式长流程，后端在每阶段完成时写显式状态字段，前端主操作按钮按状态机分支（而非计数/布尔近似）**。
- 落地检查项：每个「阶段完成」是否同步更新后端状态；主按钮是否穷举全部状态分支。

### 类目二：协作协议（多 session / 多角色）

**1. 「谁写代码」必须在开工前定死并遵守**
- 现象：主代理两次亲自写代码被用户明令禁止（被纠正后才收敛为全程 delegate）。
- 根因：主代理默认"顺手写"破坏约定；架构评审与实现职责混在一起。
- 可复用规则：**主代理只做架构、验收、编排、运维操作；一切文件实现派发子代理**。子代理 prompt 必须 self-contained 且含精确 old/new 或改动锚点。
- 落地检查项：开工时向用户确认「允许主代理直接做的操作清单 vs 必须 delegate 的清单」，并写入 session 开头。

**2. 并行度按文件/模块切，同一文件的改动串行**
- 现象：后端与前端子代理并行时，彼此在工作区看到对方的中间态改动，报告里互相「提醒未触碰 XX」造成噪音与误判风险。
- 根因：并行任务缺少「文件归属矩阵」约束。
- 可复用规则：**并行子代理按文件互斥切分；每个 prompt 里显式声明「不要动这些文件」**。
- 落地检查项：派发并行任务前画出「任务 → 文件」矩阵，确认无交集。

**3. 子代理报告只是线索，验收必须亲验**
- 现象：某子代理报告「排盘夹具漂移、测试失败」，实为其 stash 中间态所致，复跑全绿；多次「已修好」需亲自读 diff/线上探测才可信。
- 根因：把子代理的自述当作结论，而非证据。
- 可复用规则：**固定验收三步：亲自读关键 diff → 跑语法/测试 → 线上/行为探测**。
- 落地检查项：每次 delegate 返回后执行「读 diff → node/AST 自检 → grep 关键点」；不信单方面「passed/failed」。

**4. 连接类故障分层排查，勿过早归咎单一变量**
- 现象：SSH 反复 `banner` 超时一度被归咎于 VPN，实为服务器宿主机 DNS 被改成国内 DNS、`sshd` 反向解析卡死。
- 根因：TCP 通（端口 OPEN）≠ 应用层通；把现象直接贴到最常见原因上。
- 可复用规则：**故障先做探测矩阵（端口/TCP/应用层数据/DNS/配置），逐层排除后再换假设**。
- 落地检查项：每次网络故障记录「TCP 通？应用层通？DNS 上游？最近改动？」四问。

### 类目三：工作定义（角色 / 目标 / 约束）

**1. 验收标准写进派发 spec，而非留在口头**
- 现象：多轮「以为修好」实际交互不对（原生 prompt 弹窗、跳过校准卡 loading）。
- 根因：任务描述给了改动目标，没给「可执行的验证断言」。
- 可复用规则：**每个子代理 spec 末尾必须附「完成后验证」清单（语法命令/测试/线上探测点），作为唯一验收口径**。
- 落地检查项：spec 模板是否含可复制执行的验证命令。

**2. 任务拆小、单目标、可独立验收**
- 现象：积分 + session + 并发三个大改动交错在同一批文件，返工与相互等待多。
- 根因：单次派发目标过多，依赖链长。
- 可复用规则：**单子代理单目标；跨文件大改造拆顺序 phase（先基础设施如 config/DB，再业务）**。
- 落地检查项：每个任务是否能在 1–2 轮内完成并独立验证。

**3. 线上数据修复与代码修复分轨**
- 现象：重复 method_results（15 行）、余额 -327 需立即恢复；代码防复发修复却受制于 VPN/发布节奏。
- 根因：把「就地清数据」与「代码修复」捆成一个发布动作。
- 可复用规则：**线上脏数据就地 SQL 修（快），根因代码修复走正常发布（稳），两者独立追踪、独立验证**；数据修复需先备份或记录改动量。
- 落地检查项：数据修复前记录「改动前后计数/余额」，代码修复另列 commit 跟踪。

### 其它有价值条目

- **部署/推送的「VPN 依赖」要有预案矩阵**：GitHub HTTPS 直连、HTTP 代理（代理端口会随 VPN 开关变化）、SSH 直连三者网络行为不同，须准备切换脚本与探测命令。
- **预编译前端（无 JSX）纪律**：任何前端改动必须 `React.createElement`；括号层级易错 → 每次改完必跑 `new Function` 语法自检；用唯一字符串锚点做 old/new 匹配避免行号漂移。
