## 0. 一句话范围

给 5 个占卜入口补上「仪式感动效 + 可交互翻牌」的前端交互层：

- **观音灵签**：点击「开始」后出现可交互签筒，点击签筒或摇手机掉落 1 支签 → 签转为签文文字（沿用现有签文展示）。
- **六爻 / 梅花 / 小六壬**：点「起卦」先播起卦动画，动画结束再呈现卦象内容（沿用 REQ-044 v2 + REQ-055 结果布局）。
- **塔罗 / 雷诺曼**：选牌阵抽牌先播抽牌动画 → 按牌阵数量落出**背朝上**的牌（3 牌阵 3 张）；点牌背翻转为正面并展示对应解析（塔罗含正/逆位）；提供「一键全翻」。
- **统一**：动效全部可被 REQ-066①「动画与抽卡模拟」开关关闭（跳过动效直接出结果）；塔罗/雷诺曼再受 REQ-066⑥「牌面图片显示」约束（关闭→纯文字列表，无牌背/翻牌动画）。

## 2. 统一机制与横切要求（所有模块共用）

### 2.1 动效阶段状态机（建议的通用写法）

每页保留既有业务状态（method/question/loading/data 等），**新增一个只描述"演出到哪一步"的阶段字段**，不改动数据链路：

```js
// 建议名（各页面按需取子集）
const [stage, setStage] = useState(null);
// 塔罗/雷诺曼：'idle'(menu) | 'pick' | 'deal' | 'down'(背朝上待翻) | 'done'
// 临时起卦：'idle' | 'tube' | 'cast' | 'done'   （sign 用 'tube'，六爻/梅花/小六壬用 'cast'）
```

- 阶段只控制**渲染与入场时序**；真正的取数/落库仍走 `doCast()` / `draw()` / `load()` 等既有函数，`setData()` 不变。
- 动效结束 = 数据就绪 + 动画放完，二者取"较晚者"，之后立刻切到现有 v2 布局（数据早就绪时动画放完即切，无额外等待）。

### 2.2 动画与取数的数据一致性策略（关键设计决策）

动画里"演出来的结果"必须等于后端返回的最终结果，方案分两类：

| 模块 | 策略 | 说明 |
|---|---|---|
| 观音灵签 | **前端先定签号 + replay 固定**：进入签筒时前端在 1..92 随机定 n → `doCast(seed:{options:{replay:[signReplaySample(n)]}})` | 与 REQ-069 手动路径同机制（L9204-9205），签号确定故落签签身可直接显示第 n 签，结果必然一致 |
| 六爻 | **replay 固定逐爻值**（推荐）或 **取数先行再演出** | ①推荐：前端逐爻模拟 6 次掷币定 7/8/9/6 → `options.yaos=[…]`（同 REQ-069 手动路径 L9175）→ 演出与结果必然一致、无等待；②备选：先 `doCast` 拿到 `res.yaoArray` 再逐爻演出（动画所见即结果，但多一次网络等待窗口，需骨架兜底） |
| 梅花 / 小六壬 | **取数先行**：点「开始起卦」即 `doCast`，动画按结果（或可本地推算的序列）演出 | 时间类起卦结果由后端 `customDate` 决定，本地不复制引擎逻辑；动画不暴露卦象数字、只做氛围演出（光圈/符点/掌诀游走），不存在对不上 |
| 塔罗 / 雷诺曼 | **取数先行**：点牌阵即 `draw/load`，出牌动画期间数据已在手 | 数据藏在牌背下，翻牌时才揭示，天然一致 |

> 结论：观音灵签、六爻采用"客户端先定结果、replay 交给后端确定性还原"（与已验收的 REQ-069 手动通道同一契约，零新后端逻辑）；其余模块"取数先行 + 演出并行/随后"。网络慢的兜底：演出结束时数据未到 → 舞台停在上一步并显示轻量 shimmer，数据到达即续演/收尾。

### 2.3 「动画跳过」钩子（呼应 REQ-066① 与 ⑥）

REQ-066 尚未实现，方案预留**统一读取钩子**，落地时由「功能设置」页把开关写入该处即可，各动效不再各自判断：

```js
// 建议统一命名空间（由 REQ-066 落地方注入；未注入视为默认开）
const TC_SETTINGS = window.__TC_SETTINGS || { anim: true, cardImages: true };
const shouldPlayAnim = () => TC_SETTINGS.anim !== false;        // REQ-066①
const shouldShowCardImages = () => TC_SETTINGS.cardImages !== false; // REQ-066⑥
// 另做可及性兜底：CSS @media (prefers-reduced-motion: reduce) 下动画自动退化为纯淡入/直接出结果
```

| 开关 | 对各模块的行为（动画开=本方案 §3 全流程） |
|---|---|
| ①「动画与抽卡模拟」**关** | 观音灵签：不弹签筒、点「开始」直接出签文；六爻/梅花/小六壬：不播起卦动画直接出卦象；塔罗/雷诺曼：无抽牌/翻牌动画，直接以 v2 现状（正面 + 解析全展开）出结果 |
| ⑥「牌面图片显示」**关**（仅塔罗/雷诺曼） | 结果=纯文字列表（卡名 + 正/逆位[塔罗] + 含义段落），隐藏卡面/牌背/扇形；**无条件优先于①**（⑥ 关时不产出任何卡面渲染） |
| ①开 且 ⑥开 | 走 §3.5/§3.6 完整抽牌 → 牌背 → 翻牌流程 |

> 另在每个演出舞台右上角放「跳过动画」小按钮（灰色文字钮，仅动画期间可见），用户单次跳过当前演出（不改变全局开关）。

### 2.4 占位/程序化动效 + 素材替换点预留

- **开发期**：全部器物用 CSS/内联 SVG 程序化占位（签筒=圆台渐变 + CSS 装饰、签=长条矩形 + 签号文字、铜钱=圆形双面色块、牌背=CSS 星点图案、掌诀盘=现有 `.palm-disk`、粒子=少量绝对定位圆点）。不依赖任何外部图片即可完整体验。
- **替换点**：每个器物对应一个**CSS 槽位 + 变量**，样式写成"有素材用素材、无素材用占位"：

```css
/* 示意（§4 每行给出具体槽位名） */
.art-tube{ background: /* 占位渐变 */ url(var(--art-ssgw-tube)) center/contain no-repeat; }
.art-back-tarot{ background: /* 占位星点 */ url(var(--art-card-back-tarot)) center/cover no-repeat; }
```

素材接入方式（两条路，实现时二选一或并用，§5 C9 待确认）：
1. **扩 REQ-059 槽**：动效素材按新 key 家族（如 `anim-ssgw-tube` / `card-back-tarot` 等）配置进运维后台 `asset_slots`，前端经既有 `GET /api/assets` 批量拉取 → 写入 CSS 变量。热更、可回退，与 REQ-059 语义一致；
2. **静态资源直放**：文件放 `frontend/public/` 对应目录、前端常量表配置路径。

### 2.5 移动端适配与减少重绘

- 只对 `transform` / `opacity` 做动画；翻转用 `rotateY` + `backface-visibility:hidden`（前后两面叠放、90° 时换面），不动画 `box-shadow/width/top`。
- 动画器物量少（签 1、铜钱 3、卡 ≤9、粒子 ≤12），且粒子仅 transform 平动；不给整页加合成层，避免显存爆。
- 演出阶段用全屏遮罩（`position:fixed; inset:0; z-index:60`，高于 modal-mask 的 50），`touch-action:manipulation` 防双击缩放、`overscroll-behavior:contain`；演出结束即卸载遮罩，不长期驻留。
- 卡面宽度建议改为 CSS 变量（`--card-w:104px`），≤420px 视口缩小至 ~88px，多张卡随既有 `.card-fan` flex-wrap 自动换行（L614），翻牌卡点击热区 ≥44px。
- devicemotion 监听只在签筒舞台存活期间挂载、离开即 `removeEventListener`（另见 §3.1 权限与降级）。

## 3. 逐模块详细交互方案

> 每模块按「触发事件 → 动效拆分（步骤/时长/缓动）→ 实现路径 → 预期效果示意」给出。

### 3.1 观音灵签（可交互签筒 + 落签转签文）

**触发事件**：自动模式下，起卦弹窗点「开始抽签」（现按钮 `startAsk` L9146 / L9451，建议 sign 时文案显示「开始抽签」）→ 关弹窗 → 进入签筒舞台（替换现 loading 骨架）。

**动效拆分**：

| 步骤 | 内容 | 时长 | 缓动/说明 |
|---|---|---|---|
| S1 舞台就位 | 全屏演出层淡入（暗色氛围 + 程序化粒子），中央出现签筒占位体 + 提示「点击签筒，或摇一摇手机，请一支签」；筒身轻微上下浮 | 0.3s 淡入 | `opacity` + `translateY`，`--ease` |
| S2 摇动/点击触发 | ①点击签筒=直接一次有效摇动；②devicemotion：见下方"摇动检测与降级" | 即时 | — |
| S3 筒身抖动 | 签筒左右晃动 + 微旋转（表现"摇签"），签尾在筒口可见地弹动 | 0.5s | `cubic-bezier(.45,0,.55,1)`，往复 3 次，幅度 ±10px/±7° |
| S4 出签 | 签（签身带签号 n，S0 已定）自筒口斜向弹出并上抛 | 0.5s | `translate3d` 上移 ~60px + `rotate(-160deg)`，`cubic-bezier(.45,0,.9,.4)` |
| S5 空中回落 + 落地 | 签旋转下落至既定落点，落地轻弹 1 次 + 尘土粒子 burst（6–10 粒） | 0.8s + 0.25s | `ease-in` 下落；落地用 2 段式 `cubic-bezier` 小弹跳 |
| S6 签号定格 | 签停稳、签身签号淡入高亮（第 N 签） | 0.2s | `opacity` 0→1 |
| S7 转签文 | 签与舞台 0.25s 淡出 → 结果区出现现有 `DivSsgwView` 签文（第 N 签 · 标题 / 签诗 / 元信息 + 深度解读按钮），带 `.view-enter`（L273）入场 | 0.25s+0.34s | 与现状布局一致 |

全程约 1.8–2.6s（不含用户在 S2 的停留等待）。

**摇动检测（devicemotion）与降级**：
- 仅 sign 自动模式 + 动画开时挂载 `deviceorientation/devicemotion` 监听。
- **权限**：iOS 13+ 需先 `DeviceMotionEvent.requestPermission()`（须在用户手势内调用）——把该请求挂在**用户首次触摸签筒**时一并处理（点击签筒本就是兜底触发，二者不冲突）；拒绝/无权限/桌面无传感器 → 自动进入"点击模式"，界面提示文案自动切换为「点击签筒请签」。
- **判定**：窗口 800ms 内检测到 ≥3 次「合加速度峰值 > 15 m/s²」判为一次有效摇动；触发后有 1.2s 冷却，一次会话只掉一支签（点「再摇一支」重置才可再来——沿用现有「重新起卦」入口语义）。
- `visibilitychange` 页面隐藏时暂停检测；舞台销毁即移除监听。

**实现路径**：
- 新增组件 `SsgwTubeStage({ fixedNo, onFinish })`（渲染于 DivinationPage body 区，替代 loading 分支；或全屏 overlay，建议前者内嵌一个 fixed 全屏演出层）。
- 状态：`stage`（见 §2.1）；`signNo` 复用于签号 n（**与手动模式共用现有 `signNo` state 与校验 1–92**，L9004）；签号决定：进入舞台时 `n = 1 + Math.floor(Math.random()*SSGW_POOL_SIZE)` → `setSignNo(n)`。
- 触发取数：用户完成摇动（或点击）的瞬间调用 `doCast({question, options:{replay:[signReplaySample(n)]}}, null)`（走 `run` 同款 seed 组装，仅补 replay；`signReplaySample` L8980 已存在）。
- 落签动画结束 & `data` 就绪 → `setStage('done')` → 现有 `data` 分支（L9269）渲染（`DivSsgwView` 自动命中，L9247）。
