> 来源：需求方提出的成本质疑（"34 亿 token / 月，绝不是写一个 Web 项目 MVP 的正常消耗"）与开发 Agent 的诚实分解回复。
> 性质：一线观察的**定性 + 量级**分析（Agent 声明无法后台查 token 精确明细），非账单级精确数据。
> 用途：作为 `docs/Retrospective/01-项目准则.md` §4「Agent 运行成本准则（Token 经济）」的提炼来源。

---

## 一、需求方质疑

**34 亿 token / 月，绝对不是"写一个 Web 项目 MVP"正常消耗；这是【自治 Agent 框架（DSH / OpenClaw）持续不断地循环思考、工具调用、反复重试、大量上下文回放】才会产生的量级。**
普通人类 + 普通 AI 代码助手写项目，**根本达不到这个 token 规模**。

## 二、开发 Agent 的分解（先声明能力边界：无法后台查 token 精确明细，以下为基于本 session 实际运行模式的定性 + 量级分析）

### Token 都烧在哪（四层分解）

**① 主 Agent 本会话 —— 上下文回放是大头**
- 每轮工具调用都带着完整历史上下文；AGENTS.md 全文、需求表、Bug 表这些大文档在会话中反复出现；
- 读了 index.html（2.1 万行 / 1.1MB，约 35~40 万 token）几十个区块、需求表（150KB）多次、架构文档全文——每次读取都全额计入；
- 会话不收敛，越到后面每轮"回放"成本越高。

**② 子代理 —— 每个都是一次完整烧钱**
- 8 个需求派了 8+ 个子代理，每个子代理都有独立上下文（读大文件、写大段代码、跑验证），单个可能 10 万~50 万 token 级；
- 用的是继承本会话上下文的通道时，每次启动还回放主会话已积累的全部历史——主会话越肥，子代理启动费越贵；
- 每个子代理交付后，主 Agent 验证（读 diff、跑 precompile、grep、台账编辑）的输出也全部回放。

**③ 并行 Session（额外开的美术 / 需求管理 / 测试组）**
- 美术 Agent 反复 ImageGen 迭代（回执里能看到：黑图重出、批量重出、precompose 反复、rejected 帧归档）——每轮都是完整思考 + 调用；
- 需求管理员、测试组各自独立消耗。

**④ 反复重试与循环**
- 子代理通道失败重试（某通道失败 2 次换通道）；
- 部署构建卡死 → 重启 → DNS 修复 → 限流重建，多次 SSH / 轮询；
- 排查反复试错（浏览器起不来、CDP 卡住、grep 转义问题试了 N 次）——每次失败都是全量上下文回放 + 新输出。

### 为什么普通开发到不了这个量级

| 维度 | 普通开发 | 本项目实际 |
|---|---|---|
| 上下文 | 单轮问答，即问即答，用完即弃 | 长会话 + 回放，每轮携带全部历史 |
| 文件访问 | 人脑只读需要的几行 | 框架反复整段读 1.1MB 单文件 |
| 执行者 | 1 个人 + 1 个助手 | 主 Agent + N 子代理 + 并行 Session 同时烧 |
| 失败成本 | 人看一眼重敲 | 完整重试 = 全量回放 |
| 轮数 | 几十轮 | 数百轮工具调用 |

**根子**：不是"用 AI 写代码"，而是"让一个自治 Agent 团队替你做完整软件工程"——架构、拆任务、派活、验收、台账、部署全自动化，每一层都吃 token。这是这套模式的设计使然。

### 哪些是可以省的（含 Agent 自身责任）

1. **子代理通道**：用独立上下文的通道（省掉继承回放）；那次失败值得修，别将就；
2. **大文件重复读**：2 万行单文件被主 Agent 和每个子代理反复整段读——规范"先 grep 精确定位再只读命中行"能砍掉大头；
3. **会话收敛**：里程碑结束就开新会话（清空回放），别一个会话拖几百轮；
4. **失败先诊断再重试**：部署 / 验证的反复试错，每次都该先想清楚再动手；
5. **AGENTS.md 精简**：每轮注入的成本累计可观；
6. **并行 Session 数量**：美术 / 需求 / 测试并行是功能需要，但每个都是独立烧钱，能串则串。
