# 文档范式 · 协作守则（开发 / 测试 / 需求管理协作协议）

> 定位：定义多个独立 Session（开发 / 测试 / 需求管理）如何在"彼此看不到对方过程、只共享一个仓库"的前提下，异步、可追溯、无冲突协作。
> 核心一句话：**状态写在表里、结论写在 commit 里、交接写在文档里；谁改状态谁负责下一步通知（通过状态本身）。**

## 1. 核心原则（三条）

1. **文档是唯一黑板**：任何"要对方知道 / 要对方做"的事都写进仓库文档（需求表 / Bug 表 / 交接文档），不靠口头、不靠记忆。
2. **状态即沟通**：需求 / Bug 的状态流转就是双方的对话——谁改状态，就代表"这件事现在轮到谁"。
3. **commit 可追溯**：所有代码提交在 message 里带编号，用 `git log` 即可还原"哪个需求 / 哪个 bug 由谁、何时、怎么改的"。

## 2. 共享载体（沟通媒介清单）

| 载体 | 内容 | 主要维护方 |
|---|---|---|
| 需求表 | 需求 + 优先级 + 状态 + 验收标准 | 开发登记，测试确认验收 |
| Bug 表 | 缺陷 + 严重度 + 状态 + 复现步骤 | 测试登记，开发修复，测试关闭 |
| 测试交接文档 | 测试工作说明、走查清单、已知问题 | 测试组 |
| Session 交接文档 | 每轮总结 + 下一步 | 双方各自收尾更新 |
| Git commit message | 代码变更记录（带编号） | 开发（业务代码）/ 测试（测试代码） |
| 交付物中心 `docs/exchange/` | 跨 Session 交付类文档（素材 / 文案需求单、交付回执、示意），接入完成或确认后归档 | 交付方 / 需求管理员 |

## 3. 状态机与责任人

### 3.1 需求（REQ）

| 状态 | 含义 | 由谁设置 | 下一个动作 |
|---|---|---|---|
| 🟡 待办 | 已登记，未开发 | 开发（或任意） | 开发组开始 → 🔵 |
| 🔵 开发中 | 开发组正在实现 | 开发 | 开发完成 → 🟠（备注"待验收"） |
| 🟠 待验收 | 开发完成，等测试验收 | 开发 | 测试组验收 → 🟢 / 不通过 → 登记 BUG |
| 🟢 已验收 | 测试通过、已上线 | **仅测试组** | 结束 |
| ⚪ 已归档 | 明确不做 / 暂缓 | 开发 | — |

### 3.2 Bug（BUG）

| 状态 | 含义 | 由谁设置 | 下一个动作 |
|---|---|---|---|
| 🟡 待办 | 测试登记，待修复 | 测试 | 开发组认领 → 🔵 |
| 🔵 处理中 | 开发组正在修复 | 开发 | 修复提交 → 🟠（备注"待验证"） |
| 🟠 待验证 | 修复已提交，等测试验证 | 开发 | 测试组验证 → 🟢 / ⚪ |
| 🟢 已修复 | 测试验证通过 | **仅测试组** | 结束 |
| ⚪ 已关闭 | 不复现 / 重复 / 不修 | 测试（注明原因） | — |

> 约定：**🟢 只能由测试组设置**；开发组最多设置到 🟠。
>
> **口径联动（补充）**：口径修订导致返工 → 状态退回 🟡/🔵 并注明"返工待开发"；🟠 只挂"已实现待验收"，不挂未开发条目；口径演进优先"新行 supersede + 旧行保留历史 + 备注互链"，不删改已验收原文。

## 4. 协作工作流（一个需求的完整循环）

```
开发组                          测试组
  │ 登记/认领 REQ-xxx 🟡           │
  │ 开发 → 🔵                      │
  │ 完成 → 🟠（备注「待验收」）      │
  │  commit: feat ... REQ-xxx      │
  │                                │ 读需求表，看到「待验收」的 REQ
  │                                │ 按验收标准真机/自动化验收
  │                                ├─ 通过 → REQ 置 🟢
  │                                └─ 不通过 → 登记 BUG-yyy 🟡（关联 REQ-xxx）
  │ 读 Bug 表，认领 BUG-yyy 🟡      │
  │ 修复 → 🔵 → commit fix BUG-yyy → 🟠 │
  │                                │ 验证修复 → BUG 置 🟢 / ⚪
  │                                │ 回归 → REQ 置 🟢
```

## 5. 沟通约定（让 git log 能当聊天记录用）

1. commit message 必须带编号：
   - 新功能：`feat(模块): 描述（REQ-xxx）`
   - 修 Bug：`fix(模块): 描述（BUG-yyy）`
   - 测试：`test(模块): 描述（覆盖 REQ-xxx / 验证 BUG-yyy）`
2. 每轮收尾必做（双方各自）：更新本 Session 涉及的 REQ / BUG 状态；交接文档追加"本轮做了什么 + 待对方做什么"。
3. 交接触发：当 REQ 备注出现"待验收"或 BUG 备注出现"待验证"时，对方下一轮先处理这些。

## 6. 分工边界与冲突避免

| 事项 | 开发组 | 测试组 |
|---|---|---|
| 业务代码 | ✅ 改 | ❌ 不改（发现 Bug 只登记 + 附复现 / 测试） |
| 测试代码 | 可补 | ✅ 主维护 |
| 需求表 / Bug 表 / 交接文档 | ✅ 可改 | ✅ 可改 |
| 简单文案 / 样式 Bug 修复 | ✅ | 可提 PR，由开发确认 |

- 双方**不同时改同一份代码文件**；文档（需求表 / Bug 表 / 交接文档）是冲突高频区，约定"先 pull 再改、改完尽快 commit"。
- 共享台账并发写触发 IO 错误时，重读再改，不强行覆盖。

## 7. 单轮 Session 收尾 Checklist（双方通用）

- [ ] `git pull`（拿到对方最新状态）
- [ ] 更新本 Session 涉及的 REQ / BUG 状态（含"待验收 / 待验证"备注）
- [ ] 在交接文档追加本轮总结
- [ ] commit（message 带 REQ / BUG 编号）
- [ ] push（让对端可见）
