# ADR-0001: 排盘层以自研为主，mingli 仓库仅作参考

## Status

Accepted（2026-09-05）

## Context

- 技术框架方案 v2.3 §5.5（R4 + C1）定为「**原样复用 mingli Skill 契约**」，收益是零契约漂移、
  Skill 升级新增字段自动惠及产品。
- 但落地时暴露三个问题：
  1. 产品化需求（多用户隔离、异步长任务、token 计量、REST 投影）与 Skill 的「单会话文件目录」
     形态不匹配，复用需大量适配层；
  2. 复用的实现链被简化——最典型的是**校验子会话被整体省略**（见 ADR-0002），说明"原样复用"
     在执行层面并未真正成立；
  3. 用户明确决策：**别人的 repository 仅作参考，不完全复用；以本地重新写逻辑的形式纳入**。
- 关键补充事实：**mingli 本身是用户从 `reference/` 下其它项目复刻而来的产物**，并非第三方仓库。
  因此契约所有权归太初自主，不存在第三方兼容包袱。
- 硬约束：排盘是历法算术，**正确性风险极高**；自研历法 / 星历不可接受。

## Options

| 方案 | 描述 | 优点 | 代价 |
|---|---|---|---|
| **A** | 底层排盘能力用开源库（`lunar-python` / `iztro` / `mingyu-core`），胶水、切片、打分、提示词全部自研 | 数周可控；排盘正确性由成熟库保证；实现完全自有、可为产品化需求定制 | 需自建排盘适配层并做回归 |
| B | 连底层排盘库也全部自研 | 完全自主可控 | 历法算术 / 紫微星曜 / 占星星历自研工作量以月计，且排盘错 = 产品全盘错 |
| C | 原样复用 mingli 脚本与提示词（v2.3 现状） | 起步最快 | 与产品化需求冲突，受上游掣肘，且已被证明执行中会丢步骤 |

## Decision

选择 **A**。

- **自研**：排盘胶水（`paipan` 调用与降级）、切片（`slice`）、契合度打分（`score`）、
  全部 method-prompts、shared 提示词、阶段 5 合并规则。
- **引入**：`lunar-python`（八字历法）、`iztro`（紫微）、`mingyu-core`（占星 / 七政 / 奇门）
  作为**普通依赖**——它们是独立开源库，不是 skill 仓库代码。
- **参考**：`reference/mingli/` 保留作为设计与契约的对照物，**不参与构建**。
- **契约**：自主定义，兼容 mingli 关键字段（见 ADR-0001 附注）。

## Consequences

### 变得更容易
- 实现完全自有，可为异步、计量、多用户隔离等需求定制，不必迁就 Skill 的文件目录形态。
- 不受上游变更掣肘；契约演进由太初自主决策。
- 排盘正确性由成熟开源库兜底，历法风险不外溢。

### 变得更难
- 失去 C1 声明的「Skill 升级自动惠及产品」红利 → 改为**主动同步**：上游有实质改进时人工评估并回写。
- 需自建排盘适配层与回归基线（8+1 法的排盘结果快照）。
- 提示词需自行维护与防漂移（案例库锚点从 Phase2 提前到 MVP 必做）。

### 契约归属（附注）

`chart.json` / `method-result v2` / `校准记录.json` 的字段结构**由太初所有、可自由演进**，
保留 mingli 的成熟设计（method key 命名、四档 `confidence_level`、`past_propositions` 语义、
`weight = 0.4 + 0.6 × 契合度`）以便对照调试。因 mingli 同为本人复刻产物，兼容是**选择**而非义务。
