# ADR-0007: MVP 维持强制注册（R7 现状）

## Status

Accepted（2026-09-05）

## Context

- R7 定为 MVP 即建用户体系：用户名 / 密码注册 + JWT，无手机 / 微信绑定，不做找回。
- 产品规划 §6.1 同时强调**落地页转化**（避免"什么都能算"的落地页，转化最低），
  而注册墙是 H5 转化漏斗中最大的流失点之一。两者存在张力，原方案未评估。
- 产品规划 §1 的原始表述只要求「每个用户进入后拥有独立 session」，**并未要求注册**——
  注册是 R7 追加的。

## Options

| 方案 | 描述 | 优点 | 代价 |
|---|---|---|---|
| A | 免注册试算 → 结果页引导注册 | 转化摩擦最小 | 需匿名 case 机制与后续账号合并策略 |
| **B** | **维持强制注册（R7 现状）** | 实现最简；数据资产从第一次调用即绑定 `userId`，档案不丢 | 注册墙造成转化流失 |
| C | 游客限次试算（1 次） | 折中 | 需匿名配额与防刷策略 |

## Decision

选择 **B（维持强制注册）**。

理由：MVP 阶段的**首要目标是量出单位经济**（self-run 10×，产品规划 §6.3），不是规模化获客。
在成本未知、定价未定的阶段，优化转化的收益无法评估；而匿名 case + 账号合并会引入新的
数据一致性复杂度。强制注册让每一行数据从第一次调用就归属明确，多用户隔离（C20）也更容易验证。

## Consequences

### 变得更容易
- 实现最简，MVP 可最快跑通闭环。
- 数据资产从第一次调用即绑定 `userId`，无孤儿 case。
- 多用户隔离的验证面更干净（不存在匿名态的边界情况）。

### 变得更难
- **转化摩擦未消除**：注册墙的流失量在 MVP 阶段无法测量（没有流量）。
- 后续若转向 A / C 方案，需新增匿名 case 表与合并逻辑，属数据迁移类改动。

### 复评触发条件（写入待办）

当**获客开始投放、日活进入可测区间**时，必须复评本决策——届时注册墙的流失率可被实测，
再决定是否引入免注册试算。在此之前维持现状。

### 降低摩擦的低成本补偿（建议，不阻塞）

- 注册表单极简：只要用户名 + 密码，无昵称、无邮箱、无手机。
- captcha 只在异常频次时触发，而非每次注册都验（降低正常用户摩擦，同时保留防机器注册能力）。
