# ADR-0005: 长任务采用 jobId + 前端代码轮询（零 LLM 调用）

## Status

Accepted（2026-09-05）

## Context

- 断前尘为 **9 法串行 + 每法一次校验**（ADR-0002 / ADR-0003），端到端可达**数分钟**。
- 技术框架方案 v2.3 §11 已识别该风险并写「前端轮询 / 流式」，但 §5.1 的 REST 端点表
  **全部为同步接口，没有任何异步任务或状态查询端点**——契约与风险描述自相矛盾。
- 用户关注点确认：轮询必须是**代码轮询**，不得产生额外 token。

## Options

| 方案 | 描述 | 优点 | 代价 |
|---|---|---|---|
| **A** | **POST 返回 `jobId` + 前端定时 GET 状态** | MVP 最简；与单进程一致；无连接管理负担；**零 LLM 调用** | 有轮询间隔延迟（1–2s），非实时 |
| B | SSE 流式推送 | 逐法进度实时，等待体验最好 | 连接管理、断线重连、代理缓冲配置；单进程下长连接占用 |
| C | 同步长连接 + 延长超时 | 改动最小 | 受 CDN 与网关超时限制，香港节点链路长，超时行为不可控 |

## Decision

选择 **A（jobId + 代码轮询）**。

### 轮询机制（明确：零 token）

```
前端 setInterval（建议 2s，带指数退避上限 10s）
   → GET /api/jobs/{jobId}                      ← 纯 HTTP 读状态
   → 后端查 jobs 表，返回 { status, completed, total, result? }
   → 前端渲染进度条「已完成 3/9」
```

- **整条轮询链路不经过 LLM**。LLM 只在方法模块做分析 / 校验时被调用；轮询只是读数据库里的
  任务进度行。
- 轮询间隔在前端配置，服务端不推送；任务完成后前端停止轮询并拉取结果。
- 兜底：单次任务硬超时（断前尘建议 10min）后标记 `failed`，前端停止轮询并提示。

### 异步化的端点（仅这两个）

| 端点 | 变更 |
|---|---|
| `POST /api/cases/{id}/duan-qian-chen` | 改为返回 `202 { jobId }` |
| `POST /api/cases/{id}/predict` | 改为返回 `202 { jobId }` |

其余端点**保持同步**：`paipan`（纯代码，秒级）、`calibration`（`score.py` 纯代码）、
`revise`（单轮 LLM）、`query/{methodKey}`（单法 + 缓存优先）、`archive`（查库）。

### 任务状态

新增 `jobs` 表（用户分析库）：`id`、`case_id`、`user_id`、`type`、`status`、`total`、`completed`、
`error`、`created_at`、`updated_at`。任务进度由 `jobs` 模块订阅 `MethodAnalysisCompleted` 推进。

## Consequences

### 变得更容易
- 契约与长时编排风险对齐，不再自相矛盾。
- 前端可实现真实的「已完成 3/9」进度反馈，缓解数分钟等待的焦虑。
- 零额外 token 成本（明确排除 AI 轮询）。
- 单进程下无长连接占用，实现简单。

### 变得更难
- 新增 `jobs` 模块 + `jobs` 表 + 2 个端点改异步（契约变更）。
- 前端需处理轮询、退避、超时、失败重试的 UI 状态机。
- 任务失败后**已完成的法其结果仍落库**，重试时靠缓存键复用，不会重复计费——需在实现中验证。
